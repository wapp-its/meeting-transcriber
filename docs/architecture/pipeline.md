# Pipeline and output

Concurrency, audio loading, job restore, protocol generation, record-only mode and output folders.

**Concurrency:**
- `WatchLoop` is `@MainActor`. Tests for this class must also be `@MainActor`.
- Both engines deduplicate concurrent loads with `SingleFlight`. Absent an explicit release, WhisperKit still finishes with the currently requested variant loaded or a failure for it, retrying variants superseded mid-load (issue #738). A model release invalidates the in-flight generation: its original caller may return without a loaded model, and a fresh caller that joined that stale flight retries. WhisperKit includes the generation in `LoadAttempt` alongside the variant/origin result; Parakeet's flight returns an `Int` generation. The load postcondition is therefore subject to explicit release, as described in [transcription engine model retention](transcription.md).
- The queue's processing flag alone is not the idle boundary: the lifetime observer also reads waiting and active jobs and whether recording or the stop-time caption flush is in flight. The queue records `lastDrainID` when processing ends with no waiting or active jobs, so even a drain completed within one actor turn survives coalesced observation callbacks. The observer retains the previous queue through its next turn so a queue replacement cannot hide that final marker. A queue drain while that combined state is busy cannot release models. Once it is idle, the selected model and cached batch VAD follow the retention policy in [transcription engine model retention](transcription.md). This boundary keeps one model warm across adjacent jobs and through a recording's buffered caption tail; it also applies deferred setting changes and, with idle unloading on, retires an inactive engine after a switch.
- `ClaudeCLIProtocolGenerator` runs the CLI (and its `--help` probe) through `BoundedProcess.run(timeout:onStop:)`: a timer on the suspending clock and the calling task's cancellation both stop the process (SIGTERM to its process group, SIGKILL after a grace), and the exit wait deliberately ignores cancellation, so the run returns or throws (`ProtocolError.timeout`, `CancellationError`) only once the CLI is gone and its folders can be removed. A run is `.timedOut` only if the CLI was still running at the limit. No pipe is read or written blocking, since a process the CLI started can hold one open after it exits: stdout/stderr are read through readability handlers into `AsyncStream`s that end at EOF or a short drain grace after the exit (stderr keeps its last 64 KB), and the prompt goes to stdin through a `DispatchIO` channel (SIGPIPE off) that is stopped with the CLI.

**Audio loading:**
- `AudioMixer.loadAudioAsFloat32()` uses a 3-tier fallback: `AVAudioFile` → `AVAsset` → `FFmpegHelper` (ffmpeg CLI).
- `loadAudioFromAVAsset()` extracts audio tracks via `AVAssetReader`, outputs 16kHz Float32 PCM. Rescue path only: `AVAudioFile` opens MP4/MOV too on current macOS, so this runs just when tier 1 throws on a non-MKV/WebM file. Its reader is configured like `streamResampleFile` (precise timing, little-endian float, source channels averaged in Swift), each option for a measured trap: an Ogg Vorbis track where `copyNextSampleBuffer()` blocks forever partway through, an AIFF read byte-swapped into NaN, a +3 dB fold against tier 1, and `DiscreteInOrder` decoding to silence with `status == .completed`. Sizing reads the AUDIO TRACK's duration, never the asset's: on a video container whose picture outlasts its sound the asset overstates the audio by seconds. That duration is untrusted (NaN for an indefinite one, absurd for a corrupt field), so the pre-allocation is capped rather than believed.
- `FFmpegHelper` detects ffmpeg binary (env var → `/opt/homebrew/bin` → `/usr/local/bin` → `~/.local/bin` → `/usr/bin`), cached via static let. Converts to 16kHz mono WAV via temp file. The run is bounded like the Claude CLI run (`BoundedProcess` + `ProcessOutput`); timeout → `ffmpegFailed("timed out after N s")`, cancel → `CancellationError`.
- Both `NSOpenPanel` type lists (batch import + voice enrollment) come from `AudioImportTypes`, not inline literals — the panels are manual-QA-only, so the pure type list is what tests can pin. Only MKV/WebM are ffmpeg-gated; AMR, 3GPP and Ogg (`.opus`/`.ogg`) decode natively and must stay out of `FFmpegHelper.ffmpegOnlyExtensions`, whose members skip `AVAudioFile`/`AVAsset` entirely.
- ffmpeg is optional — install via `brew install ffmpeg`. Status shown in Settings → About.
- The ffmpeg-tier tests (`FFmpegHelperTests` fixtures, the MKV/WebM legs of `WhisperKitE2ETests`) skip without ffmpeg, except on a GitHub runner, where they fail (`requireFFmpeg` / `ffmpegAvailableForTests` in the test helpers): a CI skip is how that tier once went untested in every lane. Every CI job that runs them first runs `.github/actions/setup-ffmpeg`, which installs a pinned, checksum-verified static build and exports it as `FFMPEG_BINARY`.
- **A finished job only relocates audio the app itself produced.** `AudioPersistencePolicy` decides per file: sources inside the staging dir (`AppPaths.recordingsDir`, where `DualSourceRecorder` writes) move into `<outputDir>/recordings`, sources already there stay put (moving would rename them under a fresh stamp and orphan recovery would re-pick them forever), and anything else is a user-picked import that is left untouched. Persisting an import would duplicate a file the user already has for no consumer: re-diarization and late naming read the `_16k.wav` sidecar, while orphan recovery and `ProcessedRecordingsLedger` only scan the staging dir. Consequence to keep in mind: a finished import leaves **no audio at all** in the output folder, only the transcript and the protocol. The 16 kHz sidecars live there while speaker naming is outstanding and `removeNamingData` deletes them once it resolves. The source staying in the user's folder is the archive. **A relocated job then carries the new paths.** `PipelineJob.recordRelocatedAudio` is the only writer of the three path fields after enqueue (they are `private(set)`), and the queue wrapper around it writes the snapshot itself rather than waiting for the next state transition: `generateProtocol` returns before its own `.generatingProtocol` transition when no protocol generator is configured, so with `protocolProvider == .none` there would be no transition to ride on. Without this the job named an emptied staging path, and quitting during the protocol call made the restore discard it: no protocol, no job, no notification. **A slot reports the destination only when the file is actually there** (this run moved it, or an earlier run already did); every other outcome, a failed move included, reports the source, because a path nothing can open would land in `ProcessedRecordingsLedger` while the real file waited in staging to be re-picked as an orphan. Consequences: the ledger records the destination for a relocated recording (inert, the orphan scan only reads staging), and the restore's missing-audio rule now fires only on genuinely missing files, failed relocations, and snapshots written before this existed. That rule also logs what it discards now, and rewrites the snapshot so the same dead entry is not re-read and re-logged on every launch.
- **Recording retention (issue #723)** deletes relocated audio once it is due: Settings → Output → Recording Retention (`AppSettings.recordingRetentionEnabled`, off by default; `recordingRetentionDays`, where 0 means as soon as the outputs exist). It deletes only what `RecordingRetentionRegistry` (`retained_recordings.json` in `logDir`) lists and never lists the folder, so imports, record-only captures and audio from before the feature are out of reach by construction, not by a rule. Stage 3 writes the entry at the move, for exactly the files `persistAudioToOutput` reports it moved in this run (never a destination that already held a file whose source is gone: it may be the user's), whatever the setting says; a relocation under a different root starts a second entry for the job: a run restored after a quit finds its audio already relocated and moves nothing, so an entry left for `.done` would never be written for it, and switching retention on later must cover what was recorded while it was off. The entry becomes eligible where the run's output is produced, never at `.done` (`PipelineQueue.markOutputWritten`, which also requires a regular file with content): when `generateProtocol` saves the protocol, when it finds no generator (the transcript is the output then), when a restore finishes a job whose protocol was already written, and when the auto-names are accepted with no provider (`finishWithAcceptedAutoNames`). Everything else that reaches `.done` keeps its audio without a rule of its own: a failed protocol call, a job finished because its naming data was lost across a restart, and a late confirm that could not read the transcript or write the names into it (the transcript is the unconfirmed draft then). A protocol-only resume after a quit does not count the transcript even with no provider now, since the run it continues was generating a protocol. Marking before `.done` is safe because the policy keeps every entry a job that is not done holds. The output is checked again at delete time: one the user deleted since keeps the audio. The exception is a Notion export set to replace the local Markdown: once it succeeds and the local copy is removed, the entry is marked `outputExported` and the page counts as the output. Days count from `artifactStartTime`, the stamp in the file name. `RecordingRetentionPolicy.decide` keeps a whole entry when any of its tracks belongs to a job that is not done (a run reads `_app.wav`/`_mic.wav` too, and the in-flight claims name a run's staging mix path, not the relocated files, so the current queue's unfinished jobs are the real protection; a queue is only replaced once all its jobs are finished), and keeps an entry whose root is missing, or whose `recordings` folder cannot be listed (the sandbox can show the root and hide its files), since an unplugged drive read as "files gone" would drop the entry and make the files permanent. Under a live scope on one output folder, an entry under another root is kept as unreachable. Only files directly in the root's `recordings` folder are deleted, both as written and with symlinks resolved (the containing folder, plus the file itself when it exists). An entry whose audio is all gone is dropped whether or not it ever became eligible, as long as its root is reachable. Only regular files are deleted: a listed path that is now a folder or a link is skipped and stays listed. Decisions and registry writes run on the main actor, the deletes on `RecordingFileDeleter` (Spotlight stall class, as with the snapshot writer), with a nested scope opened on the root the queue holds a scope on; if it cannot be opened the pass deletes nothing. Every delete is rechecked on the main actor right before it runs (the entry still lists the path, the settings still make it due, no unfinished job of the queue that started the pass or of the current one holds any of its tracks, the registry is saved), a deleted path is forgotten only for the entry the decision was made for, and no pass deletes while the last registry write failed. The AI-title rename repoints the entry, also for files a failed rollback left under the new name. Passes run when a job reaches `.done`, after a queue rebuild, one second after either setting stops changing; every pass acts on the settled settings, so a value the stepper only passes through never acts, while switching off or lengthening the period applies at once; at launch and hourly; a pass with retention off, or with nothing listed, returns at once and logs nothing; every other pass that gets past saving the registry logs one info line with counts per outcome and keep reason, due files next to deleted files, and never a path (file names carry the meeting title), since a pass that only keeps would otherwise leave no trace that it ran; before a built queue is installed, a pass reads the output folder with `OutputDirectoryResolver.current` (never `resolve()`, which reports an unreachable folder) and the queue snapshot itself and keeps every track a job in it names, because the placeholder queue has not loaded it; an unreadable snapshot skips the pass. A registry file that exists but cannot be read or decoded is moved aside to `.unreadable` instead of being overwritten.
- **The fork's additions to recording retention** (`PipelineController+RetentionRecords.swift`): each build keeps its own registry, `retained_recordings.<bundle id>.json` (`RecordingRetentionRegistry.filename(bundleID:)`), because the development and the release build share `logDir` but not their settings. A pass deletes the audio of a listed job only when `retentionRecordGate` allows it (`RecordingRetentionPolicy.RecordGate`, keep reason `heldByRecord`): the job's meeting record, read from the record file at the start of the pass and again right before each delete, has to allow it (`MeetingFileRecord.allowsRetention`: a recording, not an import, created by this build, finished, not marked Keep, no deletion of the user's pending or incomplete, not a recovered recording from before the records), and the queue has to be through with the job (`LiveMeetingState.isSettled`: done with no Notion export running; a job the queue does not hold counts as unsettled while the saved jobs cannot be read, also after a failed snapshot restore). A job without a record is never deleted, and a record file that does not read skips the pass. Right before each delete the output is checked again as well, after the record check, since the original's recheck covers the entry, the settings and the queue only. The record check writes no mark of its own, so Keep set by the other build while a file removal stalls does not stop that one file, only the files after it (accepted; the fork's earlier deletion claimed the meeting under the record file's lock first). The files a pass found gone are marked gone in the record (`didDelete`), dated as an automatic deletion once no audio is left and only when the pass removed a file itself (`RecordingFileDeleter.deleteTellingRemoved`). A cancelled job's recording, which `relocateRecordingOfCancelledJob` moves to the output folder, is never registered. The fork's earlier `recordingRetention` setting is not read.

**Restoring an interrupted job:**
- `ProtocolResumePolicy.decide(interruptedIn:transcriptExists:hasNamingSlug:hasProtocol:)` is the pure decision the snapshot restore makes for a job it found mid-run: `.resumeProtocolOnly` generates the protocol from the transcript already on disk, `.finish` only applies the terminal transition, `.fullRun` re-runs everything.
- **It keys on the stage the job was interrupted in, never on "a transcript exists":** `saveTranscriptDraft` writes one in stage 1, so a job killed during diarization has a draft without speaker labels, and resuming from it would publish that draft. Only `.generatingProtocol` means the transcript on disk is the finished one. A late re-diarization therefore runs in full by design: its transcript is the segmentation the user asked to redo.
- The marking is the snapshot state itself, held in memory as `protocolResumeDispositions` for the span of one restore. Nothing is persisted: a quit before the resume runs degrades to a full run rather than losing anything, and a second persisted field would have to be kept in step with the state it was derived from.
- **A failed or interrupted Notion export, or failed meeting notes, come back at launch.** `restorePendingNotionExports` builds the first queue when every saved job is `done` and at least one is held after completion (`isHeldAfterCompletion`: a pending export, or notes to retry), so the retry row appears without a watch start. Any other saved job keeps waiting for a user action, because building the queue would resume it; a notes retry that was still waiting at the quit is such a job, and runs once something builds the queue.
- **A Notion retry sends the page it would have sent the first time, from the local backup alone.** With the transcript option on, the export appended the transcript under `## Full Transcript` in the file it saved, and `MarkdownToNotionBlocks` reads that section back into the same toggles, so the retry passes no separate transcript. The retry replaces the page's blocks, so a job whose option was on and whose backup has lost that heading is refused with a fixed warning and stays failed: sending it would swap a page that has the transcript for one that has none.
- Why it is not merely a saving: a late confirm transits `.generatingProtocol` too, so a full run there re-diarizes, discards the names the user just confirmed and parks the job back in the dialog they just closed.

**Speaker naming window:**
- **The naming window opens by itself only while `AppSettings.autoOpenSpeakerNaming` is on (default).** A job with naming data parks at `.speakerNamingPending` either way; the setting only gates the two automatic `.showSpeakerNaming` posts, after processing (`PipelineQueue+Stages`) and on snapshot restore (`PipelineQueue+Recovery`). The queue reads it through a closure, like `echoCancellationEnabled`, so a change applies without restarting watching. Off, `onSpeakerNamesWaiting` takes the window's place at both points and `PipelineController` turns it into a "Name Speakers" user notification; the restore site is needed because a job restored already pending never makes the transition again. The user then gets back to it through the menu bar's "Name Speakers...", and the stale cleanup on launch still accepts the auto-names once `AppSettings.staleNamingTimeout` has passed. A window the user opens, or the return from a late re-run they started, is not gated (and does not notify). A waiting job holds the queue meanwhile; see **Unnamed meetings on launch**.

**Retrying a failed job:**
- **The menu offers Retry from state alone, never from a file check.** `canRetryJob` runs in the view body on every render, and the recording can sit on a network or removable volume where `fileExists` blocks the main thread. `retryJob` checks the file itself on every click; one that finds it gone adds a fixed sentence to the job's error text (once) and changes nothing else, and the offer stays, so a volume that comes back is retryable. See the comments on `canRetryJob`.

**Unnamed meetings on launch:**
- **A meeting left waiting for names longer than `AppSettings.staleNamingTimeout` gets the automatic names at the next launch.** `loadSnapshot` runs `cleanupStalePending()`, which reads the timeout through a closure (`staleNamingMaxAge`, wired in `PipelineController.makeQueue`) and accepts the auto-names for every `.speakerNamingPending` job whose wait, counted from `namingDeadlineStart`, is longer: 1 day (the default, and the only value before the setting existed), 7 days, or never. It runs only on launch, so a meeting is resolved at the first start after its time is up, not the moment it expires. `cleanupStalePending(maxAge:)` is the ungated form tests use. **A waiting job also holds the queue.** `.speakerNamingPending` keeps `PipelineController.canReplaceQueue` false, so `rebuild()` (every watch start) and `rebuildIfOutputFolderChanged()` skip, and engine, diarization and output-folder changes reach new meetings only once the job is named or skipped, or after a relaunch (whose first rebuild runs on the empty placeholder queue). With the naming window opening by itself that wait is usually minutes; with it off (`autoOpenSpeakerNaming`) it lasts until the meeting is named or the timeout passes, and with Forever nothing bounds it, which the Settings caption says.

**Protocol generation:**
- `ProtocolGenerating` protocol with two implementations: `ClaudeCLIProtocolGenerator` and `OpenAIProtocolGenerator`.
- `AppSettings.protocolProvider` enum (`.claudeCLI` / `.openAICompatible` / `.none`) selects the provider. `.none` skips LLM generation and saves the transcript only.
- `AppSettings.protocolLanguage` string (default `"German"`) is substituted into the prompt as `{LANGUAGE}`. `{MEETING_DATE}` (`YYYY-MM-DD`) and `{MEETING_TIME}` (`HH:mm`) resolve from a captured recording start time, or to `Unknown` for imports and recovery jobs. Only a captured recording start adds the authoritative meeting-metadata preamble, so processing time is never presented as a meeting time. The preamble names the weekday beside the date (English, like the rest of the preamble), because local models that do not reason first resolved "next Friday" to the wrong day from the date alone; `{MEETING_DATE}` stays the bare date.
- `ProtocolGenerator.loadPrompt()` loads custom prompt from `AppPaths.customPromptFile` (`~/Library/Application Support/MeetingTranscriber/protocol_prompt.md`), falls back to built-in default.
- `OpenAIProtocolGenerator` supports any OpenAI-compatible HTTP API (Ollama, LM Studio, llama.cpp, etc.).
- **A CLI summary run gets the prompt and nothing else from the user's own agent setup.** The transcript reaches the model as input and holds whatever was said in the meeting, so with tools in reach a sentence that reads like an instruction could make the model act; the user's coding setup also costs input tokens on every summary (about 20 times the input, measured) and can steer the protocol. The Claude CLI always gets `--tools ""` and `--strict-mcp-config` (`ClaudeCLIProtocolGenerator+ToolRestriction.swift`); a CLI too old for them fails the protocol with a message asking for an update and gets no second run without them, since that run would hand the transcript to an unrestricted session. It gets `--setting-sources ""` only when its `--help` lists it (the rule `--no-session-persistence` follows; one content-free warning per run names it when left out, and a CLI that refuses a remembered option is asked again), and always `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` and `ENABLE_CLAUDEAI_MCP_SERVERS=false`: no tools, no MCP servers or claude.ai connectors, no hooks, plugins, permission mode or global instructions from the user's settings files, no telemetry (`ClaudeCLIProtocolGenerator+Isolation.swift`). `--bare` is not used: it never reads the CLI's own sign-in. Settings kept only in the user's settings file, a gateway URL in its `env` block for instance, no longer apply; the app's API key field and managed settings do. The Codex CLI preset keeps the model, reasoning effort and login from the user's Codex configuration and switches off connectors, plugins and the notify command (`--disable apps --disable plugins -c notify=[]`) and every configured MCP server by name, listed per run with `codex mcp list --json`: Codex merges `-c` tables, so an empty `mcp_servers` table clears nothing, and the override only takes effect after `exec`. A listing that fails leaves the servers on with a warning, and the listing itself sends sign-in discovery requests to the host of every server reached over HTTP, though the run then contacts none (`CommandProtocolGenerator+CodexIsolation.swift`). Codex's own and global instructions still load. The custom command runs exactly as written.
- **A provider failure does not fail the job.** `generateProtocol` catches it (in `protocolText`), adds the warning "Protocol generation failed — transcript saved", records the kind of failure as `PipelineJob.notesFailure` (`MeetingNotesFailure`) and the job still reaches `.done` with its transcript. The kind is decided in the catch, where the error case is known (a command provider's error maps to the closest kind; a local model's deadline is `.timedOut`, its other failures `.other`, while low memory and a missing model keep their own notice); the provider's own message reaches neither the job nor the log, which gets a content-free summary (`ProtocolError.logSummary`). The done notification then reads "Meeting Notes Failed" with the kind's fixed sentence, instead of "Transcript Saved", while `AppSettings.notifyOnMeetingNotesFailure` is on (the default). Only a Claude CLI error that asks to run `/login` adds the sign-in hint, so another provider's authentication error never sends the user to the CLI. Standard urgency: the failure is over when it is announced, and a batch import with a signed-out CLI posts one per job. `PipelineQueue.doneNotification` holds the choice of text.
- **Failed notes can be retried from the transcript, never by a full run.** A `.done` job with `notesFailure` and a `transcriptPath` (`hasRetryableMeetingNotes`) is held like a pending Notion export (`isHeldAfterCompletion`): no 60-second cleanup, kept by the snapshot restore and the queue adoption, kept even when its audio is gone, and `restorePendingNotionExports` builds the first queue for it at launch. Being held, it lets its audio sidecars go when it finishes, as an export does: the retry reads the transcript. The menu offers **Retry Meeting Notes** per job and **Retry All Meeting Notes (N)** from two such jobs; `/v1` offers the same (see `docs/automation-api.md`). `retryMeetingNotes` (`PipelineQueue+MeetingNotes`) sets `PipelineJob.generatesNotesOnly` and puts the job back to `.waiting`; `runPipeline` sends such a job to `generateNotesOnly` ahead of the protocol-only resume and the engine guard. The marker is on the job, not in the queue's memory, so a retry still waiting at a quit is a notes retry after the relaunch too (once the queue is built, as above), and the restore does not drop it for missing audio. A notes-only run claims no audio in `InFlightRunRegistry`, since it never reads it, so another run of the same recording does not refuse it. The failure stays on the job until notes are saved (`updateJobState` clears it on `.done` with a saved protocol, with the warnings that described the job without notes), so a retry that fails again, or meets a provider switched to None while it waited, stays on offer; with the provider None the retry is refused, and a provider switched to None while it waited records `.noProvider`. That is `generateProtocol`'s own answer (`ProtocolGenerationOutcome`), not the factory asked a second time after it returned: a provider switched off while the model writes leaves the reason that call recorded, and a job whose notes appeared meanwhile gets no failure. A transcript that cannot be read when the job runs records `.transcriptUnreadable`, so the notification names the reason of this run. A notes-only run that saved nothing is announced as "Meeting Notes Not Saved", never "Transcript Saved"; the marker stays on the job for that until the notes are saved. For the same reason its "Meeting Notes Failed" notification ends after the kind's sentence: "The transcript is saved" follows only for a run that saved one, so not for a notes-only run and not for `.transcriptUnreadable`. The retry passes the speaker names the failed attempt had (`notesSpeakerNames`) to the Notion export. Notes already next to the transcript, under the job's stem or the transcript's name, are never replaced: checked on the click, when the job runs and again after the model call, each ends the offer with a warning; after the call it says that the notes were generated and not written. A transcript that cannot be read leaves the offer in place with a warning. Nothing retries by itself.
- **A re-run runs a finished meeting again under its own id and swaps its files in only at success.** `PipelineQueue.rerunJob` (`PipelineQueue+Rerun`) rebuilds the job from the finished entry and the meeting's record, and both the job and the record carry a `MeetingFileRecord.RerunMarker` (stamp, outcome before, build, process, run id, the re-run's own files). The re-run writes under `<stem>.rerun-<stamp>`, never the meeting's current names, and is saved in a file of this build's own beside `pipeline_queue.json`, which keeps the finished entry it took over. Every end but success (`PipelineQueue+RerunEnd`) marks the marker as ending, moves back any rename of the swap, removes the re-run's files and restores the outcome in one record update. Success (`PipelineQueue+RerunSwap`) starts only once the job's done state is in the re-run file, since after the commit point only that file says what is left to do (a write that fails again on the flush's retry ends the re-run as R6 before any rename), waits while a Regenerate Notes runs, removes the re-run's naming data and 16 kHz copies, then writes its list of renames into the marker, renames the current transcript, notes and segments file to `<name>.until-<yyyyMMdd_HHmmss>.<ext>` (`EarlierVersionName`: `-2`, `-3`, … for a taken name, case folded, none past 99) and the re-run's files to the current names (a segments file without a current one goes to the folder the speaker naming reads it from), each only while it is the file the record names and with `renamex_np(RENAME_EXCL)`, so a name taken meanwhile is never overwritten and ends the re-run. A role without a current file takes its name by the current transcript's stem, or the notes' when the transcript is gone, so a meeting renamed to its AI title keeps it; additional reports are not touched. One record update is the commit point: the new files listed with their identity read after the rename, the earlier versions appended as owned `previousProtocol` (Move Meeting to Trash takes them), the marker gone, the stamp noted as committed. Then the earlier segments file is deleted, since only the current transcript is offered for Identify Speakers Again (until then an undo can put it back), the raw-transcript setting stamped at admission is applied as at a new meeting's `.done` (only when the re-run saved notes), the finished-job entry is written (moved last, so Last Recording shows the meeting), and only once that write landed does the job turn into an ordinary finished job (`exportsToPageDatabase`), leave the re-run file and start its Notion export, which with its retries goes to the database of the meeting's page (`notionExportResolution(for:)`). A held entry that waited for a notes retry stays held only when the re-run made no notes. At launch, `resumeRerunSwaps` takes a re-run job restored done: a stamp noted as committed finishes after the commit point (an export queued before the quit starts once from the saved notes), a marker with a list of renames is completed when every file it names is at one of its two ends and undone otherwise, and a marker without one starts the swap; a marker of this build whose job is not in the file is undone and ended as R6 (`reconcileOrphanedReruns`).
- **Notes for a transcript the user picks run the notes step only.** *Generate Meeting Notes from Transcript…* (and `POST /v1/jobs/notes/generate`) goes through `PipelineController.generateNotes(fromTranscripts:)`, which refuses while the provider is None and, for the menu only, names skipped files in a notification (`/v1` gets them in its response), to `PipelineQueue.enqueueNotes(fromTranscripts:)`: one job per `.txt`, with `generatesNotesOnly`, `transcriptPath` set to the file, `notesBasename` to its name and `meetingStartTime` from a leading `yyyyMMdd_HHmm`. `runPipeline` sends such a job to `generateNotesOnly`, the same as a notes retry, so it never transcribes, also after a relaunch. The notes are saved as `<notesBasename>.md` beside the file; `namingSlug` stays nil, because it names the speaker-naming sidecars and removing a job deletes by it, and a picked transcript can share its name with a meeting still waiting for names. Nothing is read on the main actor at enqueue: a file is taken by its extension and its size (above zero, at most `maxTranscriptBytes`, a guard rather than a measured bound; the size of the file a symbolic link points at, which is what the read reads), and read off the main actor when its job runs. A transcript given twice, or already waiting in a notes-only job, is queued once. The file is the user's, not a run's output, so the job keeps the raw transcript and never renames by the AI title whatever the settings say. A transcript that has notes is skipped at enqueue, and notes that appear while the job waits or while the model runs are never replaced. A job that ends without notes says why on the job and in its notification ("Meeting Notes Not Saved" or "Meeting Notes Failed", never "Transcript Saved"), and one that ended for a missing provider or an unreadable transcript can be retried like failed notes. Not in the App Store build: the menu item is compiled out, and `/v1` is not there either, since the sandbox grants the picked file only and not the folder the notes would go to. The panel enables `.txt` files only (`TranscriptPanelDelegate`): `.plainText` alone would also admit Markdown.
- **Transcript output options** (Settings → Output): `AppSettings.includeFullTranscriptInProtocol` (append the verbatim transcript to the generated Markdown) and `AppSettings.saveRawTranscriptSeparately` (keep the standalone `.txt`) both default to `true` for backward compatibility, and are captured per job at enqueue time so a settings change mid-queue doesn't retroactively affect jobs already running. The raw transcript is retained regardless of the setting whenever protocol generation is disabled, fails, or the job ends in an error — losing the only transcription is worse than an unwanted file. `AppSettings.useAITitleForFilenames` (default `false`, captured per job the same way) renames a job's artifacts to a snake_case slug of the title in the generated protocol's heading, without the timestamp, once a protocol exists (`ArtifactRenamePlan` plans it, `PipelineQueue.renameJobArtifacts` runs it). Every artifact is named from the closed suffix lists, never found by a directory prefix scan, a stem is only taken when none of its artifacts exist in `protocols/` or `recordings/` (else `_<shortID>` is appended), nothing is ever overwritten, and a failed move is undone so the job keeps its old stem. The meeting's additional reports `<stem> (<name>).md` move with it, found by the ownership rule rather than a prefix (`AdditionalReport`), and a stem counts as taken when it has a report or another meeting would own a moved one. A bracketed or placeholder heading, or one with no alphanumerics, keeps the timestamped name, and so does a job that ran a custom protocol template, whose first heading need not be a title (`ProtocolGenerator.fileTitleSlug`).

**Record-only mode:**
- When `AppSettings.recordOnly` is true, `WatchLoop.enqueueRecording()` moves the dual-source WAVs into `<settings.effectiveOutputDir>/recordings/` and writes a `<basename>_meta.json` `RecordingSidecar` next to them, skipping the entire post-processing pipeline (VAD, transcription, diarization, protocol generation). Both call sites — auto-detected meetings (`handleMeeting`) and manual recordings (`stopManualRecording`) — flow through the same branch, and the staging recovery is a third path into it (below). The destination is wrapped in `startAccessingSecurityScopedResource()` to honour user-picked Output Folder bookmarks (relevant for the App Store sandboxed build).
- **Mic mute times:** `MicMuteTimeline` holds them in seconds of the mic track, `MicMuteLog` saves them at each toggle for crash recovery (the orphan scan attaches it to a recovered job and deletes it for any finished stem it skips), and `PipelineJob.micMuteIntervals` carries them. The recorder, a reimport and orphan recovery each attach them only to a job with a mic track, since without one the mix is transcribed and it holds the far end (a lone `_mix.wav` is a paired group too). A reimport of `_mix.wav` and `_mic.wav` without the `_app.wav` the sidecar names gets none either, for the same reason (`RecordingSidecar.micMuteIntervals(app:mic:)`). `PipelineJob.init` clips, orders and merges them (`sanitized`), since a sidecar on disk can hold anything. A meeting-end cut clips them where it cuts the mic track (`RecordingCut.micMuteIntervals`; a failed cut keeps them as recorded), and orphan recovery ends them with the mic track, which a recovered cut shortened after the log was written: a mute begun after the cut point would otherwise mark the transcript past its end and count toward a microphone muted throughout. Mic text more than `TimestampedSegment.maxMutedShare` inside a mute is dropped because the engines are not trusted on long zeroes, and each mute renders as `[Mic muted 12:03–12:15]`. A dual-source recording muted throughout resolves to `DualTrackViability.appOnlyMicMuted`, which skips mic transcription and diarization; a microphone-only one fails with `micMutedThroughout`.
- Sidecar JSON contains: `version` (currently `RecordingSidecar.currentVersion = 3`), `title`, `appName`, `startedAt`/`stoppedAt` (ISO 8601, reconstructed from `recordingStart` uptime), `participants`, `micDelaySeconds`, `micMuteIntervals`, `trigger`, `files` (basenames only), and in this fork `pauses`. Optional `app` / `mic` filenames are omitted when nil, and so is `pauses` for a recording without a pause. Both sides took version 3 for their field (`micMuteIntervals` the original, `pauses` the fork); both decode as optional.
Suffix constants live as static lets: the audio-file suffixes on `RecordingFileSuffix` (`mix = "_mix.wav"`, `app`, `mic`, and the raw-temp `appRaw`/`legacyAppRaw`), and the sidecar suffix on `RecordingSidecar.filenameSuffix = "_meta.json"`.
- `trigger` (`auto` | `manual`, added in version 2) says which call site produced the recording, so a fleet consumer can discard a very short *auto* capture as a false trigger while always processing an equally short *manual* one — duration alone cannot tell those apart. A browser meeting is `auto`: the detector initiates it and the consent prompt only gates it. Every field added after version 1 must decode as optional, because `RecordingSidecar.read` is a `try?` and one unrecognised value would otherwise discard the *entire* sidecar on the reimport path.
- Intended for fleet topologies where macOS clients capture and a separate machine (e.g. Linux GPU host) processes the audio via Syncthing or similar.
- **Recovery files too (issue #77).** A recording no job tracks that a staged recovery pass finds (the app died during it, a live record-only write failed, or a quit's budget ran out during the write) is filed the same way when `recordOnly` is on at the moment the pass hands its recordings on: the setting then decides, not the one at recording time, which nothing stores. `PipelineController.recoverOrphans` runs the orphan scan unchanged and then, in record-only mode, `PipelineQueue.fileOrphanedRecordings` (`RecordOnlyRecovery.swift`) in place of the adoption. Right before each write it asks again, on the main actor: the mix is still in staging, no job, run or ledger entry accounts for it, the queue is not retired, and no quit has begun (`WatchingController.isQuitting`, handed over as `PipelineController.quitHasBegun`), since a quit writes the recording it stopped off the main actor and keeps its staging files until its sidecar commits. A recording that fails any of these is skipped silently and stays where it is. The processed ledger names only recordings the pipeline finished or the user dismissed, and nothing seeds it from the staging folder: a record-only install never finishes a job, so a ledger seeded from staging would hide its crashed recordings from every pass. The write is `RecordOnlyWrite`, off the main actor, into the folder the watch loops use. The sidecar: title `Recovered Recording (<stem>)` (the processing path's title), `appName` `Unknown`, `startedAt` read from the stem in the current time zone (a stem that is no recorder time takes the files' earliest creation date), `stoppedAt` its start plus the length of the mix as written (after a stored meeting-end cut), no participants, `micDelaySeconds` 0, the mute times its mute log kept (`micMuteIntervals`, read by the scan as for a recovered job; the log is removed once the write committed), and no `trigger` or `pauses` key. A failed write leaves the recording in staging, one notice per pass gives the count, and the next pass tries again; while record-only stays on it is never processed instead. A pass that files anything logs one line with the counts; no log line of a record-only write names a stem, title, path or participant. Jobs restored from the snapshot keep processing.
- Menu bar: the small red dot is rendered as a **persistent overlay** (`MenuBarIcon.image(..., recordOnlyOverlay:)`) on top of *whatever* primary badge `BadgeKind.compute(...)` would otherwise show — idle, recording, transcribing, etc. — so the mode is always visible. Permission overlay (red exclamation) takes precedence when both apply, since a permission problem actually breaks recording. Settings tabs dim Transcription / Protocol / VAD / Diarization sections via `View.recordOnlyDisabled(_:)` and show a banner in the General tab pointing at the active output dir.
- Sidecar write failures notify the user via `NotificationManager` (injected as `any AppNotifying` on `WatchLoop`) since record-only does not transition state to `.error`.

**Output folder fallback:** when the chosen output folder's bookmark stops resolving (unplugged drive, unmounted share, deleted folder), output goes to `~/Downloads/MeetingTranscriber` and the user is told once. `AppSettings.outputDirectoryResolution` says which happened (`.defaultLocation` / `.custom` / `.fallback`, the last one naming the chosen path read from the bookmark bytes); `effectiveOutputDir` is its URL and stays a pure read. `OutputDirectoryResolver` (owned by `PipelineController`, shared with `WatchingController`) is the only thing that notifies, and it is called only where a destination is captured: `PipelineController.makeQueue()` (by value, for every job the queue runs) and the record-only destination closure (per write). Once per episode, keyed on the bookmark; a folder that resolves again or a new choice re-arms it. Views and the poll must never call `resolve()`. `AppSettings.init(defaultOutputDir:)` exists so tests can point the fallback away from the real Downloads folder; a test that resolves to the production default is one step from writing into it.
