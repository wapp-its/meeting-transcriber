# Meeting summaries in All Recordings

## Conversation Evidence

The fork is public, so the owner's turns are paraphrased, not quoted.

> owner (paraphrased, 2026-11-16): in the All Recordings window, each recording should show a short summary of what the meeting was about, so the overview already tells which entry is which.
> owner (paraphrased, 2026-11-16): the summary comes from the generated meeting notes or the transcript, and the owner can edit it.

## Goal & Context

<!-- Source: 0% user / 35% [paraphrase] / 65% [inferred] -->

All Recordings lists each meeting with its title, app, date and length. Many titles are generic: the meeting app's name, an imported file's name, "New Recording 3" or "Recovered Recording (…)". To find out which row is which meeting, the user opens the notes one by one. [paraphrase]

After this spec, every finished meeting can carry a short summary of what it was about, shown under its title in All Recordings. The app takes it from the meeting notes when it saves them, so it costs no extra model call. The user can change it or write one for a meeting without notes, and new notes never replace a summary the user wrote. Meetings that already have notes get theirs from their notes file. The search finds words in summaries too. [paraphrase]

Who it is for: everyone who records or imports meetings with the app. Why now: the owner asked for it on 2026-11-16. It builds on the rows and the row menu that #171 (Transcribe Again, Identify Speakers Again) changes, and says what happens to the summary when a meeting is processed again. [inferred]

Upstream check (2026-11-16): the original project has no issue or pull request about a summary per recording or about editing one. Related only: its open issue 873 proposes a separate "Meetings" window that shows a meeting's notes and transcript side by side (no pull request yet); its open PR 990 adds named notes templates, which is why the summary rule below does not depend on the built-in template's headings; its open PR 979 passes the meeting title to the notes prompt and does not change the title the list shows. In the fork, #126 (the search finds no participants, since few meetings have any) and #201 (All Recordings must not wait on a volume that stops answering) bear on R5 and R6.

## Architecture & Data Models

- **The summary of a meeting** is one plain-text paragraph, at most 600 characters, with one of two origins: taken from the meeting's current notes, or typed by the user. A typed summary stays until the user changes or empties it; a summary taken from notes follows the meeting's current notes. [inferred]
- **Where it is kept:** its own file in the app's data folder, beside the finished-job list, keyed by the meeting's job id: per meeting the text, its origin and when it was written. Neither the meeting record (gh-97, `MeetingFileRecord`) nor the finished-job list (`TerminalJobRecord`) holds it: meetings from before the record have no record, and a build that does not know a field drops it when it rewrites either file, which would lose a typed summary (A8). The file is written atomically and readable only by the user, as the record file is, and two running builds of the fork take turns through a lock beside it, as they do for the record file. [inferred]
- **The rule that takes a summary from notes** is one pure function of the notes' text: the first paragraph of plain text after the first second-level heading (`## …`), whatever that heading says. In notes made from the built-in template that is the Summary section, in any notes language. It skips headings, lists, tables, block quotes, horizontal rules, HTML comments, paragraphs made only of label lines such as `**Date:** …`, and a paragraph wholly in square brackets (a model that copied the template's placeholder). It never reads past the separator before an appended full transcript. It removes Markdown marks (emphasis, inline code, link targets), joins the lines with single spaces and cuts the text to 600 characters at a word end, adding "…". No such paragraph means no summary. [inferred]
- **When it is taken:** wherever the app saves a meeting's current notes, from the text it saved, never by reading the file back: a new meeting's notes, Retry Meeting Notes, Generate Meeting Notes from Transcript…, Regenerate Notes… with "Replace the current notes" (gh-190), and the success step of Transcribe Again and Identify Speakers Again (#171). It replaces a summary taken from notes and never a typed one. An additional report (gh-190) and notes made by "Regenerate from File…" change no summary. [inferred]
- **The row** (`TranscriptionsView`) reads the summary from the store in memory, never from a file while it is drawn, and shows it directly under the title. The row's list entry carries it, so the search reads it too. [inferred]
- **"Edit Summary…"** is one more item of the pure row decision (`RecordingRowActions`), so the "…" menu and the right-click menu list it together. It opens a sheet over All Recordings, like the regenerate sheet; its layout is the accepted mockup (Mockup gate in Decision Context). The sheet's state lives in one `@Observable` object, so a ViewInspector test can read back what a control wrote (gui-testing doc, rung 2). [inferred]
- **Meetings from before this version:** when All Recordings opens, the app reads, off the main actor and one file at a time, the first 64 KB of the notes file of each finished row that has notes and no summary yet, and stores what the rule takes as "taken from notes". Each file is read at most once per launch. [inferred]

## API Contracts

- No new endpoint. The summary is not part of `JobStatusDTO`, `GET /v1/jobs/<id>` or any other `/v1` response, and All Recordings stays off the `/ui/tree` and `/ui/press` window allowlist, since it shows meeting content. [inferred]
- The summary file is new and only this fork reads it. The meeting record file and the finished-job list keep their formats unchanged, so a build without this spec reads them as before. [inferred]

## Edge Cases & Constraints

- **Notes in another language:** the rule keys on the position of the paragraph, not on the heading's words, so German notes ("## Zusammenfassung") work the same as English ones. [inferred]
- **Custom templates (gh-2, gh-207):** the first section's first plain paragraph is taken. Notes whose first section is a list or a table get no summary; the user can type one. [inferred]
- **No notes:** protocol provider None, failed notes, notes generation off for a re-run (#171 A12) and meetings whose notes were never saved leave the summary as it was; a row without one shows no summary line. Retry Meeting Notes that succeeds fills it. [inferred]
- **Notion export that replaces the local Markdown:** the summary is taken from the generated text before the local copy is removed. Such a meeting from before this version has no file to read, so it gets none until the user types one. [inferred]
- **Transcribe Again and Identify Speakers Again (#171):** while the re-run waits or runs, the row keeps showing the summary of the current notes, since those notes stay current until the re-run succeeds. At success the new notes' summary replaces one taken from notes; a typed one stays. A re-run that fails, is cancelled or stays unnamed leaves the summary as it was. Earlier versions (`.until-<stamp>`) and `.previous-<stamp>` copies get no summary of their own. [inferred]
- **Notes edited outside the app** do not change the summary. "Use Summary from Notes" in the sheet reads the current file again. [inferred]
- **Unreachable files:** a notes file that is gone, unreadable, on a volume that is not connected or does not answer, or outside the folder the App Store build may read, stores nothing; the window never waits for such a read (#201). [inferred]
- **Record-only mode:** recordings made in it have no row, so nothing changes for them; rows from before stay editable. [inferred]
- **Privacy:** a summary is meeting content. It never appears in a log line, a notification, the automation API or a test fixture; tests use made-up text. [inferred]
- **Wording:** on screen the app says "notes" (gh-97 A11) and "summary". [inferred]

## Acceptance Criteria

- **R1:** The app keeps each meeting's summary, with its origin (taken from notes or typed), in its own file keyed by the job id, written atomically and readable only by the user, and loads it at launch. Errors: a file that cannot be read or decoded is moved aside under an `.unreadable` name before anything new is written, and the app starts with no summaries; a failed write is logged without content and never fails a job or an action; while the other running build holds the lock longer than the wait bound, the write fails and is logged, as for the record file. [inferred]
- **R2:** Each time the app saves a meeting's current notes (a new meeting, Retry Meeting Notes, Generate Meeting Notes from Transcript…, Regenerate Notes… with "Replace the current notes", the success step of Transcribe Again and Identify Speakers Again), it takes the summary from the saved text by the rule in Architecture and stores it as taken from notes, unless the meeting has a typed summary, which stays unchanged. Errors: notes with no such paragraph remove a summary taken from earlier notes and keep a typed one; an additional report, "Regenerate from File…", failed notes and a re-run that fails, is cancelled or stays unnamed change no summary; with the Notion export replacing the local Markdown the summary is still taken. [paraphrase]
- **R3:** A finished meeting with a summary shows it directly under its title in All Recordings, in at most two lines cut with "…", and the whole summary appears as the row's tooltip. Errors: a row without a summary looks as today; a meeting that is being transcribed again keeps showing its summary until the re-run succeeds; drawing a row reads no file. [paraphrase]
- **R4:** Every finished row offers "Edit Summary…" in its "…" menu and its right-click menu, directly after "Show in Finder", also when it has no notes or no record. It opens the Edit Summary sheet of the accepted mockup: the meeting's title, date and length, a text field with the summary, a line saying whether the summary was taken from the notes or typed and that new notes do not replace a typed one, "Use Summary from Notes", Cancel and Save. Save stores the trimmed text as typed, and the row shows it at once; Cancel changes nothing. Errors: saving an empty text removes the summary, so the next notes fill it again; Save is disabled above 600 characters, with a line saying the limit; "Use Summary from Notes" is disabled for a row without a notes file, reads the current notes off the main actor and puts their summary into the field (saved unchanged, it is stored as taken from notes); a notes file that is gone or holds no summary paragraph leaves the field as it was and the sheet says which; not offered for a waiting, running, naming or failed row, nor in the menu of a multi-row selection. [paraphrase]
- **R5:** When All Recordings opens, each finished row that has a notes file and no summary gets one from the first 64 KB of that file, read off the main actor, at most once per row and launch, stored as taken from notes. Errors: a file that is gone, unreadable, out of reach or without a summary paragraph stores nothing and the row stays without one; the window stays responsive while a read waits on a volume; a summary typed while the read ran is never replaced. [inferred]
- **R6:** The All Recordings search matches the summary as well as the title and the participants, ignoring case and diacritics, and its hint reads "Search titles and summaries". No error surface beyond today's search. [inferred]
- **R7:** Move Meeting to Trash removes the meeting's summary once its files are moved; a deletion left incomplete keeps it until it finishes; Move Audio to Trash and the automatic deletion leave it. At launch, a summary whose job neither the finished-job list nor the record file holds is dropped. Errors: a failed removal is logged without content and retried at the next launch by the same rule. [inferred]
- **R8:** The summary rule, the replace-or-keep rule for every save point of R2 and the menu item list for every job state are pure functions with unit tests: notes from the built-in template in English and in German, a custom template that starts with a list, an appended full transcript, label lines, a bracketed placeholder, Markdown marks and the 600-character cut. The store is tested with a temporary folder: an unreadable file, two writers, a write failure. The re-run's success step is tested in the pipeline's test setup with a stub generator, with a taken and with a typed summary. Each new control has one ViewInspector wiring test located by an `A11yID` constant. Both build variants run the suite, and `docs/architecture/pipeline.md` describes the summary, its file and its rule. No error surface beyond R1 to R7. [inferred]
