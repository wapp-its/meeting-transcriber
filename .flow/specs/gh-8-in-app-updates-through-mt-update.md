## Goal & Context

The fork's build of Meeting Transcriber is built and installed by `mt-update`, a script on the fork's `tools` branch: it merges the original's newest `main` with the fork's branches, builds the app and replaces `/Applications/MeetingTranscriber-Dev.app`. The app's own update check asks the original's GitHub releases, which lack the fork's extensions and install as a second app, so the owner switched that check off and updates by typing `mt-update` in a terminal. The goal is that the app itself says when a newer build is available, installs it with one click through mt-update, and reports the outcome as a macOS notification. [paraphrase]

Today's code, read on 2026-10-06: `UpdateChecker` compares the semantic version of the original's latest GitHub release (`GitHubReleaseProvider`, hard-coded to `pasrom/meeting-transcriber`) with the running version, checks 30 s after launch and then every 24 h while the "Check for Updates" switch is on, and the menu and About open the release's DMG. Nothing in the code disables the check; "off" is the owner's switch (`AppSettings.checkForUpdates`, default on). [inferred]

Today's mt-update (read from `origin/tools:mt-update.sh` on 2026-10-06): `--check` prints German human-readable lines, ignores any further argument and always exits 0. Install mode (no argument) exits 2 on a merge conflict, 3 on a failed build and 4 when the app stays busy past its wait (3 h) or cannot be quit; it waits until nothing records or processes, quits the app with a normal AppleScript quit, replaces the bundle, writes its stamp and reopens the app. It updates itself from the `tools` branch on every run, provided it finds itself on `PATH`. [inferred]

This spec covers the app side. The porcelain check is a separate change to mt-update on the `tools` branch; the contract the app relies on is fixed below. Installing needs no change to mt-update: the app reads the outcome from mt-update's existing exit codes while it still runs, and from the build it finds itself running as after the restart. [inferred]

## Architecture & Data Models

- **Update source, chosen once at launch.** mt-update mode when all three hold: the Homebrew variant (`#if !APPSTORE`), an executable file at `~/.local/bin/mt-update`, and the running bundle is `/Applications/MeetingTranscriber-Dev.app`, the one app mt-update replaces. Anything else keeps today's GitHub check unchanged. A pure function takes these three facts as inputs. [inferred]
- **A separate seam, not a third method on `UpdateProviding`.** `UpdateProviding` and `GitHubReleaseProvider` stay as they are. Their shape (`latestRelease`/`allReleases`, compared by semantic version) does not fit a source that compares build states, so `UpdateChecker` gains an optional mt-update installer next to its provider and branches on it. [inferred]
- **Check.** Run `~/.local/bin/mt-update --check --porcelain` as a child process with a 5-minute limit. At the limit the app signals mt-update's whole process group (SIGTERM, then SIGKILL one second later) and treats the check as still running until every process in that group has ended, because a `git` that mt-update started works on the same checkout an install uses. Its stdout and stderr go to `~/Library/Logs/MeetingTranscriber/mt-update-check.log`, truncated at each check. After it exits, a pure parser turns the exit status and that file's text into one of: up to date, update available with a summary, or check failed with a reason. [inferred]
- **Install.** Launch `~/.local/bin/mt-update` with no argument (today's install mode). Its stdin is `/dev/null`, its working directory is the home folder, and its stdout and stderr go to the file `~/Library/Logs/MeetingTranscriber/mt-update.log`, truncated at each install. They never go to a pipe: the child keeps writing after this app has quit, and a write to a pipe with no reader kills it with SIGPIPE, possibly between deleting the old bundle and moving the new one in. Right after a successful launch the app stores a **pending-install record** in its own UserDefaults (key `mtUpdatePendingInstall`): start time, the child's process ID and process start time, the running build's identity, the summary being installed, and whether meeting watching was on. [inferred]
- **How the app learns the outcome.** While the app still runs, from the child's exit status in its termination handler: 2 merge conflict, 3 build failed, 4 busy too long or could not be quit, 0 finished without restarting this app, anything else (including a signal) failed. At the next launch, from the pending record against the build now running: a different build identity means installed; the same identity while the recorded process still runs means the install is still going (the app shows it as running and looks again every 30 s); the same identity with that process gone means the install did not finish. Build identity is `GitCommitHash` from `Info.plist` plus the main executable's modification date; every mt-update build sets both anew. A process counts as running only when its ID is alive and its start time matches the recorded one, so a reused process ID never reads as mt-update. [inferred]
- **Child environment** (check and install alike). The app's environment minus every variable whose name starts with `MT_`, so the app always gets mt-update's defaults, including reopening the app after the install. `PATH` gets `~/.local/bin:/opt/homebrew/bin:/usr/local/bin` in front, because a launched app inherits a minimal `PATH` and mt-update's self-update looks itself up there. `GIT_TERMINAL_PROMPT=0` is set, so a git credential prompt fails at once instead of hanging a child that has no terminal. The Claude CLI launch builds its environment the same way. [inferred]
- **State on `UpdateChecker`.** The summary of an available build (mt-update mode), whether an install is running, and the last install failure. `hasAvailableUpdate` (a GitHub release or an mt-update build) feeds the menu-bar update badge and `/state.updateStatus` in both modes. [inferred]
- **Install gate.** A pure function says why an install is not possible right now: a recording runs or a manual recording is starting (the wide manual-recording predicate included), or a job is waiting or being processed. This mirrors what mt-update itself waits for. [inferred]
- **Notifications** go through the app's notifier (`AppNotifying.notify`, `.standard` urgency), with the texts built by a pure type in the manner of `PreviousExitNotice`. [inferred]

### The mt-update contract (the tools side builds it separately)

| Call | What the app relies on |
|---|---|
| `mt-update --check --porcelain` | No build, no install, never quits the app, never prompts. |
| stdout | Lines `key=value` (the value is the rest of the line). Lines in any other form and unknown keys are ignored, so self-update and hint lines may stay. Required: `format=mt-update-porcelain/1` and `status=up-to-date` or `status=update-available`. With `update-available`: `summary=<one line of at most 80 characters saying what is new>`, e.g. `upstream 1a2b3c4 · wapp/main 5d6e7f8`. |
| exit code | 0 up to date, 10 update available, anything else check failed. |
| acceptance rule (app) | A check counts only when the format line is present and the status agrees with the exit code. Everything else is a failed check, so today's `--check` (exit 0, human text) never reads as up to date or as an update. A missing summary shows as `new build`; a longer one is cut to 80 characters. |
| `mt-update` (install) | Unchanged: exit 2 merge conflict, 3 build failed, 4 busy too long or could not be quit, any other non-zero failed; on success a normal quit of the app, replacement of the bundle, and reopening it. No result file is needed. |
| log files | Chosen and opened by the app, which owns the child's stdout and stderr; mt-update needs no log option. |

## Edge Cases & Constraints

- mt-update installed after launch: picked up at the next launch. Removed after launch: the check fails with "mt-update was not found" and Install reports that it could not start; no switch to the GitHub check mid-run. [inferred]
- Offline, or GitHub's rate limit reached inside mt-update: it exits non-zero, which is a failed check. An update found by an earlier check stays shown, as today. [inferred]
- A check while an install runs, and an install while a check runs, are refused: both work on mt-update's git checkout. [inferred]
- A recording starts after Install was pressed: mt-update itself waits until the app is idle (up to 3 h), then quits it; if it gives up, exit 4 is reported as in R6. [paraphrase]
- Open speaker namings do not block an install, as in mt-update; they reappear after the restart, and names typed but not confirmed are lost, as with any restart. [inferred]
- The person quits the app while mt-update builds: mt-update installs and reopens it, and the new instance reports "installed" (R5). [inferred]
- The app is reopened by hand while mt-update still runs: R7's "still running" path; when mt-update finishes it quits and replaces this instance too. [inferred]
- mt-update fails after it quit the app (copying or replacing the bundle): nothing reopens the app; the next manual launch of the old build reports "did not finish" (R7). [inferred]
- Notifications denied or hidden: nothing replaces the banner; About keeps a live failure on screen until the next check or install. [inferred]
- A pending-install record is read only in mt-update mode; a build that starts without mt-update leaves it alone, and the next mt-update-mode launch evaluates it. [inferred]
- A check stopped at its 5-minute limit releases the check guard only once mt-update and everything it started have ended, so no install or second check meets a leftover `git` on mt-update's checkout, and no leftover process writes into the next check's log. Measured on 2026-10-06: a child started through Foundation's `Process` leads its own process group, and signalling that group also ends a grandchild running in the background. [inferred]
- Once started, an install cannot be cancelled from the app. [inferred]
- Privacy: the two log files hold mt-update's and the compiler's output (branch names, commit hashes, file paths); notifications hold the build summary and the log path. Neither holds a meeting title, a participant or transcript text. [inferred]
- App Store variant: everything that starts a process is `#if !APPSTORE`; the pure types compile in both variants. [paraphrase]
- The menu-bar and Settings bodies read new state through single-member `AppState` accessors, because inline chains have pushed these bodies over the 300 ms type-check limit before (pattern `AppState.hasPermissionProblem`). [inferred]
- Neither Install control is ever added to the `/ui/press` allowlist: pressing it ends the app. [inferred]

## Acceptance Criteria

- **R1:** A Homebrew build running as `/Applications/MeetingTranscriber-Dev.app` with an executable `~/.local/bin/mt-update` takes its update checks and installs from mt-update; every other build (no mt-update, a development build run from another folder, the Homebrew release) behaves exactly as today with the GitHub check, and the App Store build contains no code that starts mt-update. Errors: a path that cannot be read counts as absent, which means today's behaviour. [paraphrase]
- **R2:** In mt-update mode the periodic check (while "Check for Updates" is on: 30 s after launch, then every 24 h) and "Check Now" run `mt-update --check --porcelain`; an accepted "update available" shows "Update available: <summary>" in About, an install item in the menu and the menu-bar update badge, and an accepted "up to date" shows "Up to date" in About. Errors: any other exit code, a missing or contradicting status, no answer within 5 minutes, or mt-update not startable show a failed-check message in About and never an available update; an update found earlier stays shown. [paraphrase]
- **R3:** An mt-update that predates the contract (today's `--check`: human text, exit 0) is never reported as up to date or as an update; About says that this mt-update cannot report updates to the app yet, and no install is offered. Errors: none beyond R2's failed-check message. [inferred]
- **R4:** In mt-update mode with an update available, "Install Update" in About and in the menu starts mt-update in the background with its output in `~/Library/Logs/MeetingTranscriber/mt-update.log`; both places then show that an install is running and offer no second install and no check. Both controls are disabled, About naming the reason, while a recording runs or is starting, while any job is waiting or being processed, and while a check runs. Errors: mt-update cannot be started → a notification and an About message naming the cause, and nothing else changes. [paraphrase]
- **R5:** When mt-update has replaced and reopened the app, the new instance posts one "Update installed" notification naming the installed build's summary, and turns meeting watching back on if it was on when the install started. Errors: with notifications switched off no banner appears and nothing else changes; the record is cleared either way, so the message never repeats. [paraphrase]
- **R6:** When mt-update ends while the app still runs (merge conflict, build failure, app busy too long or not quittable, any other failure), the app posts one notification that names the cause and the log path and says the installed app is unchanged, shows the same in About, and offers "Install Update" again. Errors: an exit status the app does not know is reported as a failure with its number. [paraphrase]
- **R7:** When the app starts with an install on record and is still the same build: while mt-update still runs, it shows the install as running and looks again every 30 s; once mt-update has gone without a new build, it posts one "Update did not finish" notification with the log path, clears the record, and returns to the idle state, so checks and "Install Update" are available again. Errors: a recorded process ID whose start time no longer matches counts as gone. [inferred]

### practice-scout
- **Gotcha:** a child that outlives the app must not write to a pipe: once the reading app is gone, the next write raises SIGPIPE and ends the child. Source: the install flow in `origin/tools:mt-update.sh` (quit, then copy, delete, move, reopen)
- **Gotcha:** a launched app inherits a minimal `PATH`, so tools under `~/.local/bin` or Homebrew are not found without a prefix. Source: `app/MeetingTranscriber/Sources/ClaudeCLIProtocolGenerator.swift` (`buildEnvironment`)
- **Gotcha:** `sysctl(KERN_PROC_PID)` on a process ID that does not exist returns success with a size of 0, so liveness must check the returned size before reading the start time. Source: `app/MeetingTranscriber/Sources/DualSourceRecorder.swift` (`launchedAt`)
- **Gotcha:** a bounded child run needs SIGTERM, a short grace, then SIGKILL; for mt-update the signals go to its process group (the child leads its own group, measured with a throwaway Swift probe on 2026-10-06), and the run ends only when that group is empty. Source: `app/MeetingTranscriber/Sources/ClaudeCLIProtocolGenerator+SessionPersistence.swift` (`runBounded`)
- **Gotcha:** the development build is signed without the hardened runtime, so mt-update's AppleScript quit needs no Apple Events entitlement; whether macOS asks for Automation consent when the request comes from the app's own child is unverified and left to the owner's install check. Source: `scripts/lib/signing.sh`, `scripts/run_app.sh`
