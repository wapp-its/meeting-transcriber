## Goal & Context

<!-- Source: 55% [paraphrase] / 30% owner-selected / 15% -->

Every recorded meeting leaves three WAV files of several hundred megabytes in the output folder's recordings subfolder, and nothing ever removes them. The All Recordings window lists the meetings but says nothing about their audio, and the only way to delete a sensitive meeting is to find its files in Finder. Audio is also the most sensitive part of a meeting. Often only the protocol and the transcript are needed afterwards. [paraphrase]

This spec gives each meeting a record of its files, and with it two ways to delete them. By hand, from the All Recordings window: move one meeting's audio to the Trash, or the whole meeting, also for several selected meetings at once. Automatically: a setting deletes the audio of finished meetings after a chosen number of days, never touching imported files, failed meetings or meetings marked Keep. Each row says what happens to its audio and when, and the setting shows what it will delete before a shorter time takes effect. [paraphrase]

Who it is for: everyone who records meetings with the app, and first the owner, whose recordings folder grows with every meeting. Why now: the owner asked for a lifecycle for recordings and picked this first slice from a proposal on 2026-10-21. [paraphrase]

Upstream check (2026-10-21): the original project has an open feature request for a configurable retention of audio recordings and no pull request for it. Its maintainer announced the rules there: one threshold in days, counted from the recording date, off by default; only audio the app recorded itself; nothing deleted unless a protocol was written; a failed run keeps its audio; audio waiting for speaker naming stays; recordings made before the feature ships are not swept. This spec follows the same rules so the fork can switch to the original's version if it lands first (#188).

## Architecture & Data Models

<!-- Source: 40% owner-selected / 25% [paraphrase] / 35% -->

- **Meeting file record.** One durable record per meeting, keyed by the job's id, created when the meeting enters processing (a recording handed over by the watch loop or a manual stop, an orphan recovered after a crash, an imported file). It lists every file the meeting has: the recorded audio tracks, the 16 kHz copies, the transcript segments and the speaker naming file while they exist, the transcript and the protocol. Each file carries whether the app owns it (an imported source never is), and the record carries the recording date, the Keep mark and the deletion state (when audio was moved to the Trash or deleted automatically, and which files a deletion could not remove). The record follows each file as it is written, moved, replaced (Regenerate Protocol) or removed by the pipeline. It is separate from the finished-job list, which keeps at most 1000 entries: a record lives as long as any of its files exists. [paraphrase]
- **Paths and ownership.** The record stores each file's full path, with symbolic links resolved when it is recorded, and the file's identity on disk (volume and file number) taken when the file is recorded. A deletion only ever touches a path its record lists and no other record lists: a path another record also lists is blocked, stays listed, and is reported until the other reference is gone. Ownership comes from how the meeting started (a recording the app made, or an import), set once when the record is created, never from where a file sits: an imported file the user placed inside the recordings subfolder stays not owned.
- **Same file, right before removal.** Just before each file is moved or deleted, it must still be a regular file (not a folder, not a symbolic link) in the recorded folder, with the recorded identity; anything else is a failure for that file, never a removal. The record follows every rewrite the app itself makes of a listed file (a transcript rewritten when speakers are named, the naming file on each save, a regenerated protocol), so the app's own files always pass this check. Deleting for good removes one file and never a folder's contents. The remaining window between this check and the removal is accepted: changing files there needs write access to the user's own folder, which already allows deleting them.
- **Recording date.** The recording start; for a meeting without one (a recording recovered after a crash), the time it entered processing, which is later, so its audio is kept longer, never shorter. It is written once when the record is created and never changed, also not by a Retry. Imports have no recording date and are never deleted automatically.
- **Recordings from before this feature.** The record file notes when it was first created. A recording recovered after a crash whose audio file was created before that moment is a recording from before this feature: it gets a record and the manual actions, but is never deleted automatically (D9).
- **Meeting outcome.** The record knows whether the meeting finished, failed, or left the queue without finishing (cancelled, dismissed, removed), and for a finished one whether protocol generation was on for it. A protocol that fails to generate or to save still finishes the job, with only a transcript and a warning, so "finished" alone does not mean a protocol exists. Speaker naming counts as resolved once the job is done (confirmed, skipped, or never needed). A Retry keeps the same record, and the meeting is judged by its new outcome; the queue's own removal of a finished job a minute after it finishes does not change its outcome. Only a finished meeting whose protocol was saved, or that had protocol generation off (A1), is ever deleted automatically.
- **Reachable versus gone.** A file counts as gone only when the folder it lives in can be read and the file system answers that the file does not exist. When that folder or its volume is missing (drive not connected, share unmounted), or the answer is a permission, access or input/output error, the file is unreachable: it stays listed as present and nothing about it changes.
- **One writer.** The record is changed in one place on the main actor, and every change holds an exclusive lock on a lock file beside the record file across reading it again, changing the one record and writing it, because a second running build of the app (the development and the release build share the data folder) changes the same file. The lock is never held while files are moved or deleted. A write reports whether it was saved.
- **Pending deletion.** Before touching any file, a deletion saves its kind (audio to the Trash, meeting to the Trash, or automatic) and the files it covers in the record, and starts only when that save succeeded; a file is marked as being deleted before it is moved or deleted and as gone afterwards; the pending deletion is cleared when the deletion finishes. At launch a pending deletion is checked against the disk: a manual one becomes "Deletion incomplete" with a retry of the same kind, an automatic one is cleared and the next check tries again. "Deletion incomplete" belongs to manual deletions only.
- **Pure decisions**, tested without views or files: (1) which audio files of a meeting the automatic check deletes now, given the record, the meeting's state, the setting and the current time; (2) the row's audio line and Keep badge; (3) which of the new menu items a row or a selection offers; (4) the texts of the confirmations and of the preview.
- **The check** runs the deletion decision over all records, also those whose row has left the finished-job list, and deletes what it returns, at launch, after a meeting finishes (including after its speakers are named), once a day while the app runs, and within a minute after a confirmed setting change. At most one check runs at a time; it reads the setting once per run and re-checks a meeting's state right before touching its files. The current time, the daily schedule and the time zone are injected, so tests control them. [paraphrase]
- **The Trash mover** moves a list of files to the Trash one by one and returns a result per file, so a partial failure is recorded per file and the retry moves only what is left.
- **The window** (All Recordings, built by the earlier menu spec) keeps its list source and its search; it gains the audio line per row, a footer, multi-row selection, three row-menu items and the confirmations. **Settings → Output** gains a "Recordings" section with one picker. [paraphrase]

## API Contracts

<!-- Source: 100% -->

- The automation API gains no endpoint and no field; deleting through it was dropped. After "Move Meeting to Trash", the meeting's finished-job readback (`GET /v1/jobs/<id>`) answers 404 as for an unknown id, because the meeting is gone; the API reference says so.
- `/ui/tree` and `/ui/press` keep their window allowlist: All Recordings shows meeting titles and stays off it.

## Edge Cases & Constraints

<!-- Source: 100% -->

- A file in an output folder that is not reachable (drive not connected, share unmounted, bookmark not resolving; see "Reachable versus gone") is never treated as deleted. The automatic check skips it and tries again at the next check; it never deletes anything from the fallback output folder in its place. A manual deletion reports it as "Deletion incomplete".
- A file the user already removed or moved away (its folder can be read) counts as gone, not as a failure. A file replaced by another file or a folder at the same path is not removed and is reported. A meeting none of whose audio files is still there shows "Audio not found" and is skipped by the check.
- Quitting or a crash during a deletion leaves the record consistent: every file is either still listed as present or marked as gone. An interrupted "Move Meeting to Trash" shows as "Deletion incomplete" after the restart.
- Deleting inside an output folder the user picked uses that folder's bookmark access, as writing there does (relevant for the App Store build). A meeting saved to an output folder the user has since replaced may be out of reach for the App Store build; it is reported like an unreachable file.
- With protocol generation off, a meeting counts as finished when its transcript is saved and its speakers are named (A1).
- Record-only mode: those recordings never enter processing, get no record and are never listed or deleted; the Recordings section stays enabled, since it still applies to meetings recorded earlier.
- The transcript segments file holds the spoken text and is written readable only by the user, like the transcript and the protocol already are. Segments files written before this version keep their permissions.
- A meeting that left the queue without finishing (cancelled, dismissed, removed) has no row and keeps its audio; #184 covers it.
- Retention is one app-wide setting, not part of a profile (gh-6).
