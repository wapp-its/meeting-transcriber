# Show a pending recording prompt on the menu bar icon

## Goal & Context

Every detected meeting now asks "Record <App> meeting?" through a notification before it records (spec gh-3), and the question stays open for five minutes. Whoever misses the banner (Focus, a second screen, notifications switched off) sees an icon that looks exactly like "watching, nothing going on", so a meeting goes unrecorded without anyone noticing. The icon should show that a question is waiting, and the menu should let the person answer it when the notification is gone or never appeared. [paraphrase]

What the code does today (checked 2026-10-06 on `wapp/main` 65888b53): the open question is `WatchLoop.pendingConsentApp`, set when the consent gate posts a prompt and cleared when the prompt is answered, expires, or is declined because watching stopped or a manual recording started. `NotificationManager.askToRecord` parks the prompt in `ConsentPromptCoordinator` and withdraws the notification from Notification Center however the prompt resolves. A notification tap answers its own prompt by id (`ConsentPromptCoordinator.resolve(id:answer:)`); the automation hook (`POST /action/confirmBrowserConsent`) answers through `AppNotifying.resolveBrowserConsent(granted:)`, which resolves whatever the coordinator has parked. The prompt registers in the coordinator off the main actor (`awaitDecision` is a nonisolated async method, and the package builds in Swift 6 mode without nonisolated-nonsending), so a prompt can still register after Stop Watching has cleared its question. The prompt is parked even when the user has switched notifications off (delivery is refused only without an app bundle or before set-up), so the menu is a real way to answer exactly when the banner is never seen. `BadgeKind.userAction` is not reachable in the running app, because `WatchLoop.transcriberState` only maps to idle, watching, recording and error. The watching indication of PR #51 is an overlay: a dot in the icon's own colour at the top right, drawn over every badge. [inferred]

## Architecture & Data Models

- **One input for "a question awaits your answer".** `AppState` gains a single Boolean that is true while the current watch loop has an open recording prompt. It drives the icon's question mark. Issue #58 can later feed its own pending question into the same input; nothing else is generalised now. [inferred]
- **The question mark is an icon overlay, not a new badge state.** `MenuBarIcon.image(…)` gains a `questionOverlay` flag (default false) next to `watchingOverlay`. While it is set, a question mark in the icon's own colour is drawn at the top right in place of the watching dot (a prompt only exists while watching, so nothing is lost); the waveform state, the red channel tints and the bottom-right badges (permission "!", record-only dot, update arrow) are drawn as before. It keeps the template path when no red overlay applies and gets a pre-rendered cache like the watching one. `BadgeKind`, `BadgeKind.compute` and the `badge` value in `/state`, `/v1/watch` and `/v1/record` do not change; automation clients already see the open question as `pendingConsentApp`. [inferred]
- **The open question is a value with its own identity.** A small value type `ConsentQuestion` (a fresh `id` per prompt, the app, the title, the body) is built once when the consent gate posts a prompt; its title and body are exactly what is posted, and its id is the prompt's id in the coordinator and the notification's identifier. The loop stores it as `pendingConsentQuestion` in place of the stored `pendingConsentApp`, which becomes a read-only computed view of `pendingConsentQuestion?.app`, so its readers (detection exclusion, the consent gate, `/state`, `/v1/watch`) keep working unchanged and the two cannot disagree. Equality includes the id, so a later prompt about the same app is a different question. [inferred]
- **Only a prompt's own completion clears it.** When a prompt's answer lands, the loop clears the consent state only if the open question is that prompt's question; a late completion of an earlier prompt (one already declined by Stop Watching or a manual start, or one that registered after its question was cleared) never wipes a newer question. [inferred]
- **The menu answers exactly its prompt, by id, the way a notification tap does.** `AppNotifying` gains two requirements with fail-closed defaults: `askToRecord(_ question: ConsentQuestion) async -> ConsentAnswer` (default: forwards to the existing `askToRecord(title:body:)`, so existing notifiers keep working) and `answerConsentPrompt(id: UUID, granted: Bool) -> Bool` (default: false, nothing answered). `NotificationManager` posts and parks the prompt under the question's id and answers by id through `ConsentPromptCoordinator.resolve(id:answer:)`, the call a notification tap makes, which now reports whether that prompt was waiting. `WatchLoop.answerParkedConsent(_ question: ConsentQuestion, granted: Bool) -> Bool` returns false unless `question` is the open question, and otherwise returns `notifier.answerConsentPrompt(id: question.id, granted:)`. Everything after that is unchanged: `askToRecord` returns, withdraws the notification, and the loop applies the answer exactly as for a notification tap. A click can therefore resolve only the prompt it displayed, whatever else the coordinator holds; `resolveBrowserConsent` (resolve everything parked) stays the automation hook's and Stop Watching's call and is not used by the menu. [inferred]
- **Menu section.** `MenuBarView` gains `consentQuestion: ConsentQuestion?` and `onAnswerConsent: ((ConsentQuestion, Bool) -> Void)?`, both defaulting to nil so existing constructions compile. When a question is set, the menu's first section shows its title and body as posted in the notification, then "Record" and "Ignore" buttons that hand back the question they displayed, then a divider. `AppState` exposes the open question and the answer call as single-member accessors, the pattern the menu-bar scene uses to stay within the type-check budget. [inferred]

## Edge Cases & Constraints

- **Stale menu.** The prompt expires, is answered elsewhere, or is replaced (also by a new prompt about the same app) while the menu is open: a click on the old question changes nothing and `answerParkedConsent` returns false. A menu-style menu bar extra may not refresh its items while open, so this is a normal case, not a rare one. [inferred]
- **Between setting and parking.** The question is set before the coordinator registers the prompt; a click in that window finds nothing under its id, returns false and changes nothing, and the question stays on the icon and in the menu. [inferred]
- **A prompt that registers after Stop Watching** (its question was already cleared): it is not on the icon or in the menu, the menu cannot answer it, and its late completion cannot clear a newer question. Its notification still appears until it expires or is answered, as today. [inferred]
- **A prompt that cannot be posted** (no app bundle, notifications not set up; never the case in the installed app) resolves at once as a decline, as today; the question mark can appear for at most that one hop. [inferred]
- **Another meeting records while the question is open** (an app that records without asking started while the prompt waited): the icon shows the recording animation with the question mark, the menu still offers the question, and a Record answer is dropped exactly as a notification Record is today ("an approval is not a reservation"). [inferred]
- **Watching stopped or a manual recording started** while a question is open: the loop declines the parked prompt as today, so the question mark and the menu section disappear with it; a later menu click on it returns false. [inferred]
- **Ignore from the menu** is the notification's Ignore: a decline with the same cooldown. "Never for this app" stays in the notification and in Settings only. Apps waiting behind the open question are not shown in the menu, as today in the notification. [inferred]
- **Both build variants.** `AppNotifying`, `NotificationManager`'s prompt and answer methods and the coordinator are not behind `#if !APPSTORE`, so the menu fallback works in the App Store build too; nothing new may be placed behind that flag. [inferred]
- **Build gates.** A SwiftUI body or expression that type-checks for over 300 ms fails the build, so the new menu section is its own hoisted view property and the menu-bar scene reads only single-member `AppState` accessors. SwiftLint runs with `--strict`, so files at the 600-line warning stay under it (new code goes into extensions or new files where a file is near the cap). [inferred]
- **Fork rules.** `CLAUDE.md` is not edited (fork rule for PRs into `wapp/main`); the icon and menu entries in `docs/architecture-macos.md` are. [inferred]

### Verification

- **Answer by id, against the real coordinator:** with the fake notification scheduler and two prompts parked, answering the second by its id resolves only the second (the first stays parked and in Notification Center); answering an id that is not parked returns false and resolves nothing; the answered prompt is withdrawn from Notification Center with the matching answer. [inferred]
- **Answer path, through the real poll loop:** a scripted detector and a parking notifier show that answering the open question with Record starts the recording and Ignore records nothing and is not re-asked within the cooldown; the question is cleared after either; a question that is not the open one (older prompt for the same app, already answered, nothing open, watching stopped) returns false and leaves a parked prompt untouched; the posted title and body equal the stored question's. [inferred]
- **Own-completion clearing:** a prompt declined by Stop Watching whose completion lands after a newer question was set leaves the newer question in place. [inferred]
- **Menu wiring (ViewInspector):** the section is absent without a question; with one, its title and body are shown; the Record and Ignore buttons, found by their `A11yID` constants, hand back the displayed question with true and false. One wiring test per control. [inferred]
- **Icon (pure render tests at 1x, the watching-dot test pattern):** for every badge, the question-mark render differs from the watching-dot render while its bottom half is pixel-identical to it (the bottom-right badges are untouched); it stays a template image without red overlays; animated badges still animate under it; the `AppState` question input follows the loop's open question, including when the loop is replaced or removed. [inferred]
- Dev-only snapshot references for the question mark are recorded locally and skipped on CI. How the mark looks in a real light and dark menu bar, and the menu interaction itself, are manual checks for the owner (menu-bar dropdown interaction is manual-QA-only per the GUI testing rules). [inferred]

## Acceptance Criteria

- **R1:** While a "Record <App> meeting?" prompt is open, the menu bar icon shows a question mark at its top right in place of the watching dot, in every state the icon can be in (idle, recording, processing an earlier recording, update available, permission or record-only badge, channel tint); everything else in the icon is drawn as it would be without the prompt. Errors: a prompt that cannot be posted at all (no app bundle, notifications not set up) resolves at once as a decline, as today, and its question mark disappears with it. [paraphrase]
- **R2:** When the prompt ends — answered in the notification, in the menu or through `POST /action/confirmBrowserConsent`, expired after five minutes, or declined because watching stopped or a manual recording started — the question mark disappears and the icon is exactly what it would be without the prompt (the watching dot while watching). Errors: the late completion of an earlier prompt never removes the question mark of a newer open prompt. [paraphrase]
- **R3:** While a prompt is open, the menu opened from the icon shows at its top the prompt's title and text exactly as posted in the notification (including the reminder that everyone must agree to being recorded), with "Record" and "Ignore". When no prompt is open, the section is absent. Errors: none beyond R4. [paraphrase]
- **R4:** "Record" and "Ignore" in the menu answer the open prompt through the same consent coordinator the notification and `POST /action/confirmBrowserConsent` use, by the prompt's id as a notification tap does, with the same effect as the notification's Record and Ignore (Record starts the recording under the existing rules, Ignore starts the same cooldown), and the notification is withdrawn from Notification Center. This also works while the app's notifications are switched off. Errors: a click on a question that is no longer open (expired, answered elsewhere, declined by Stop Watching or a manual start, or replaced by a new prompt, also one about the same app) changes nothing and never answers a different prompt. [paraphrase]

## Boundaries

- `BadgeKind` (including the unused `.userAction`) and the `badge` value of `/state`, `/v1/watch` and `/v1/record` stay unchanged; automation clients read the open question from `pendingConsentApp`. [inferred]
- No "Never for this app" in the menu, no remaining-time display, no colour or pulsing for the question mark: follow-up. [inferred]
- The icon's VoiceOver label (`AppState.currentStateLabel`) does not mention the open question: follow-up. [inferred]
- The Settings warning that a prompt nobody sees means nothing is recorded (`BrowserConsentReadiness`) keeps its wording, although the menu now offers a way to answer: follow-up. [inferred]
- The pending auto-stop question of spec gh-54 on the icon is issue #58; this spec only provides the input it can reuse. [paraphrase]
- No new automation endpoint, and no change to how prompts are timed out, cooled down or denied, or to how a notification tap, the automation hook and Stop Watching answer them. [inferred]
- A prompt that registers after Stop Watching still shows its notification until it expires or is answered (behaviour before this spec): follow-up. [inferred]
