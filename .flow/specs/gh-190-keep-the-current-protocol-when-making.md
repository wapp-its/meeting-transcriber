## Goal & Context

"Regenerate Notes…" makes a finished meeting's protocol again with a chosen template and background info, and moves the previous protocol to the Trash, so a meeting has one protocol at a time. One meeting can need a report for each of several audiences, for example full minutes for the participants and a short summary for others. Today the user has to take the earlier protocol back out of the Trash and rename it by hand. With this spec the new protocol can be saved as an additional report next to the existing one.

## Architecture & Data Models

- **A meeting's files today:** the transcript `<basename>.txt` and the protocol `<basename>.md` in the output folder. That protocol stays the main protocol, with its role unchanged. A basename the app made has the form `<yyyyMMdd_HHmm>_<slug>_<short id>`, with no space or bracket in it. The mockup shortens these names for reading ("Budget review.md"); the sheet shows the real file names. [inferred]
- **Additional report:** a Markdown file in the same folder named `<basename> (<template name>).md`, so Finder sorts it next to the meeting. The template name is as the template picker shows it, except that the built-in template is called "Standard". It has the same document shape and the same owner-only file permissions as a regenerated protocol. [inferred]
- **Whose report a file is (one rule, used by the row's list, the sheet's count, the same-template check and "Regenerate from File…"):** a Markdown file with a `.txt` transcript beside it under its own full name is a meeting of its own, never a report. Any other file whose name ends in `)` is split at each ` (`, and it belongs to the longest part before such a split that has a transcript the way regeneration finds one today: its `.txt`, or the transcript inside its `.md`, which is all a meeting has with "Save raw transcript separately" off. `Budget (Q3) (Short).md` belongs to `Budget (Q3)` when that meeting's transcript is found, else to `Budget`; `Budget (Alpha (Beta)).md` with only `Budget.txt` beside it is the report "Alpha (Beta)" of `Budget`. The text after the split, without its closing bracket, is the name the menu shows. A file with no such part is no report and resolves as today. A hand-named `Budget (Q3).md` with no `.txt` of its own, beside a meeting `Budget`, reads as that meeting's report; that is accepted, since a name alone cannot tell them apart. A meeting a row already knows also keeps its reports when its transcript is gone: from the row's side, its reports are the files named `<basename> (…).md` that no longer meeting name claims. [inferred]
- **No list of reports:** nothing records them while the meeting lives, so a report deleted or renamed in Finder drops out, and a report whose template was deleted later stays listed. [inferred]
- **Moving a meeting to the Trash (gh-97):** when "Move Meeting to Trash…" is confirmed, and again on each "Retry Deletion", the app reads the folder of the meeting's transcript and protocol as its record lists them, and adds each report it finds to the record as an owned file with its identity on disk, in the same save that writes gh-97's pending deletion. From there gh-97's rules apply unchanged: the deletion starts only when that save succeeded, the same-file check right before each move, a result per file, the check after a restart, and the retry. A folder that cannot be read leaves the deletion incomplete, also when the record lists nothing else there, and the retry reads it again. When another record also lists the meeting's transcript or protocol, its reports count as shared too: they are blocked and stay, as gh-97 does for a shared path. [inferred]
- **Reports in gh-97's record (plan):** a report enters the record as a `MeetingFile` under the existing role `previousProtocol`, owned, with its path and identity read when it is listed, appended beside the other entries, never through `MeetingFileRecord.list`, which drops the other files of a role. A report found at a deletion is appended only when its path is not listed yet: a listed entry keeps its identity, so a report replaced since it was listed is refused as replaced, as gh-97 refuses any replaced file. A file the app itself just wrote or moved (an old report copy the regenerator kept, a report a failed rename left under the new name) is appended by gh-97's rule for a kept previous protocol (`MeetingFileStore.noteProtocolReplaced`: an entry of the same path is replaced). No new role and no new field: the release and the development build share the record file, a build without this spec decodes `MeetingFile.Role` strictly and moves a file it cannot decode aside as corrupt, which would empty its records. That role also keeps a report out of the "right after the notes" retention check, which counts only `.protocol` entries. Nothing in this spec tells a report from a kept previous protocol by its role. [inferred]
- **Finding a meeting's reports at a deletion (plan):** one function used by the dialog, the confirm, the action and the retry. For each folder holding a transcript or protocol the record lists (in any state), it reads the folder inside the output folder's scope and returns the files the ownership rule gives to that file's basename, or "unreadable" for that folder. It takes a name only when `lstat` finds a regular file there, so a symbolic link named like a report is never taken, and stores the folder's path plus the name without resolving it further. A folder whose resolved path is not the one the record lists (replaced by a link, moved) counts as unreadable, as gh-97's remover refuses a file in such a folder. [inferred]
- **The confirmation (plan):** the window reads the reports when the user chooses Move Meeting to Trash…, on one row or a selection, in the button's action, never while a menu is built. `TrashConfirmationText` takes them as input and words them by A10, and the request's `named` set (one row, and `TrashSelectionPlan.named` per meeting) holds their paths beside the record's files. A folder it cannot read adds no report to the dialog. Move Audio's dialogs stay as gh-97 wrote them. [inferred]
- **Confirm and action (plan):** `TranscriptionsView.confirm` reads the reports again with the record (`namesEveryFileToMove`), and a report the dialog did not name stops the whole request with gh-97's A22 message. The action (`PipelineController.moveMeetingToTrash(jobID:named:)`, through `runConfirmedDeletion`) reads them once more and refuses an unnamed report the same way it refuses an unnamed record file. A named report gone since is no harm. [inferred]
- **The save before the first move (plan):** `MeetingFileStore.beginDeletion` also takes the reports as files to add; in its one transaction it checks the record against the one read, as today, appends the reports whose paths it does not list yet, and writes the pending mark, whose paths include every report. False starts nothing, as today. `runManualDeletion` then moves the record's covered files, reports included, through gh-97's remover, so the same-file check, the per-file results, the launch check and the retry apply unchanged. `retryDeletion` keeps running without a named set: it reads the folders again and appends a report found since the same way, while a report listed by the earlier run keeps its entry. A report's last look before its move (`MeetingFileStore.startRemoving`) also counts as listed by another meeting when another record lists, not gone, the transcript or protocol whose basename the report belongs to; the report then fails with gh-97's "also listed by another meeting" and stays. [inferred]
- **A folder that cannot be read (plan):** the folders are read before anything is saved. When one cannot be read, the action writes no pending mark and moves nothing; in one store save under the lock, with the same checks as `beginDeletion` (record unchanged since the read, no pending mark), it records "Deletion incomplete" with the reason of A12 and kind `meetingToTrash`, and Retry Deletion reads the folders again. So no launch check, of this build or of the other one, can settle a deletion whose reports were never looked for. [inferred]
- **No deletion during a report run:** gh-97's A19 keeps Move Meeting to Trash and the retry of a Move Meeting off while any regeneration runs, so the window cannot delete a meeting while a report of it is being written; the transcript check under Edge Cases stays for a run that started some other way. [inferred]
- **Notion:** a meeting's Notion page holds its main protocol. An additional report never goes to Notion. It also leaves the job as it is: only a run that writes the main protocol reports its template to the job, because a retried export titles the page by the job's template and exports the main protocol, so an additional report's template there would title the page by the wrong rule. [inferred]
- **The regenerator's record hooks (plan):** an additional-report run calls neither `Environment.regenerated` nor `Environment.protocolReplaced`; the second lists its file under `.protocol` (`MeetingFileStore.noteProtocolReplaced`) and would make the report count as the meeting's saved notes. An old report that the Trash refused, or that could not be put back after a failed write, goes to the record through a hook of its own, which appends it under `previousProtocol` by the rule above, so Move Meeting to Trash finds it as it finds gh-97's kept previous protocol. A Replace run calls both existing hooks as today. The success state and notification name the report's file where today's name the protocol's. [inferred]
- **A rename:** when the pipeline moves a meeting's files to its AI title, its reports move with them under the new name, all or nothing with the rest, and a new name counts as free only when no report of that name exists. [inferred]
- **The rename (plan):** `ArtifactRenamePlan` takes the protocols folder's file names as one more input and stays pure. Besides its closed list it moves each file the ownership rule gives to the old stem as a report, `<old stem> (<name>).md` to `<new stem> (<name>).md`, in the same all-or-nothing run and undo of `PipelineQueue.renameJobArtifacts`, and `availableStem` counts a candidate as taken when a report of it exists. Its header rule against finding files by a folder prefix holds for every other file and is relaxed for reports only, which the ownership rule finds by their whole name before ` (`, so `weekly_sync_retro (Short).md` is never a report of `weekly_sync`. The moves reach the record through `PipelineQueue.noteMoved`, like every other move; that only follows listed entries, so a report that moved and could not be moved back after a later move failed is appended to the record under its new path by the rule for files the app moved, and Move Meeting to Trash still finds it. A folder that cannot be listed renames nothing and keeps the old names with today's warning. [inferred]
- **Regenerate sheet (accepted mockup):** the template and background choice stay as they are. The meeting's lines gain the number of reports after the protocol's file name when there are any ("<file> · 1 additional report", "· 2 additional reports"). Between the background notice and the buttons comes the radio group "Save as:": [paraphrase]
  - "An additional report", with the small line "Saved as “<file>”. The current notes stay as they are." When the chosen template already has a report, that line turns orange and reads "Replaces the existing “<file>”, which is moved to the Trash. The current notes stay as they are."

A row without reports shows neither the heading nor its separator. [paraphrase]
- **The row menu's items (plan):** `RecordingRowActions.RowMenuItem` gains a separator, the heading "Additional Reports" and a report item (its name and file); the pure `menuItems(…, meeting:)` returns them in the accepted order, with gh-97's items after Regenerate Notes… and no separator before them (A11), so the order is tested without a view. `TranscriptionsView.rowMenu`, which builds both menus from one list, renders the separator as a divider and the heading as non-interactive text; a report item opens its file through the window's Open, so a file gone since it was read shows "The file was moved or deleted.". The heading and each report item get an `A11yID`. [inferred]
- **Reports in the row snapshot (plan):** `RecordingRowActions.FilesOnDisk` gains the row's reports (name and file, in alphabetical order), none by default, so `TrashSelectionPlan.applies` keeps building one without reports and a report never decides a selection. `AllRecordingsActions.readFilesOnDisk` reads them by the ownership rule with the row's other files, so they follow `RowAvailability`'s refresh moments (window shown or made key, entries changed, after a row action); the window also refreshes when a regeneration ends, so a new report is listed without leaving the window. Deleting or renaming a report in Finder takes the window out of key and coming back refreshes it, which is how R2's "the next time the menu opens" holds. [inferred]

## Edge Cases & Constraints

- **No protocol yet** (protocol generation was off or failed): the result becomes the main protocol, as today, and the sheet offers no choice. [inferred]
- **Same template again:** saving an additional report for a template that already has one replaces that report the way Replace treats the main protocol, with the old file moved to the Trash; the main protocol is never touched. When the Trash refuses the old report, the new one stays saved, the old one stays beside it under today's `.previous-<stamp>` name, which is no report by the rule above, and the sheet shows today's warning with "report" in place of "meeting notes". A user template named "Standard" shares its report file with the built-in template, so it counts as the same template here. [inferred]
- **The name belongs to another meeting.** In a folder of hand-named files, the ownership rule above can give the report's file name to something other than this meeting: the protocol of a meeting of its own (`Budget (Q3).md` beside `Budget (Q3).txt`, for a template named "Q3"), or a longer meeting name that claims it (`Budget (Q3) (Short).md` beside `Budget.txt` and `Budget (Q3).txt`, for a template named `Q3) (Short`). The rule decides this for the file name the choice would write. The sheet then shows the orange line "“<file>” belongs to another meeting, so this template cannot be saved as an additional report here." and Generate is disabled while that choice is selected. The check runs again right before the write, so a meeting that took the name during the run stops it with today's message and writes nothing. A folder holding only meetings the app named cannot meet this, since those names hold no space or bracket. [inferred]
- **Today's safety holds for both choices:** nothing is replaced when generation fails, when the meeting's files changed while the protocol was made, or when the write fails; the transcript is never changed. The report the run would write counts among those files, so a report that appeared, changed or vanished during the run stops it with today's message. A run that finishes after its meeting went to the Trash finds its transcript gone and writes nothing. [inferred]
- **A name too long for the volume** fails with the existing write-failed message, and nothing is replaced. [inferred]
- **A pipeline retry** of the job rewrites only the main protocol and leaves additional reports alone. [inferred]
- **Privacy:** template names are user text and appear in log lines only as private values. [inferred]
- **Tests of the gh-97 seams, beside Validation's list:** a report's record entry encodes with the raw value `previous_protocol`, and a second report or a kept previous protocol of the same role stays listed beside it; a report that appears after the dialog opened stops the confirm and is refused by the action; `beginDeletion` writes the reports and the pending mark in one save, and a record changed since the read adds nothing; a retry adds a report found since, and a report replaced after the first run is refused as replaced on the retry; a report-named symbolic link to a file elsewhere, and a folder replaced by a link, never lead to a move; an unreadable folder moves nothing, writes no pending mark and leaves Deletion incomplete, also when every listed file is already gone; a report stranded by a failed rename rollback is listed and found by Move Meeting to Trash; a report run leaves the record's `.protocol` entries and the job's template as they were, and a refused Trash of its old copy appends that copy under `previousProtocol`; a rename takes the reports and treats a stem with a report as taken; `menuItems` returns the separators, heading and reports in order, and a selection never offers a report item. [inferred]

## Validation

Test first, from the criteria, in this order, at the cheapest layer that can fail:

1. **The naming rule (pure logic, with the existing target tests):** a plain report, a file with its own transcript, a bracket in the meeting's name, a bracket in the template's name, both meeting names present (the longer wins), a meeting whose transcript is only inside its protocol, no meeting present, a report name that is another meeting's protocol, a report name a longer meeting name claims, and the built-in template's name.
2. **The write (with the existing regenerator tests, which inject every file operation):** an additional report lands at its own path with owner-only permissions and leaves the main protocol and other reports byte for byte; the same template replaces its report and trashes the old one; a meeting without a protocol gets its main protocol; a report that appears, changes or vanishes during the run, a meeting that takes the report's name during the run, a failed write and a failed generation each leave every file as it was; a refused Trash move keeps the new report and the old copy beside it, with the warning, and that copy is not listed as a report; an additional-report run leaves the job's stored template and protocol path unchanged, while a Replace still records its template.
3. **The sheet (the existing sheet state and view tests):** the additional choice is preselected, each small line and the orange lines appear in their accepted wording, the meeting lines count the reports, no choice shows without a protocol, and Generate is disabled on a taken name.
4. **The row (the existing row action and window tests):** the "…" menu and the right-click menu both list the reports under their heading, in order, each opening its file; a row without reports has neither heading nor separator; a report removed from the folder is gone the next time the menu opens; "Open Notes", "Open Last Notes", the automation API's protocol path and a pipeline retry still use the main protocol only.
5. **The deletion (with gh-97's record and Trash tests, on a temporary folder):** reports enter the record in the same save as the pending deletion and before any move, a failed save moves nothing, a report whose identity changed is refused, a refused Trash move and an unreadable folder give "Deletion incomplete", an interrupted deletion comes back with its reports, a retry finds a report added since, a shared transcript blocks the reports, "Move Audio to Trash…" and the automatic deletion leave them. A rename to the AI title takes the reports along (`ArtifactRenamePlan` tests) and a name held by a report is not free.
6. **Both build variants:** the suite runs for the Homebrew and the App Store build, as CI does.
7. **Look:** a dev-only snapshot of the sheet in its three forms and of the row menu, to check that the longer lines wrap. How it looks stays the owner's check on the installed build.
