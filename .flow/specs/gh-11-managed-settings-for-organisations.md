# Managed settings for organisations

## Conversation Evidence

> issue #11 (owner, problem): "For use in an organisation (e.g. through a university's client management) everybody has to set everything up themselves today: models, protocol provider, internal endpoints, templates. There is no way to distribute a configuration or to lock settings."
> issue #11 (owner, request): "1. **Distribute a preconfiguration:** set settings and — once they exist — profiles (#6) centrally, e.g. a profile 'Committee' with the organisation's internal protocol endpoint (such as a LiteLLM gateway), a Swiss German model and a template. 2. **Locked settings:** centrally set values are **read-only** for normal users; they can only choose among the existing profiles. Only administrators change the configuration."
> issue #11 (owner, implementation proposal): "Use the macOS standard: **Managed Preferences.** The client management (MDM, e.g. Jamf or Intune) distributes a configuration profile (`.mobileconfig`) for the app's identifier. `UserDefaults` reads these values automatically; `UserDefaults.objectIsForced(forKey:)` tells whether a value is locked → the control is disabled and labelled 'Managed by your organisation'. The operating system enforces the lock, not the app." · "**Profiles** as a managed key (list of profiles) or as a file in a folder only admins can write (`/Library/Application Support/…`); allow users' own profiles alongside or forbid them by policy." · "**Credentials** not in plain text in the configuration profile: better sign-in through the organisation (SSO) or a token the person stores once themselves (Keychain)." · "Ship a `.mobileconfig` template and a list of all manageable keys."
> issue #11 (owner, acceptance): "Configuration profile with protocol endpoint and locked provider installed → the setting shows the value, cannot be changed, note 'managed'. A centrally distributed profile appears in the choice at the start and cannot be edited." · "Depends on #6 (profiles); central files such as vocabulary see #10."
> coordinator triage 2026-10-06: the owner answered "Spec now, tasks later": this spec is written now and cut into tasks only right before it is built, because it comes last and the specs before it change the code it restructures. The dev build's bundle id differs from the release build's. The profiles part depends on the profiles spec for issue #6; the coordinator adds the spec-level dependency.

## Goal & Context

An organisation that rolls the app out to many Macs wants to hand everyone the same configuration (models, the internal protocol endpoint, profiles) and keep people from changing the parts that matter, such as which endpoint transcripts are sent to. macOS already has the mechanism: a configuration profile installed by the organisation's device management sets values in the app's preferences domain, and the operating system marks them as forced. The app's job is to honour that: use the forced values, show them as locked, never let a user or a user profile route around them, and accept centrally distributed profiles as read-only. [paraphrase]

Every setting the app keeps in `UserDefaults` is read through `AppSettings` (`AppSettings.swift:634-744`), which already receives forced values without any change, because managed values sit above the app's own domain when `UserDefaults.standard` is read. What is missing is everything around that: the app does not know a value is forced, shows an editable control, writes the user's change into its in-memory value (every property persists through a `didSet`, `AppSettings.swift:142ff`), and has no notion of distributed profiles or of which keys an administrator may set. [inferred]

## Architecture & Data Models

- **One table of manageable keys.** A new type lists every manageable key with its value type, its valid values and the Settings control it belongs to. Manageable: every `AppSettings` value persisted as a plain property-list value (booleans, numbers, strings, enum raw values, string lists). Not manageable in v1: the Keychain-backed credentials (`openAIAPIKey`, `claudeAPIKey`, any profile key), the three bookmark-backed choices (output folder, custom vocabulary file, custom model folder), the protocol prompt and gh-2's template files, and internal state that is not a setting. The table is the single source for the code, the documentation and the template (R7). [paraphrase]
- **A seam for "forced".** A small injectable source answers "is this key forced, and with which value"; production asks `UserDefaults.standard.objectIsForced(forKey:)`, tests use a fake, because a test cannot install a configuration profile and `objectIsForced` on a suite `UserDefaults` is always false. `AppSettings` keeps its injectable `defaults` (`AppSettings.swift:120-123`) and gains this source next to it. [inferred]
- **Forced values win everywhere.** A forced key's value is what `AppSettings` holds; every write to it (a control, a notification action such as "Never for this app" on `consentDeniedApps`, a migration, the automation surface) leaves the forced value in place. [paraphrase]
- **Locked controls.** One view modifier, in the shape of `View.recordOnlyDisabled` (`Settings/View+RecordOnly.swift`), disables a control whose key is forced and shows "Managed by your organization" under it. Every control of a manageable key carries it and an `A11yID` constant, so one test can force every key and check every control (CLAUDE.md "GUI Testing"). [inferred]
- **Profiles.** Managed profiles come from one forced key, `managedProfiles`: an array of profile dictionaries in the same shape the profiles spec's `ProfileStore` stores, each with a stable `id`. They are listed with the user's profiles and in the start dialog, marked "Managed", and cannot be renamed, edited or deleted; the only thing a user sets on one is the API key its endpoint needs, stored in the Keychain as for any profile with its own endpoint. A `managedProfiles` value that is not forced (for example one written with `defaults write`) is ignored. [paraphrase]
- **Locks bind profiles too.** The profiles spec's resolver gains the forced keys as an input: a user profile or a per-meeting adjustment cannot override a forced key, while a managed profile can, since it comes from the same administrator. Without this a user profile could send transcripts to an endpoint the organisation locked out. [inferred]
- **Two bundle identifiers.** Preferences are per bundle identifier: the release build reads `app.meetingtranscriber`, the dev build (`scripts/lib/bundle-ids.sh`, installed by the fork's `mt-update` as `/Applications/MeetingTranscriber-Dev.app`) reads `app.meetingtranscriber.dev`. The template targets the release identifier, and the documentation shows the one line to change for the dev build. [inferred]
- **Deliverables.** `docs/managed-settings.md` (what managing does, both identifiers, the key list with types, valid values and Settings labels, the `managedProfiles` shape, how credentials are entered) and a `.mobileconfig` template using the Custom Settings payload (`com.apple.ManagedClient.preferences`, `Forced`) with a locked protocol provider, an endpoint and one managed profile as worked example (A2). [paraphrase]

## Edge Cases & Constraints

- **When a change takes effect.** Forced values are read at launch; a configuration profile installed, changed or removed while the app runs takes effect at the next launch at the latest (A3). [inferred]
- **Removing the profile restores the user.** Because writes to forced keys never reach the app's own domain, removing the configuration profile brings back each user's own earlier values. [inferred]
- **Invalid forced values.** A forced value of the wrong type, or a raw value the build does not know (for example the Claude CLI provider in the App Store build), is not applied: the user's own value is used, the control stays editable, and the key name is logged once at error level. Clamping rules (`pollInterval`, `endGrace`, `asymmetricSilenceWarningSeconds`, `AppSettings.swift:210-295`) apply to forced values as to typed ones, and the control stays locked. [inferred]
- **Managed profile errors.** An entry of `managedProfiles` that does not parse is skipped and logged with its index; a managed profile whose `id` equals a user profile's hides the user profile in lists while the user's entry stays stored; a user profile set as default whose fields a lock now overrides stays default and resolves with the forced values. [inferred]
- **Credentials.** Nothing the app reads from the configuration profile is ever used as a credential. A key named like a credential (`openAIAPIKey`, `claudeAPIKey`, an `apiKey` field inside a managed profile) is ignored and its name logged once. [paraphrase]
- **Automation API.** A forced `debugRPCEnabled = false` keeps the local automation server off even when the app is launched with `MEETINGTRANSCRIBER_DEBUG_RPC=1`, which today starts it regardless (`RPCServerController.swift:60`); the refusal is logged. Homebrew build only, like the server. [inferred]
- **No secrets, no values in logs.** Log lines about managed settings name keys, never forced values, since an endpoint or a profile name can be internal information. `/state` lists the forced key names (no values) so a live check can see what is managed. [inferred]
- **Conflict risk with the original.** The lock modifier touches every Settings view (`Settings/*.swift`, `SettingsView.swift`) and `AppSettings.swift`, which the original edits often; the modifier and the table live in new files, and existing files change only by one modifier line and one identifier per control. [inferred]

### Verification

- With the fake forced source: each manageable key forced to a valid value is what `AppSettings` returns after launch, writes to it change nothing, an invalid value is not applied and is logged, clamping applies; removing the forcing returns the user's earlier value. [inferred]
- Drift guard: a test builds `AppSettings` on a suite, touches every property, and compares the keys written to the suite with the manageable table plus its exclusion list, so a setting added later fails until someone decides whether it is manageable; a second test checks that the documentation's key list and every key in the template are in the table and the template's identifier is the release one. [inferred]
- ViewInspector: with every key forced, every control in the table is found by its `A11yID`, is disabled and shows the managed caption; with none forced, none is. [inferred]
- Resolver tests from the profiles spec, extended: a user profile and a per-meeting adjustment cannot override a forced key; a managed profile can. `ProfileStore` tests: forced and unforced `managedProfiles`, an unparsable entry, an id collision, a credential field ignored. [inferred]
- `RPCServerController` test: forced `debugRPCEnabled = false` with the environment variable set leaves the server off. [inferred]
- The owner installs the template, edited for the dev identifier, on a Mac and checks a locked control and a managed profile in the shipped app, then removes it (see the Human checks in the report). [paraphrase]

## Acceptance Criteria

- **R1:** With a configuration profile that forces a manageable key, the app uses the forced value, and that key's control in Settings is disabled and shows "Managed by your organization". Errors: an invalid forced value is not applied, the control stays editable, and the key name is logged once. [paraphrase]
- **R2:** No user action changes a forced value: not the control, not a notification action, not the automation surface, not a migration. Errors: a refused write is logged once per key and launch, with the key name only. [paraphrase]
- **R3:** A profile installed, changed or removed takes effect at the next app launch at the latest, and removing it restores each user's own earlier values. Errors: no error surface. [inferred]
- **R4:** A forced key cannot be overridden by a user profile or a per-meeting adjustment; a managed profile may set it. In a user profile's editor the forced field is shown locked with the same caption. Errors: no error surface beyond R1. [inferred]
- **R5:** Profiles in a forced `managedProfiles` key appear in the profile list and in "Start with options…", marked "Managed", and cannot be renamed, edited or deleted; the user can enter the API key a managed profile's endpoint needs, which is stored in the Keychain. Errors: an entry that does not parse is skipped and logged; an unforced `managedProfiles` value is ignored. [paraphrase]
- **R6:** Credentials are never read from the configuration profile: a credential-named key or field there is ignored and its name logged, and the documentation and template contain none. Errors: no error surface. [paraphrase]
- **R7:** The repository ships `docs/managed-settings.md` and a `.mobileconfig` template that match the manageable-key table, enforced by a test that fails on any key in either that the table does not know. Errors: no error surface. [paraphrase]
- **R8:** A forced `debugRPCEnabled = false` keeps the automation server off even under `MEETINGTRANSCRIBER_DEBUG_RPC=1`. Errors: the refusal is logged. [inferred]

## Boundaries

- Follow-up: a policy key that forbids users' own profiles and per-meeting adjustments ("they can only choose among the existing profiles", issue #11 request 2); in v1 locks already bind them (R4), which covers the confidentiality case. [paraphrase]
- Follow-up: a managed default profile, managed output folder and vocabulary file by path (bookmarks cannot be distributed), managed protocol templates and central files (issue #10). [paraphrase]
- Follow-up: applying a changed configuration profile while the app runs. [inferred]
- Out: sign-in through the organisation (SSO); profiles as files in an admin-only folder (the configuration profile already carries them, and a file would need its own installer). [paraphrase]
