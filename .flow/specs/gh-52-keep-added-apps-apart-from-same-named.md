# Keep added apps apart from same-named apps

## Conversation Evidence

> issue #52 (problem): "With "Add App…" (from the original, merged in with #47) any app can be watched. But detection knows a watched app only by its **display name**. If two different apps have the same name, for example an added app "Zoom" next to the built-in Zoom, they share one identity:"
> issue #52: "**"Never for this app"** for one also blocks the other (the name is what is stored, `AppSettings.consentDeniedApps`)."
> issue #52: "Counters, cooldown and "meeting still running" (`MicInputDetector.isMeetingActive`) apply to both: activity in one can keep the other's recording running."
> issue #52: "**Not affected:** the prompt itself. Since #47 an added app always asks, under any name; no app records without consent. Both faults err on the cautious side (more blocked, recording somewhat longer)."
> issue #52 (when it matters): "When someone adds an app whose display name equals a built-in or another added app. "Add App…" already refuses apps with the same bundle ID or the same executable name; what remains are different apps with the same display name."
> issue #52 (solution idea): "Key added apps internally by their bundle ID (e.g. `custom:<bundleID>` as the key for counters, cooldown, deny list), the display name only for the UI. Touches code the original changes often (`MicInputDetector`, deny list) – best proposed to the original first, since the bug exists there the same way."
> coordinator triage 2026-10-06: "prio:later. Apps added via "Add App…" are identified by display name only, so two different apps with the same display name share "Never for this app" (`AppSettings.consentDeniedApps` stores the name), the consent cooldown/counters and `MicInputDetector.isMeetingActive`. Fix: key added apps internally by bundle id (e.g. `custom:<bundleID>`) for counters, cooldown and deny list; display name only in the UI."
> coordinator triage 2026-10-06: "Data integrity: existing deny-list entries are names. Plan a migration that keeps every "Never" the user set (losing one makes that app ask again: safe direction, but still a user-visible regression) and keeps Settings → General's deny-list review/revert working."
> coordinator triage 2026-10-06: "The same bug exists in the original repo; the fork fixes it without waiting (fork rule: never wait for the original's maintainer)."

## Goal & Context

An app added under Settings → General → Apps to Watch → "Add App…" is watched through the microphone detector, but everything the app remembers about it is filed under its display name. A different app with the same display name, built in or added, therefore shares its "Never for this app", its detection and prompt cooldowns, and its "call still running" check: a Never answered for one silences the other, and a call in one keeps the other's recording running. The user should be able to tell the app "never this one" without silencing an unrelated app that happens to carry the same name, and a recording should end when its own app's call ends. [paraphrase]

Checked against today's code (`wapp/main` 65888b53), the name is the identity in more places than the issue lists: [inferred]
- `MicInputDetector` files confirmation counts, detection cooldowns, the winning match and title matchers under `meetingPattern.appName`, and `isMeetingActive` accepts any pattern carrying that name.
- `PowerAssertionDetector.isMeetingActive` compares the meeting's `pattern.appName` with its own identity keys, so the built-in Zoom's call assertion keeps a recording of an added app named "Zoom" running, across detectors (`CompositeMeetingDetector` ORs liveness).
- The consent gate files the deny list, the decline and no-answer cooldowns (`BrowserConsentPolicy`), the one-open-prompt slot, the apps waiting for it and the detector reset under `meeting.pattern.appName`, and so does the reset after a recording ends.
- Settings counts an added app as "asks first" unless its display name is denied (`AppSettings.anyWatchedAppAsksFirst`).

The prompt itself is already safe: since commits 7d02d4aa and 55dac33f an added app always asks, whatever its name, and its detected meeting carries its own pattern rather than a built-in one looked up by name. This spec does not change that. [inferred]

## Architecture & Data Models

- **Identity key on the meeting pattern.** `AppMeetingPattern` gains a stored `identityKey: String`, set through a new optional `identityKey:` initializer argument that defaults to `appName`. Every built-in pattern and every browser identity synthesised by `PowerAssertionDetector.meetingIdentity` therefore keeps its name as its key, unchanged. An added app's pattern (`MicInputDetector.MicPattern.meetingPattern`, the `usesBuiltInMeetingPattern == false` branch) sets it to `custom:<bundleID>`, using the pattern's single bundle ID. [inferred]
- **Key helper.** A new fork-local type `AddedAppIdentity`, in its own file, holds the key format in one place: `key(bundleID:) -> String` (`"custom:" + bundleID`) and `bundleID(fromKey:) -> String?` (nil for any string without the prefix). Nothing else spells the prefix. [inferred]
- **Identity vs. display.** Everything that remembers or compares an app uses `pattern.identityKey`: the mic detector's counters, cooldowns, winning match, title-matcher table, deny check (`isIdentityDenied`) and `isMeetingActive` filter; `PowerAssertionDetector.isMeetingActive`'s `identifies(meetingAppName:)` argument; the default `MeetingDetecting.checkOnce(excluding:)`; and in the consent gate the deny list, `BrowserConsentPolicy`, the open-prompt slot, `appsWaitingForPrompt`, `appsExcludedFromDetection` and every `detector.reset(appName:)` call (the parameter label stays; it now carries the identity key). Everything a person reads uses `pattern.appName`: the prompt title and body, the recording's app name (job, sidecar, menu status), the "<App> Call" title placeholder, the title matcher's owner names, and `pendingConsentApp` on `/state` and `/v1/watch`. [inferred]
- **Open-prompt state.** `WatchLoop` keeps both the identity key (for gating and exclusion) and the display name of the app being asked about; `pendingConsentApp`, read by the `/state` and `/v1/watch` builders, keeps returning the display name, so neither RPC file nor the `/v1/watch` contract changes. [inferred]
- **Deny list.** `ConsentDenyList` keeps storing strings, now identity keys: a Never answered for an added app stores `custom:<bundleID>`, one for a built-in app or a browser stores its name as today. A pure `ConsentDenyList.displayName(for:resolveAppName:)` turns an entry into its Settings row text: `"<display name> (added app)"` for a key, resolved through `MicInputDetector.appDisplayName(bundleID:)` (which falls back to the bundle ID for an app that is not installed), and the entry unchanged otherwise. The "Never record these apps" rows in Settings → General show that text; Remove keeps reverting the stored entry. [inferred]
- **One-shot migration.** On the first `AppSettings` init that finds the defaults flag `consentDeniedAppsAddedAppKeysMigrated` unset, the deny list read from defaults is passed through a pure `ConsentDenyList.migratingAddedAppNames(_:addedBundleIDs:displayName:)`: for every bundle ID in the stored `watchCustomApps` whose current display name, or bundle ID, is on the list, its `custom:<bundleID>` key is appended (once). No entry is removed or reordered. The result and the flag are written to defaults; later launches skip the step. It follows the existing `audioDebugLogging` → `verboseDiagnostics` migration inside `AppSettings.init`. [inferred]
- **Readiness warning.** `AppSettings.anyWatchedAppAsksFirst` counts an added app as asking unless `AddedAppIdentity.key(bundleID:)` is denied. [inferred]
- **An added app is never also a browser meeting.** Keying the two apart would otherwise split one call in an added Electron app (a Slack huddle, say) into two identities when Browser Web Meetings is on: the browser path sees its WebRTC assertion under the process name, the mic path sees it under `custom:<bundleID>`, and an Ignore or Never on the first prompt would be followed at once by a second prompt for the same call. Today the shared name hides this. `PowerAssertionDetector` therefore gains `addedAppBundleIDs: [String]` (default empty) and an injectable `bundleIDForPID: (pid_t) -> String?` (default: `NSRunningApplication(processIdentifier:)?.bundleIdentifier`); a process-open (browser) pattern skips an assertion whose PID resolves to an added app's bundle ID, or to `<bundleID>.<anything>`, the rule an added app's mic pattern uses (`MicPattern.matches(bundleID:)` with helpers). `WatchingController.defaultDetectors` sets `addedAppBundleIDs` from `settings.watchCustomApps`, frozen per watch session like the mic patterns. Same principle as `PowerAssertionDetector.claimedProcesses` for native apps, but by bundle ID and from user data rather than a static name list. [inferred]

## Edge Cases & Constraints

- Two added apps with the same display name get two keys and are kept apart from each other exactly as from a built-in. [inferred]
- The same added app removed and added again keeps its key, so its Never still applies; a removed app's deny entry stays listed and removable, as name entries do today. [inferred]
- An added app that is not installed shows its bundle ID as its name, in the Apps to Watch row as today and in its deny-list row ("com.example.app (added app)"). [inferred]
- Migration, ambiguous name: a legacy "Zoom" entry may have been answered for the built-in Zoom, an added "Zoom" or a browser process called "Zoom"; which one cannot be recovered. The name entry stays (it keeps blocking whatever it blocked), and each added app carrying that name also gets its own key, so nothing that was blocked becomes unblocked. The user may then see two rows, "Zoom" and "Zoom (added app)", and can remove either. [inferred]
- Migration, app not installed at that moment: its display name cannot be resolved, so a legacy entry under its old display name is not carried over; once reinstalled it asks again (the safe direction), and the name row stays removable. A legacy entry equal to its bundle ID (stored while it was not installed) is still carried over. [inferred]
- Migration runs once per defaults domain. A later name entry is never re-migrated, which is what keeps a new Never for the built-in Zoom from being copied onto an added "Zoom". [inferred]
- Downgrading to an older build leaves `custom:` entries the old build does not understand: it lists them raw and the added app asks again. Accepted; nothing breaks. [inferred]
- The browser-path exclusion only looks up a PID when Browser Web Meetings is watched, the added list is non-empty and the assertion already matched the WebRTC keyword, so a default install pays nothing. A PID whose bundle cannot be resolved is treated as not added (browser path as today). [inferred]
- An added app's WebRTC assertion that the browser path now skips may still show up once per session in the "power assertion did not match" diagnostic (`PowerAssertionDetector.unmatchedWatchedAssertionKeys`), like a natively claimed process does today. Accepted. [inferred]
- `./scripts/lint.sh` runs SwiftLint `--strict`, so a file crossing the 600-line `file_length` warning fails lint; `WatchLoop`'s main file is within a few lines of it (see the task). [inferred]
- No code under `#if APPSTORE`/`#if !APPSTORE` is touched; both variants get the change. [inferred]

## Acceptance Criteria

- **R1:** "Never for this app" answered for an added app keeps only that app from being detected and recorded; a built-in app or another added app with the same display name is still detected and still asks. Never answered for a built-in app (e.g. Zoom) does not block an added app named "Zoom". Errors: a Never on an added app is stored as `custom:<bundleID>`; nothing is stored under the display name. [paraphrase]
- **R2:** An added app's confirmation count, detection cooldown, decline and no-answer cooldowns, and its place in the "one prompt at a time" queue are filed under its own identity: a same-named built-in or added app being declined, ignored, left unanswered, detected or recorded never starts one of these cooldowns for it and never suppresses its prompt. Errors: two rules that apply to every app alike stay as today and are not identity-specific: while one prompt is open every other app that needs one waits for it, and the detector reset after any answer or recording restarts every app's confirmation count (Boundaries). [paraphrase]
- **R3:** A recording of an added app keeps running only while that app (its bundle or a `<bundleID>.*` helper) holds the microphone; a same-named built-in app's microphone use or call assertion, or a same-named added app's microphone use, does not keep it running, and an added app's microphone use does not keep a same-named built-in's recording running. Errors: when its own app releases the microphone the recording ends after the end grace, as today. [paraphrase]
- **R4:** Wherever a person reads it, an added app appears under its display name: the consent prompt, the recording's app name (job, record-only sidecar, menu status), the "<App> Call" placeholder title, `pendingConsentApp` on `/state` and `/v1/watch`, and its row in Settings → General → "Never record these apps", shown as "<display name> (added app)"; Remove on that row deletes only that entry. Errors: an added app that is not installed shows its bundle ID in place of the name. [inferred]
- **R5:** On the first launch of this version, every existing "Never" is kept: each added app whose current display name or bundle ID is on the deny list gets its own key added, and no entry is removed; built-in apps and browsers stay denied exactly as before. The step runs once and never again. Errors: an added app not installed at that moment cannot be matched by display name; its old name entry stays, removable, and the app asks again once reinstalled. [paraphrase]
- **R6:** The Settings warning that the consent prompt cannot be seen counts an added app as asking unless that app's own key is denied; a denied built-in or added app with the same name does not count it out. Errors: none. [inferred]
- **R7:** While an app is in the added list, its process is never detected as a browser meeting: a call in it raises one prompt through the microphone path, and one Ignore or Never answers that call. Removing the app from the list gives today's behaviour back. Errors: a process whose bundle cannot be resolved is handled by the browser path as today. [inferred]
- **R8:** Built-in apps and browser meetings behave exactly as before: same detection, same deny-list entries, same cooldowns, same prompt text, same `/state` and `/v1/watch` values. Errors: none; every existing test other than the three named under Verification passes with its assertions unchanged. [inferred]

## Resolved via Research
<!-- provenance: plan on 2026-10-06; the planner ran the docs-scout, practice-scout and docs-gap-scout charters inline (no subagent dispatch was available) -->

### docs-scout
- **AppKit `NSRunningApplication.init(processIdentifier:)`** returns the running application for a PID, or nil when none is registered; `bundleIdentifier` is nil for a process without a bundle. A nil answer is treated as "not an added app". Source: https://developer.apple.com/documentation/appkit/nsrunningapplication/init(processidentifier:)

### practice-scout
- **Measured:** on this Mac (macOS 26, 2026-10-06) an Electron app's power assertion is held by its main process, and `NSRunningApplication(processIdentifier:)` on that PID returned the app's bundle ID while daemons (`powerd`, `caffeinate`) returned nil, so matching an assertion to an added app by PID → bundle ID works without reading executable names. Source: throwaway probe over `IOPMCopyAssertionsByProcess`, planner scratch, not committed

### docs-gap-scout
- **Docs that must change:** none in the fork. `docs/automation-api.md` keeps describing `pendingConsentApp` as the app name, which stays true; the original's `CLAUDE.md` does not mention added-app identity and is not edited by fork work (Boundaries follow-up). Source: docs/automation-api.md (`pendingConsentApp` field description)
