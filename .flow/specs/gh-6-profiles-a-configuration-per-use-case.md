## Goal & Context

Every setting applies to every recording, so a person who alternates between, say, a committee meeting (Swiss German model, Nemotron diarization, a local language model) and a private conversation (stock model, Sortformer, no protocol) changes several settings by hand before each recording. Profiles are named configurations chosen when a recording starts; one profile is the default, used whenever nothing is chosen. [paraphrase]

Today a job does not even keep the configuration it was recorded under. `PipelineController.makeQueue` (`PipelineController.swift:247-294`) copies some settings into the queue when watching starts (diarization on/off, expected speakers, VAD, microphone speaker label, echo dedup) and hands it closures that read others live at stage time (the diarizer mode at `:254`, the whole protocol provider at `:256` via `makeProtocolGenerator` `:348`, the terminology rules at `:279`, echo cancellation at `:265`), while `EngineController.syncEngineSettings` (`EngineController.swift:94-144`) pushes the current model, language and vocabulary into the shared engine instances whenever Settings change. A job waiting in the queue is therefore processed with whatever is configured when its stage runs, and only three values are frozen per job today (`PipelineJob.swift:127-143`: the two transcript output options stamped at enqueue by `PipelineQueue.stampTranscriptOutputOptions`, `PipelineQueue.swift:507`, and `usedDiarizerMode` recorded after diarization). Profiles make that worse unless the choice is frozen into the job, which is why the owner's design starts with a frozen job configuration. [inferred]

## Architecture & Data Models

- **Three layers, resolved once.** Global settings (`AppSettings`) → the chosen profile (overrides only the fields it sets) → adjustments for this one meeting (gh-2's template and background). A pure resolver turns the three into one `JobConfiguration`; nothing else combines them. [paraphrase]
- **`JobConfiguration` (new value type, Codable, `version: Int`).** Holds every value a pipeline stage reads from Settings today, not only the fields a profile can override: transcription engine; WhisperKit model selection (variant plus origin, `WhisperKitModelOrigin`); transcription language; vocabulary file path and bookmark; WhisperKit vocabulary-prompt switch; terminology rules text; diarization on/off, diarizer mode, expected speakers, the five offline tuning values, the microphone speaker label; VAD on/off and threshold; echo cancellation and echo dedup; protocol provider with its provider-specific fields (Claude CLI binary, OpenAI-compatible endpoint and model, gh-7's CLI and custom-command fields), protocol language, gh-2's template reference and background text; the two transcript output options; the profile's id and name. It never holds a secret: a credential is a Keychain account reference, resolved when the protocol generator is built. [paraphrase]
- **Stored on the job.** `PipelineJob` gains an optional `configuration` field, stamped when the job enters the queue (recording, import, automation API, recovered orphan), the same admission point `stampTranscriptOutputOptions` uses today. A recording resolves its configuration when it starts and carries it to its enqueue, so a settings change during a long meeting does not change it. The existing per-job fields (`includeFullTranscriptInProtocol`, `saveRawTranscriptSeparately`, gh-2's template and background) move into the configuration; snapshots that only carry the old fields still decode and keep their values. `usedDiarizerMode` stays a record of what ran (a re-run may differ from the configured mode). [inferred]
- **Stages read only the configuration.** One accessor on the queue (configuration for a job id) replaces the queue-level copies (`diarizeEnabled`, `numSpeakers`, `micLabel`, `vadConfig`, `echoDedupEnabled`, `isEchoCancellationEnabled`, `PipelineQueue.swift:89-127`) and the live factories: the diarizer factory, the protocol generator factory and the terminology normalizer take the job's configuration as input. The queue keeps only what is not per job: the output folder and its security scope, logs, staging folder. Read sites today: `PipelineQueue+Stages.swift:362,379` (echo), `:407` and `:803-814` (mic label), `:445` (terminology), `:469,:987` (VAD), `:542-572` (diarization, expected speakers), `:924` (protocol generator), `:964` (output options); the naming session's late paths `SpeakerNamingSession.swift:212` and `SpeakerNamingSession+Late.swift:152-160,232,277`. [inferred]
- **Engine per job.** The transcription stage picks the engine instance (WhisperKit or Parakeet, both owned by `EngineController`) from the job's configuration and passes the job's model, language and vocabulary with each transcription call, instead of relying on the engine state that the Settings observer writes (A7). The stage-timing tag (`PipelineQueue.swift:840,861`) names the job's engine. [inferred]
- **`ProfileStore` (new, `@Observable`, separate from `AppSettings`).** Owns the user's profiles and which one is the default. Persisted as a property-list array under one key of the app's own defaults domain (A3), with an injectable `UserDefaults` like `AppSettings` (`AppSettings.swift:120-123`) so tests use a suite. A built-in "Standard" profile overrides nothing, cannot be renamed or deleted, and is the default until another profile is marked. A profile stores optional overrides; an unset field follows the global setting (A2). [inferred]
- **Profile fields (v1).** Transcription engine; WhisperKit model (a stock variant, or a custom Hugging Face repository plus variant); transcription language; diarization on/off, diarizer mode, expected speakers; protocol provider with its endpoint, model and (after gh-7) CLI fields; protocol language; protocol template (gh-2); VAD on/off; echo cancellation on/off; the two transcript output options. [paraphrase]
- **Credentials.** A profile that keeps the global protocol endpoint uses the global key (`openAIAPIKey` / `claudeAPIKey` Keychain accounts, `AppSettings.swift:560-585`). A profile that sets its own OpenAI-compatible endpoint has its own key, stored with `KeychainHelper` under an account derived from the profile id and entered in that profile's editor; the profile and the job store only that account name (A4). Deleting a profile deletes its Keychain item. [inferred]
- **UI.** Settings gains a "Profiles" tab (`SettingsView.swift:99-126` lists the tabs): the list with add, rename, delete and "Make default", and an editor for the selected profile in which every field offers "Same as Settings" next to its own value. gh-2's "Start with options…" dialog gains a profile picker at the top, preselected with the default profile; picking a profile pre-fills the dialog's template from that profile. [inferred]
- **Where a profile is chosen in v1.** Only in "Start with options…". "Start now", "Record App…", "Record Microphone Only", automatically detected meetings, file imports and the automation API use the default profile (A5). [inferred]

## Edge Cases & Constraints

- **Upgrade is invisible.** With no user profile, "Standard" is the default and resolves to exactly today's settings; nothing is written to disk until the user creates a profile. [inferred]
- **Restored and retried jobs.** A job restored from a snapshot written before this spec has no configuration: it gets one resolved from the current settings when it is restored, once, and keeps it from then on. A retried job (`PipelineJob.prepareForRetry`, `PipelineJob.swift:232`) keeps its configuration; a re-run of diarization from the naming dialog uses the mode the user picks there and everything else from the job's configuration. [inferred]
- **Settings observer vs. job.** `EngineController` keeps syncing global settings into the shared engine instances for live captions and the launch preload; a job's transcription must not read that state, because `WhisperKitEngine.transcribeSegments` awaits `ensureModel()` before it snapshots its options, so a Settings change during the load or between the app-track and mic-track calls would otherwise reach the running job. [inferred]
- **Model switching.** Two consecutive jobs with different WhisperKit models each load their own model; the second load drops the first (`applyModelVariant`, `WhisperKitEngine.swift:267`). A model that is not on disk is downloaded by the transcription stage as today. Live re-transcribe captions that run on the WhisperKit engine while a job has loaded another model use that model until the next sync; accepted, since captions are never saved. [inferred]
- **A deleted or broken profile.** Deleting a profile never changes jobs already queued with it. A profile field this build cannot use (the Claude CLI or gh-7's CLI providers in the App Store build, an unknown raw value written by a newer build) follows the global setting, and the editor shows that. A template a profile references that no longer exists falls back to the default template with a warning on the job. [inferred]
- **Unknown configuration version.** A job whose configuration has a version this build does not know is given one resolved from the current settings, with a warning on the job; it is never processed with half-decoded values. [inferred]
- **No secrets at rest.** The pipeline snapshot, the event log, `TerminalJobStore`, `/state` and the logs never contain an API key; profile names are user text and are logged `.private`, profile ids `.public`. [inferred]
- **App Store variant.** Provider fields for the Claude CLI and gh-7's CLI providers exist only under `#if !APPSTORE`, like `ProtocolProvider.claudeCLI` (`AppSettings.swift:98-116`). [inferred]
- **Conflict risk with the original.** The change runs through files the original changes often: `PipelineQueue.swift`, `PipelineQueue+Stages.swift`, `PipelineQueue+Recovery.swift`, `PipelineJob.swift`, `PipelineController.swift`, `SpeakerNamingSession.swift`, `SpeakerNamingSession+Late.swift`, `EngineController.swift`, `WhisperKitEngine.swift`, `ParakeetEngine.swift`, `TranscribingEngine.swift`, `WatchLoop.swift`, `WatchingController.swift`, `SettingsView.swift`, `MenuBarView.swift`. New types go into new files (`JobConfiguration.swift`, `JobConfigurationResolver.swift`, `ProfileStore.swift`, `Settings/ProfilesSettingsView.swift`), and existing files change only at their read sites, so the fork's six-hourly upstream merge (`wapp-upstream-sync.yml`) conflicts in as few hunks as possible. Tasks are cut after the earlier specs have landed (D1), so the read-site list above is re-verified then. [inferred]

## Acceptance Criteria

- **R1:** Every job carries a `JobConfiguration` from the moment it enters the queue (recording, import, automation API, recovered orphan), and transcription, diarization, echo handling, VAD, protocol generation, the naming dialog's late confirm and re-run, and retry read only from it. Changing any setting or the default profile while a job waits or runs does not change how that job is processed. Errors: a job restored from an older snapshot without a configuration gets one resolved from the current settings once, at restore, and keeps it. [paraphrase]
- **R2:** No API key or other secret is stored in a job, a profile, the pipeline snapshot, the event log, the terminal-job store, `/state` or a log line; the protocol generator resolves the job's credential reference from the Keychain when it is built. Errors: a referenced Keychain item that is missing makes protocol generation fail for that job with a warning that names the profile, and the transcript is kept, as for any generation failure today. [paraphrase]
- **R3:** Settings → Profiles lets the user create, rename, delete and mark as default a profile, and set per profile the fields listed under "Profile fields (v1)", each defaulting to "Same as Settings". A built-in "Standard" profile exists, cannot be renamed or deleted, and is the default until another profile is marked. Errors: an empty or duplicate name is refused with an inline message; deleting the default profile makes "Standard" the default; deleting a profile leaves queued jobs that use it unchanged. [paraphrase]
- **R4:** Profiles and the default choice survive an app restart and are stored by `ProfileStore`, not as `AppSettings` properties. Errors: an entry that cannot be read is skipped with a log line and the other profiles load; a field this build cannot use follows the global setting and the editor says so. [inferred]
- **R5:** "Start with options…" shows a profile picker preselected with the default profile; picking a profile pre-fills the dialog's template from it; the template and background chosen in the dialog apply to this meeting only and never change the profile. The recording's job is processed with global settings, overridden by the profile, overridden by the dialog's choices. Errors: a profile deleted while the dialog is open is reported in the dialog and the recording does not start until another profile is picked. [paraphrase]
- **R6:** "Start now", "Record App…", "Record Microphone Only", automatically detected meetings, file imports and the automation API use the default profile. Errors: no error surface beyond R1. [inferred]
- **R7:** A job whose configuration names an engine or model other than the one loaded is transcribed with its own engine and model, loaded (and downloaded if needed) by the transcription stage; the next job loads its own. Errors: a model that cannot be loaded fails the job with an error naming the model and the profile; the job is never transcribed with another model instead. [inferred]
- **R8:** A profile that sets its own OpenAI-compatible endpoint keeps its own API key in the Keychain, entered in that profile's editor; a key entered for one endpoint is never sent to another. Deleting the profile deletes its key. Errors: a Keychain write that fails is shown in the editor and the key is not reported as saved. [inferred]

## Boundaries

- Follow-up (issue #6 step 4b, its own spec, depends on this one): recording sources per profile and per meeting (#5). [paraphrase]
- Follow-up (issue #6 step 5): a profile or auto-start choice per detected app (#3). [paraphrase]
- Follow-up: the expected participant count in the start dialog choosing the diarization model by configurable thresholds, a profile restricting which diarization models are offered, and the Teams participant count pre-filling the field (issue #6 comment of 2026-09-30); the thresholds are unproven, and the field only matters once the rule exists. [paraphrase]
- Follow-up: the output folder as a profile field; the queue holds one output folder and its security scope for its lifetime (`PipelineController.swift:43,56-72`, `PipelineQueue.swift:69-86`), so a per-job folder changes the naming-sidecar and recovery paths. [inferred]
- Follow-up: choosing a profile for imports, from the consent prompt of a detected meeting, and through the automation API (`/v1/record`, `/v1/jobs`, `/v1/transcribe`). [inferred]
- Follow-up candidates not asked for: vocabulary file, terminology rules, diarization tuning and a custom model folder on disk per profile; live captions following the profile; exporting and importing profiles. [inferred]
- Centrally distributed, read-only profiles and locked settings belong to the managed-settings spec for issue #11, which depends on this one. [paraphrase]
- Changing a finished job's profile and regenerating its protocol is not part of this spec. [inferred]
