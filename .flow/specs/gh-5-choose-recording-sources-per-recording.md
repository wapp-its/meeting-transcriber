# Choose recording sources per recording

## Conversation Evidence

> issue #5 (owner, problem): "Today the app records **one** microphone (Settings → Audio, or 'System Default') plus the audio of the meeting app. Which sources are recorded cannot be set per recording."
> issue #5 (owner, request): "In the start dialog from issue #2 (and as the default in the settings) **choose the recording sources**: **one or more microphones** (e.g. headset + room microphone, or several USB microphones), **app audio** of one or more apps (Teams, Zoom, browser …) or none at all. Several sources are mixed together; additionally **save each source as its own track** (multichannel WAV), if wanted."
> issue #5 (owner, why separate tracks): "Separate tracks help speaker attribution: one person per microphone makes attribution easier — though not automatically unambiguous, because microphones pick up their neighbours (crosstalk typically only 12–23 dB quieter). Level matching per source (see issue #4) becomes possible."
> issue #5 (owner, technical notes): "Several input devices at once: via an aggregate device or one recording per device with a shared time base; mind the clock drift between devices. App audio per app already exists ('Record App…')."
> issue #5 (owner, acceptance): "Recording with headset + built-in microphone + Teams audio → mixed track plus three single tracks, in sync (offset < 20 ms). Recording without app audio (room microphone only) selectable."
> issue #6 (owner): the profile content includes "later recording sources (#5)".
> coordinator triage 2026-10-06: the owner answered "Spec now, tasks later": this spec is written now and cut into tasks only right before it is built, because it comes last and the specs before it change the code it restructures. It breaks the pipeline's two-track assumption (app `R_` / mic `M_` prefixes, the dual-track diarization merge, echo-bleed detection over a pair, `DualSourceRecorder`), and each such place is named here as a constraint. It depends on the profiles spec for issue #6, because sources are a profile field and a start-dialog choice; the coordinator adds the spec-level dependency.

## Goal & Context

A recording today captures at most one microphone and the audio of one app. People who meet in a room with several microphones, or who want their headset and a room microphone at once, cannot record that, and nobody can keep the individual sources apart for later work (speaker attribution, level matching per source). The owner wants the sources chosen per recording, in the start dialog and as a default in Settings, mixed for processing and optionally kept as separate, time-aligned tracks. [paraphrase]

What exists: a microphone-only recording ("Record Microphone Only", issue #633, `RecordingSource.micOnly`) and an app-only one ("No Microphone"), so "no app audio" is already selectable, but only with the one microphone from Settings → Audio (`AppSettings.micDeviceUID`, `AppSettings.swift:236`). The capture library already taps a list of processes as one app track (`AudioCaptureConfiguration.pids`, `tools/audiotap/Sources/AudioCaptureConfiguration.swift:20-25`), which is how several apps can share one tap. Everything else assumes exactly one app track and one microphone track. [inferred]

## Architecture & Data Models

- **Sources value.** `RecordingSource` (`RecordingSource.swift:16-27`, three cases) becomes a value holding a set of microphones (device UIDs, "System Default" as one entry) and a set of apps (process roots), with at least one source; the empty combination stays unrepresentable, as `RecordingSource` makes it today. [inferred]
- **Capture.** All chosen apps share one process tap: their PID trees are unioned into the one `pids` list the tap already takes, so the far end stays one app track. Each microphone gets its own capture with its own device pin, restart handling and stall watchdog, as the single microphone has today (`MicCaptureHandler`), and all microphones open before the tap, keeping the start order issue #693 made load-bearing (`AudioCaptureSession.start()` doc comment). [inferred]
- **One timeline.** Every source is placed on the host clock for the whole recording, not only at its first frame: `TimelineAnchor` (`tools/audiotap/Sources/TimelineAnchor.swift`) already fills a source that falls behind with silence; a source whose clock runs ahead is corrected too, so no two tracks drift apart over a long recording (A3). The per-source files are padded to one shared origin, the way `MicDelayNormalisation` pads the app track today, so sample *n* of every per-source file is the same moment. [inferred]
- **Two logical tracks for processing (v1).** The pipeline keeps receiving exactly what it receives today: the app track (all chosen apps) and one microphone track, which is the sum of all chosen microphones after alignment. A recording without apps is processed as a microphone-only recording, one without microphones as an app-only one (A2). [inferred]
- **Per-source tracks.** When "Keep each source as its own track" is on, each source is also saved as a 16 kHz mono WAV next to the recording, named by the recording's basename plus a per-source suffix, moved, recovered and cleaned up together with the recording's other files. Separate mono files rather than one multichannel WAV (A4). [inferred]
- **Where sources are chosen.** gh-2's "Start with options…" dialog lists the running apps and the input devices to tick, defaulted from Settings → Audio and from the profile chosen in the same dialog. Settings → Audio replaces the single "Microphone" picker and the "No Microphone" switch with a default microphone set and the per-source-track switch; existing installs migrate (R2). The profile spec's `ProfileStore` gains two optional fields, the default microphone set and the per-source-track switch; apps are not a profile field, because they are whatever is running when the meeting starts. [inferred]
- **Automatically detected meetings and "Start now"** record the detected or picked app plus the default microphone set. [inferred]

## Edge Cases & Constraints

- **The two-track assumption (the places a source-aware pipeline would have to change).** In v1 the processing places keep seeing exactly two logical tracks; the capture and storage places change. Processing, unchanged in v1: `SpeakerKey` `R_`/`M_` prefixes (`SpeakerKey.swift:12-47`); `DiarizationProcess.remoteSpeakerLabel`, `mergeDualSourceSegments` and `assignSpeakersDualTrack` (`DiarizationProcess.swift:38,55,274`); `DualTrackViability` (`DualTrackViability.swift:22-44`); `EchoBleedDetector.analyse(app:mic:)` (`EchoBleedDetector.swift:124`), `EchoSegmentClassifier`, `EchoEmbeddingQuarantine` (mic-prefix filter) and LocalVQE cancellation with the app track as reference (`PipelineQueue+EchoCancellation.swift`); `AudioMixer.mix` and `suppressEcho` (`AudioMixer.swift:36,114`); `PipelineJob.mixPath/appPath/micPath/micDelay` (`PipelineJob.swift:70-73`); the naming session's `_app_16k`/`_mic_16k` sidecars and per-track speaker snippets (`SpeakerNamingSession.swift:333-334`, `SpeakerNamingStore.swift:49`). Capture and storage, changed in v1: `RecordingSource`/`CapturedChannels` (`RecordingSource.swift:16-104`); `AudioCaptureConfiguration.micDeviceUID`/`micOutputURL` (one each) and `AudioCaptureSession`'s one app capture plus one mic capture (`AudioCaptureSession.swift:30-33`); `AudioCaptureResult.micDelay` (one pair, `AudioCaptureResult.swift:16`); `RecordingResult` (`DualSourceRecorder.swift:12-21`) and `DualSourceRecorder.start(source:micDeviceUID:debugLogging:)` (`:392`); `RecordingFileSuffix` (`RecordingFileSuffix.swift:5-7`); `RecordingSidecar.Files` (`RecordingSidecar.swift:51-54`); `AudioPersistencePolicy`, `ProcessedRecordingsLedger`, `DualSourceRecorder.recoverCrashedRecordings` and `cleanupTempFiles` (`DualSourceRecorder.swift:130,345`) and the orphan scan (`PipelineQueue+Recovery.swift`); `ChannelHealthMonitor` and `ChannelFaultMonitor` (`ChannelFaultMonitor.swift:9,63`) with the menu-bar per-channel tint; the live-caption sinks (`DualSourceRecorder.swift:381-382`, `LiveTranscriptionController.swift:114,122`). [inferred]
- **Features landing before this one that edit or stop tracks** (gh-54's cut-back of an unanswered auto-stop, gh-46's pause, gh-44/gh-55's microphone restart) apply to every per-source track at the same timeline point; a per-source track is never cut or paused differently from the mix. [inferred]
- **A source that fails.** A microphone or the tap that fails to start, or stops delivering mid-recording, does not end the recording while another source still records; the user is told which source failed (device name, never the device UID, which `CLAUDE.md` "Diagnostics" keeps out of unconditional logs). Only when no source can start does the start fail, as today. [inferred]
- **A chosen device that is absent at start** is skipped and named in the same notice; if no chosen microphone is present and no app is chosen, the system default input is recorded and the notice says so, matching today's single-device fallback (issue #724). The same physical device chosen twice (for example "System Default" and the device it currently is) is recorded once. [inferred]
- **Crosstalk.** Several microphones that hear the same voice colour it in the summed microphone track; the per-source tracks keep each microphone clean. Accepted for v1. [inferred]
- **Live captions** read the first chosen microphone and the app track; a second microphone is not captioned in v1. [inferred]
- **Record-only mode** writes the per-source files and lists them in the sidecar under a new optional field with kind and device name (never the UID), bumping `RecordingSidecar.currentVersion` to 3; every field added after version 1 decodes as optional (`CLAUDE.md` "Record-only mode"). [inferred]
- **Migration and e2e lanes.** `scripts/e2e-browser.sh` and `scripts/e2e-channel-fault.sh` write `noMic` with `defaults write`; the old keys keep their meaning when read until those lanes are moved to the new setting. [inferred]
- **Conflict risk with the original.** The capture library (`tools/audiotap`) and `DualSourceRecorder*.swift` change often upstream (issues #588, #672, #693 in the last weeks); new behaviour goes into new types where it can, and tasks are cut only after the earlier specs land (D1). [inferred]

### Verification

- The alignment arithmetic is a pure type, tested with simulated device clocks at ±100 ppm against the host clock over a simulated 60-minute recording, with a restart gap and a late-starting device: every track stays within 20 ms of every other. [inferred]
- Recorder tests with stand-in capture sessions (the seams `AudioCaptureSession` already has for the app attempt and the mic session factory) cover two microphones plus app, microphones only, app only, a microphone failing at start and mid-recording, an absent device, and a duplicate device; they assert the files written, the per-source padding to one origin, and the notices. [inferred]
- WAV-fixture tests: the summed microphone track and the per-source files of a three-source fixture, the record-only sidecar (version 3 and a version-2 reader), crash recovery and orphan scan with per-source files present, and the relocation into the output folder. [inferred]
- Settings migration tests from `micDeviceUID`/`noMic`, and one ViewInspector wiring test per new control (CLAUDE.md "GUI Testing"). [inferred]
- The owner's acceptance run with real devices (headset, built-in microphone, a Teams call) and a clap test whose per-source tracks are compared numerically for offset at the start and the end. [paraphrase]

## Acceptance Criteria

- **R1:** "Start with options…" lets the user choose any combination of running apps and connected microphones, at least one source, defaulted from Settings → Audio and the chosen profile. Errors: with no source ticked, Start is disabled and the dialog says why. [paraphrase]
- **R2:** Settings → Audio holds the default microphone set (one or more devices, or "System Default") and the switch "Keep each source as its own track" (off by default). An existing install keeps its behaviour: its configured microphone, or System Default, becomes the set, and "No Microphone" becomes an empty set. Errors: no error surface. [paraphrase]
- **R3:** With the switch on, a recording of N sources leaves the usual recording plus one 16 kHz mono WAV per source next to it; all per-source files share one origin, and at the start and the end of the recording any two of them are within 20 ms of each other. Errors: a source that never delivered audio gets no file and the job carries a warning naming it. [paraphrase]
- **R4:** The transcript, speaker attribution and protocol are produced from the app track and the summed microphone track, exactly as for today's two tracks; a recording with only microphones is processed like today's microphone-only recording. Errors: as today when a track has no audio (`DualTrackViability`). [inferred]
- **R5:** A source that fails to start or stops delivering mid-recording leaves the recording running on the others and posts a notice naming it; the start fails only when no source starts. Errors: the notice is posted once per source and recording. [inferred]
- **R6:** Automatically detected meetings and "Start now" record the detected or picked app plus the default microphone set. Errors: no error surface beyond R5. [inferred]
- **R7:** Record-only mode writes the per-source files and lists them in its sidecar with kind and device name; a consumer that reads only the version-2 fields is unaffected. Errors: a per-source write that fails is reported like today's record-only write failure, and the other files are kept. [inferred]
- **R8:** Moving a finished recording into the output folder, crash recovery, the orphan scan, the processed-recordings ledger, and the track edits of gh-54 and gh-46 treat the per-source files as part of their recording. Errors: a per-source file that cannot be moved stays in staging, is reported, and is never picked up as a recording of its own. [inferred]

## Boundaries

- Follow-up: a separate app track per app (one tap per app); in v1 all chosen apps share one tap and one track. [inferred]
- Follow-up: transcribing and diarizing each source on its own (speaker attribution per microphone), which is where the processing places listed under the two-track constraint change. [paraphrase]
- Follow-up: level matching per source before mixing (issue #4) and following the meeting app's microphone (issue #43). [paraphrase]
- Follow-up: live captions for every microphone. [inferred]
- Choosing sources through the automation API (`/v1/record`) is not part of v1. [inferred]
