# Notes made again are kept and show up

## Conversation Evidence

The fork is public, so the owner's turns are paraphrased, not quoted.

> owner (paraphrased, 2026-11-19): in All Recordings, choosing "An additional report" in the regenerate sheet replaced a report the meeting already had; after notes were made again the list did not update; a meeting whose local-model notes stopped for low memory showed no clear state and no next step; the sheet looks broken, with a scrollbar in an unbordered "Background info" area; and no click shows all of a meeting's reports.
> owner (paraphrased, 2026-11-19): took all four recommendations of the All Recordings review. For this spec that means: a low-memory stop names the memory the model needs and the memory that was free, and offers a way to try again; a per-run choice of notes provider is filed for later, not built.
> review (2026-11-19, code reading and renders with made-up meetings; nothing was driven live): most of what looks broken has one cause: "Regenerate Notes" runs beside the job list, not in it, so its result often never reaches the meeting's row. The review split the work into three specs; this is the first, the bug fixes that need no mockup and no decision.

## Goal & Context

<!-- Source: 0% user / 50% [paraphrase] / 50% [inferred] -->

Making a meeting's notes again never loses a report, and its result shows on the meeting's row. After this spec, "An additional report" always adds a file and never replaces or trashes one; notes written later for a meeting without notes appear on its row with "Open Notes"; a local-model stop for low memory or a missing model reads as notes not written, says why with the memory figures, and can be retried from the window and from the menu bar. [paraphrase]

Today the regenerator (`ProtocolRegenerator`) runs outside the pipeline queue. The row knows a meeting's notes only from its job's notes path (`TranscriptionEntry.protocolURL`), and the regenerator's success hooks update the template, the summary and the meeting's file record, but never that path or a recorded notes failure. A local-model stop for low memory or a missing model adds a job warning but records no notes failure (`PipelineQueue.localModelResult`), so the row reads "Done, with warnings", the job leaves the list after 60 s, and only the notification's Try Again leads back. A second additional report from the same template takes the first one's file name and moves the old report to the Trash, which gh-190 assumed on purpose (its A3). [inferred]

Who it is for: everyone who makes notes again or uses the local model. Why now: the owner reported these problems on 2026-11-19 and the review traced each to its cause. This spec comes first; "Writing notes is a visible job" (gh-279: dialog closes at once, progress and Stop on the row) and "A meeting's reports in one place" (gh-280: reports line, Reports submenu, earlier versions) build on it and wait for their mockups. [paraphrase]

Stands on the original: no. It builds on gh-170 (All Recordings) and gh-190 (additional reports), which exist only in the fork. Upstream check (2026-11-19): the original's open issue 873 proposes a separate "Meetings" window with notes and transcript side by side, with no pull request yet; the original has no regenerate sheet and no additional reports. Related fork work: #263 (an open spec that makes a start refused for memory wait and try again by itself; its end state after 24 hours is this spec's "notes not written"), #262 (small gaps around re-runs and notes, among them the template a regeneration records for a meeting that left the queue), #261 (a local-model picker in the regenerate sheet), #197 (additional reports to Notion). [inferred]

## Architecture & Data Models

<!-- Source: 0% user / 20% [paraphrase] / 80% [inferred] -->

- **Report names (R1).** The name rule lives in one pure function beside `MeetingReportFolder`: for template name `T` the candidates are `T`, `T 2`, `T 3`, … and the report takes the first candidate whose file `<meeting> (<candidate>).md` neither exists in the folder (compared without case, as the folder's names are today) nor is given to another meeting by the ownership rule (`MeetingReportFolder.owner(ofFileName:)`). The built-in template's name stays "Standard" (gh-190 A5), so its second report is "Standard 2". `MeetingReportFolder.slot(forReportNamed:)` and the sheet's line under "An additional report" use the same function, so the sheet names the file the run will write. The run picks the name again right before it writes, from the folder as it is then, and writes with a rename that never replaces an existing file; a report run therefore never moves a file aside, never trashes one and never calls the `reportKept` hook. `.previous-<stamp>.md` copies that older builds left stay where they are. [inferred]
- **Notes saved by a regeneration (R2).** When a regeneration writes the main notes of a meeting that has a job, the regenerator's success hook gives the pipeline the job id and the written notes path. The pipeline then, for a job in the queue: sets its notes path, clears its notes failure with the existing `clearNotesFailure(at:)` (which removes the warnings that described the job without notes) plus the two local-model shortfall warnings (`LocalModelNotice.Shortfall.warning`), saves the snapshot and rewrites the job's history record. For a meeting known only from the history (`TerminalJobStore`), it rewrites that record's notes path, warnings unchanged except the same stale ones. Either rewrite keeps the record's place in the history, so a regenerated older meeting does not become "Last Recording" (A5). The row and the menu read the new path at once because both read the queue and the history (`TranscriptionList`). Retry Meeting Notes and a notification's Try Again end in the same state: the first through the queue's own notes save, the second through the regenerator. [inferred]
- **Local-model stops as failed notes (R3).** `PipelineQueue.localModelResult` records a notes failure for `.lowMemory` and `.noModel` as it already does for `.deadline` and `.failure`, keeping today's warnings word for word. The precise kind and the memory figures go into a new optional job field (for example `localModelShortfall`: kind `lowMemory` or `noModel`, needed bytes, free bytes), while `notesFailure` itself stores an existing case (`.other`), so a build without this spec decodes the job unchanged and reads it as a generic notes failure (A2). The needed figure is the one the memory check compared against: the model's weight size plus the start headroom (`LocalModelMemoryGuard.admissionHeadroomBytes`); the free figure is the reading's available memory. The local-model outcome carries both from the gate to the queue. A notes failure keeps the job held in the queue (`isHeldAfterCompletion`), which puts it under "Needs you" in the menu bar and keeps its row until it is retried or dismissed. [inferred]
- **Status of a failed-notes meeting (R3).** `JobMenuSummary` gets one more input, whether the finished job's notes failed, and then reads "Notes not written" instead of "Done, with warnings", for every notes failure, not only local-model stops (A3). The row draws that status in orange. The row's outcome line starts with the failure's sentence (`MeetingNotesFailure.summary`, or the shortfall's sentence with its figures) and then lists the job's other warnings, leaving out the stored warnings that only say the notes were not written. `TranscriptionEntry` carries the failure for a job in the queue; an entry known only from the history has none, as today. [inferred]
- **Retry in the window (R4).** `RecordingRowActions.mainAction` gives a finished job with retryable notes (`TranscriptionEntry.hasRetryableMeetingNotes`) the main button "Retry Meeting Notes", and `menuItems` lists the same item first in the "…" and right-click menus. Both call the menu bar's action (`PipelineQueue.retryMeetingNotes(id:)`), which checks the transcript on the click. [inferred]
- **The sheet and the running run (R5).** The regenerator's running phase names the meeting it is writing for (its job id, else its folder and basename, and its title). The sheet compares that with its own meeting: for another meeting it shows the line of R5 in place of the spinner, disables Generate, and never shows the other run's result; `RegenerateSheetState.present` keeps clearing only a finished result. [inferred]
- **Background info (R6)** is drawn as a bordered text box whose scroll view hides its scroller while the text fits (`autohidesScrollers`), also with the system setting "Show scroll bars: Always". [inferred]
- **Finder (R7).** "Show in Finder" reveals the meeting's notes, transcript and every additional report the row read (`FilesOnDisk.reports`) in one `NSWorkspace.activateFileViewerSelecting` call. "Open Notes Folder" opens `<output folder>/protocols`, where the queue writes notes, and creates it when it is missing, as it creates the output folder today. [inferred]
- **Wording (R8)** lives in the existing label functions (`TranscriptionsView+RowLabels`, `RegenerateProtocolView`). [inferred]

## API Contracts

- No new endpoint and no change to `/v1`. Job warnings keep their stored texts, which `/v1` clients and saved jobs match on. `JobStatusDTO` does not carry the new failure detail. [inferred]
- The job snapshot gains one optional field; the finished-job history and the meeting record keep their formats. A build without this spec ignores the new field and decodes everything else as before. [inferred]

## Edge Cases & Constraints

- **Many reports from one template:** the numbering goes on without a limit ("Short 10" after "Short 9"); the row menu sorts reports with the existing natural order, so "Short 2" comes before "Short 10". A template whose own name ends in a number gets a further number ("Board 2", then "Board 2 2"). [inferred]
- **A report name claimed by another meeting** (a longer meeting name whose transcript is in the folder) is skipped like a taken name, instead of refusing the report as today (A4). [inferred]
- **A name taken during the run** (Finder, another build): the run takes the next free number when it writes and never replaces the file. A folder that cannot be listed at that moment ends the run with today's "could not be saved" message and writes nothing. [inferred]
- **A meeting without notes** still gets its main notes from "An additional report", as today. [inferred]
- **A regeneration that writes an additional report** changes no notes path, failure or status on the row. [inferred]
- **A hand-picked file without a job** ("Regenerate from File…" on a file no listed meeting owns) changes no row. [inferred]
- **A failed snapshot or history write** after a regeneration is logged without content and does not fail the regeneration; the row shows the notes for this session. [inferred]
- **Notifications:** a local-model stop keeps today's notifications: its low-memory or no-model notice with Try Again or Open Settings, and the done notification as today, so one stop never posts a second "Meeting Notes Failed" (A6). [inferred]
- **Memory figures:** decimal GB as Finder counts, one decimal (A7). When the free figure is not below the needed one (the stop came from memory pressure), or a figure could not be read, the sentence names memory pressure and leaves the figures out. [inferred]
- **Retry Meeting Notes on a local-model failure** runs the local model again through the queue; a second stop records the failure again with new figures. [inferred]
- **App Store build:** the local model does not exist there, so R3's shortfall never occurs; R1, R2, R4 to R8 apply to both variants. [inferred]
- **Privacy:** no notes, transcript or background text in a log line, a notification or a test fixture; tests use made-up meetings. [inferred]
- **Docs:** `docs/architecture/pipeline.md` describes additional reports and regeneration; the build updates it where this spec changes the behaviour, in the same commit. [inferred]

## Acceptance Criteria

- **R1:** Saving "An additional report" with a template that already has a report writes `<meeting> (<template> 2).md`, then 3 and so on. Every existing report stays byte for byte, nothing goes to the Trash, and the line under the option names the file the run will write ("Saved as “<file>”. The current notes stay as they are."). The orange "Replaces the existing …" line no longer appears. This supersedes gh-190's A3, and the test that pinned A3 (`ProtocolRegeneratorReportTests`, the same template replacing its report) is changed to expect a second report. Errors: a name taken in the folder (any case) or claimed by another meeting is skipped; a name taken during the run is skipped at write time and no file is ever replaced; a folder that cannot be listed ends the run with today's message and writes nothing; a meeting without notes gets its main notes as today. [paraphrase]
- **R2:** When "Regenerate Notes…", "Regenerate from File…" on a listed meeting's file, a notification's Try Again or Retry Meeting Notes saves notes for a meeting that had none, its row offers "Open Notes" as the main button and in its menus at once. The failure line is gone, the menu bar no longer lists the meeting under "Needs you", and "Last Recording" opens the notes when it shows that meeting. All of this still holds after a relaunch, for a meeting in the queue and for one known only from the history. Errors: the history record keeps its place, so the regenerated meeting does not become "Last Recording"; a failed snapshot or history write is logged and does not fail the regeneration; an additional report and a file without a job change no row. [paraphrase]
- **R3:** A local-model stop for low memory or for a missing model is recorded as failed notes. The row and the menu bar's "Needs you" offer Retry Meeting Notes. The row's status reads "Notes not written" in orange, not "Done, with warnings", and its outcome line gives the reason, for low memory with the needed and free memory ("Not enough free memory for the local model: needs about 22.5 GB, 21.5 GB free"), for a missing model "No local model is chosen, or it cannot be reached". The same status applies to every finished meeting whose notes failed. Errors: the stored warning texts stay unchanged; a build without this spec still decodes a saved job that carries the new detail; a figure that could not be read, or a stop for memory pressure with enough free memory, leaves the figures out and names memory pressure; the notifications stay as today. [paraphrase]
- **R4:** Every finished row whose notes failed offers "Retry Meeting Notes" as its main button and as the first item of its "…" and right-click menus, wherever the menu bar offers it (a job in the queue with a recorded transcript). Errors: a transcript that is gone at the click is reported as the menu bar's Retry Meeting Notes reports it; a meeting known only from the history offers no retry, as in the menu bar. [paraphrase]
- **R5:** The sheet opened for meeting B while A's notes are written shows B without A's spinner or result, with the line "Notes for “A” are being written. You can start these when they are done." and Generate disabled. Once A's run ends, B's sheet enables Generate and still shows nothing of A's result. Errors: a sheet opened for A itself shows the run as today; a sheet opened from "Regenerate from File…" shows the line once its chosen file belongs to another meeting than the running one. [paraphrase]
- **R6:** "Background info" is drawn as a bordered text box. With the system setting "Show scroll bars: Always", no scroller shows while the text fits the box; a longer text scrolls with a scroller. No error surface beyond today's editor. [paraphrase]
- **R7:** "Show in Finder" selects the meeting's notes, transcript and every additional report in one Finder window. "Open Notes Folder" opens the folder the notes are written to (`protocols` in the output folder). Errors: files that are gone are left out, and with none left the row says "The file was moved or deleted." as today; a missing notes folder is created before it opens, as the output folder is today; files in different folders each show in their folder. [paraphrase]
- **R8:** For a meeting without notes, the row item reads "Write Notes…" and the sheet's title "Write Meeting Notes"; a meeting with notes keeps "Regenerate Notes…" and "Regenerate Meeting Notes". The sheet's success line reads "Report “Short 2” saved" for an additional report, "Notes replaced" for replaced notes and "Notes saved" for a meeting's first notes (A8). No error surface beyond today's failure lines. [paraphrase]
- **R9:** Tests at the cheapest layer that can fail: the name rule and the status rule as pure-function unit tests; the regenerator with injected file operations (a second report of one template, a name taken during the run, a claimed name, an unlistable folder, nothing in the Trash); the pipeline's notes-saved step for a job in the queue and one only in the history, with the record's place kept; the local-model results with their figures and a decode test that reads a job with the new detail through the field types a build without this spec has; the row's main button and menu items for every state; the sheet's line for another meeting's run and its success lines (ViewInspector); the Finder selection and the notes folder through the injected actions. Each test fails without its change. [inferred]

## Boundaries

- **"Writing notes is a visible job" (gh-279):** the sheet closing at once after Generate, progress and Stop on the row, a waiting line for a second run, the notification "Report “<name>” saved" with Open, Try Again and Settings… on the row for a failed regeneration, the template the meeting's notes were made with preselected, a run cut off by a quit. [paraphrase]
- **"A meeting's reports in one place" (gh-280):** the reports line on the row, the Reports submenu with earlier versions, "Replace the notes" keeping the old notes as an earlier version (this spec still moves them to the Trash), "Show All in Finder" as a name, at most 10 top-level menu entries. [paraphrase]
- **Later:** choosing the notes provider for one run (filed); waiting and trying again by itself when memory is short (#263). [paraphrase]
- No change to the notes prompt, the templates, the notes files' format, the Notion export or the deletion rules. `CLAUDE.md` and `AGENTS.md` stay unchanged. [inferred]
