## Goal & Context

Whoever downloads a WhisperKit model today depends on whatever Hugging Face token happens to sit on the Mac: an environment variable or a token file left behind by another tool. A stale one breaks downloads of public models with an unexplained "Load Model", and there is no way to give the app a token of its own for a private or gated model. The person setting up the app wants one optional field in Settings that decides this alone: empty means the app asks Hugging Face anonymously, filled means it uses exactly that token, kept in the Keychain, and a refused token is named as such. [paraphrase]

Verified against today's code (wapp/main at 65888b53, WhisperKit 1.1.0, pinned in `Package.resolved`):

- The stale-token fallback from upstream PR #759 is already in wapp/main (commit f2b84eef): `WhisperKitModelSource.downloadRetryingAnonymously` first lets WhisperKit look the machine token up (`token: nil`) and retries once with `""` when the Hub answers 401/403. This spec removes it (D6). [inferred]
- The custom WhisperKit model support (`WhisperKitModelOrigin`, `WhisperKitLocalSnapshot`, `WhisperKitModelSource`) is in wapp/main; the Hub download is `WhisperKit.download(variant:from:token:progressCallback:)` in `WhisperKitModelSource.hub(repoID:)`. [inferred]
- **The issue's assumption about `WhisperKitConfig(modelToken:)` does not hold.** WhisperKit uses `modelToken` only in `setupModels` when no `modelFolder` is given, and this app always passes `modelFolder` to both of its pipe constructions. The tokenizer is fetched in `WhisperKit.loadTokenizerIfNeeded()` → `ModelUtilities.loadTokenizer`, which builds `HubApiWrapper(downloadBase:useBackgroundSession:)` with no token at all, so ArgmaxCore's `HubApi.init` falls back to `hfTokenFromEnv()` (the machine search). Same on WhisperKit's main branch as of 2026-10-06. So the token has to reach the tokenizer another way (see Architecture). [inferred]
- The stock variants in `argmaxinc/whisperkit-coreml` ship no tokenizer (only `config.json` and `generation_config.json` next to the CoreML bundles); WhisperKit fetches `openai/whisper-<size>` on first use into `<download base>/models/openai/whisper-<size>`. A machine with a stale token and no cached tokenizer therefore fails even the stock model's first load today, after the anonymous retry rescued its download. [inferred]
- An empty string really suppresses the lookup: `HubApi.init` does `self.hfToken = hfToken ?? Self.hfTokenFromEnv()` and `httpGet`/`httpHead` send no `Authorization` header for an empty token. HTTP 401 and 403 both surface as `Hub.HubClientError.authorizationRequired`, which `WhisperKitModelSource.isRejectedToken` already recognises by its reflected name. [inferred]
- The Keychain pattern exists: `KeychainHelper` and the Keychain-backed `AppSettings.openAIAPIKey` / `claudeAPIKey`, each with a Keychain account injectable through `AppSettings.init`. The App Store variant already stores `openAIAPIKey` this way inside its sandbox and has `com.apple.security.network.client`; no entitlement change is needed. [inferred]

## Architecture & Data Models

**Token storage (`AppSettings`, new file `AppSettings+HuggingFaceToken.swift` plus stored properties in `AppSettings.swift`).** [inferred]
- `struct HuggingFaceTokenStore` with four closures, `read: () -> String?`, `save: (String) -> Bool`, `delete: () -> Bool`, `exists: () -> Bool`, and `static func keychain(account: String) -> Self` backed by `KeychainHelper` (service = the app's subsystem). `AppSettings.init` takes `huggingFaceTokenStore: HuggingFaceTokenStore = .keychain(account: "huggingFaceToken")`, so tests inject an in-memory or failing store and never touch the real item (same reasoning as the injectable API-key accounts' doc comments).
- `KeychainHelper.save` and `KeychainHelper.delete` gain `@discardableResult` `Bool` results: `save` is true only when the add or the update returned `errSecSuccess`; `delete` is true for `errSecSuccess` or `errSecItemNotFound`. Each failure is logged with the account name and `OSStatus`, never the value. Existing callers ignore the result.
- `var huggingFaceToken: String { get }`: the saved token from the store, `""` when none. This is the one reusable accessor (issue #9 reads it later). Read only where a Hugging Face request is about to be made, never from a view body.
- `var huggingFaceTokenDraft: String` (observable, not persisted): what the user is typing. Lives on `AppSettings`, a reference type, so a ViewInspector test can type into the field and press Save and see the result (CLAUDE.md "GUI Testing", point 2, on `@State` copies).
- `var huggingFaceTokenSaved: Bool` (observable, not persisted, initialised `false`): whether an item exists. Set from `store.exists()` (an attribute-only query) by `refreshHuggingFaceTokenSaved()`, called from the view's `.onAppear` the same way the custom vocabulary validation is refreshed, and after every save and remove.
- `var huggingFaceTokenProblem: String?` (observable, not persisted): "The token could not be saved to the Keychain." after a failed save, "The token could not be removed from the Keychain." after a failed remove; cleared by the next successful save or remove.
- `func saveHuggingFaceTokenDraft()`: trims whitespace and newlines; an empty result changes nothing. Otherwise `store.save`: on success the draft is cleared and the problem cleared; on failure the draft is kept (so the user can retry) and the problem set. Either way `huggingFaceTokenSaved` is refreshed, so a failed replacement still shows the older token as saved and the problem line says the new one was not stored.
- `func removeHuggingFaceToken()`: `store.delete`, clears the draft; on failure sets the problem; refreshes `huggingFaceTokenSaved`.
- Never written to `UserDefaults`, never part of `AppSettings+RPC` / `RPCStateSnapshot` (secrets are excluded there by construction), never logged.

**Settings row (`TranscriptionSettingsView`).** [inferred]
- A new hoisted property (e.g. `huggingFaceTokenRow`) rendered at the end of the view's WhisperKit model-picker group, so it sits next to the model choice, appears for every WhisperKit model (stock and custom) and stays hidden for Parakeet, and the section's direct children keep their positions (existing tests locate some controls by position, and CI enforces a 300 ms body type-check budget).
- Contents: `SecureField("Hugging Face token", text: $settings.huggingFaceTokenDraft, prompt: …)` with `.onSubmit` saving; a "Save" button (disabled while the trimmed draft is empty); a "Remove" button (shown only while `huggingFaceTokenSaved`); one caption line: saved → "A token is saved. WhisperKit models download with it."; not saved → "Optional, for private or gated models. Without a token, models download anonymously; tokens elsewhere on this Mac are not used."; plus, when `huggingFaceTokenProblem` is set, that message as a second caption line.
- New `A11yID` constants: `huggingFaceTokenField`, `huggingFaceTokenSaveButton`, `huggingFaceTokenRemoveButton`. Not added to the `/ui/press` allowlist.

**Token routing in the engine (`WhisperKitEngine`, `WhisperKitModelSource`, `EngineController`).** [inferred]
- `WhisperKitEngine` gains `var hubToken: @MainActor () -> String = { "" }`. The default is anonymous, so an engine built in a test never reads the Keychain. `EngineController.init` sets it to `{ [settings] in settings.huggingFaceToken }`.
- `modelSource` changes from `(WhisperKitModelOrigin) -> WhisperKitModelSource` to `(WhisperKitModelOrigin, @escaping @MainActor () -> String) -> WhisperKitModelSource`, default `WhisperKitModelSource.production(for:hubToken:)`; `performLoad` passes `hubToken`. `production(for:hubToken:)` defaults `hubToken` to `{ "" }` (anonymous), so its existing direct callers in tests keep compiling and stay anonymous. The two `installModelSourceForTesting` overloads keep their signatures and ignore the provider. The production source calls the provider only immediately before a Hub request (download, tokenizer fetch), so a test source never triggers a Keychain read.
- `hub(repoID:)` download passes `token: hubToken()` straight to `WhisperKit.download`; `downloadRetryingAnonymously` and its tests are removed (D6). `isRejectedToken` stays.
- **Tokenizer.** Both `makePipe` closures build a new `final class HubTokenScopedWhisperKit: WhisperKit` instead of `WhisperKit`. Its designated `init(_ config: WhisperKitConfig, hubToken: String, mayFetchTokenizer: Bool) async throws` stores both, then calls `super.init(config)`; Hub origins pass `mayFetchTokenizer: true`, a picked folder `false`. It overrides `open func loadTokenizerIfNeeded()` so that `super.loadTokenizerIfNeeded()` is reached only when WhisperKit's local branch is certain to succeed, because WhisperKit's local branch swallows any load error and falls back to its own Hub fetch with the machine token:
  1. When `tokenizer != nil`, or `textDecoder.logitsSize` / `audioEncoder.embedSize` is unknown, call super unchanged (nothing to fetch; super then throws its own "tokenizer unavailable" error without a request).
  2. Otherwise work out the tokenizer repository and the folder WhisperKit will pick: the first of the four search paths holding `tokenizer.json`.
  3. Trial-load that folder with the public `AutoTokenizerWrapper.from(modelFolder:hubApi:)`, the same call WhisperKit's local branch makes on the same folder (its `WhisperTokenizerWrapper` wrapping does not throw). A passing trial calls super.
  4. No folder found, or the trial threw: with `mayFetchTokenizer`, fetch `config.json`, `tokenizer_config.json` and `tokenizer.json` with `HubApiWrapper(downloadBase: tokenizerFolder, hfToken: hubToken).snapshot(from:matching:)` into the first search path (overwriting a broken copy there), trial-load it, and call super only if that passes; without `mayFetchTokenizer`, throw `WhisperKitModelError.folderNotLoadable`.
  5. Any fetch or trial error after step 4 is rethrown. WhisperKit's own fetch is never reached.
- The pure parts live in a small value type (e.g. `WhisperTokenizerCache`), each mirroring one WhisperKit-internal piece of knowledge and pinned by a test:
  - `repository(logitsDim:encoderDim:) -> String`: `"openai/whisper-" + <size>`, mirroring `ModelUtilities.detectVariant(logitsDim:encoderDim:)` followed by `ModelUtilities.tokenizerNameForVariant(_:)`, including the `.base` / `.baseEn` defaults for unrecognised sizes. Both functions are `internal` to WhisperKit, so the test reaches them with `@testable import WhisperKit` (the existing `WhisperKitHubTokenTests` already uses `@testable import ArgmaxCore` the same way) and compares over a grid of dimensions.
  - `searchPaths(repository:modelFolder:tokenizerFolder:) -> [URL]`: the four places `loadTokenizerIfNeeded` / `ModelUtilities.loadTokenizer` look for `tokenizer.json`, in their order: `HubApiWrapper(downloadBase: tokenizerFolder).localRepoLocation(repo)`, `tokenizerFolder` itself when set, `modelFolder`, `HubApiWrapper(downloadBase: modelFolder).localRepoLocation(repo)`.
  - `ensureLoadable(...)`: steps 2 to 5 above, with the fetch and the trial load injectable (closures), so every branch (found and loadable, found but broken, absent, fetch not allowed, fetch failing, fetched copy still broken) is unit-tested without the network.

**Refused-token message (`WhisperKitLoadFailure`, engine, view).** [inferred]
- `enum WhisperKitLoadFailure: LocalizedError, Equatable { case tokenRejected, tokenRequired }` with a `message` used as `errorDescription`, and `static func classify(_ error: any Error, tokenSent: Bool) -> WhisperKitLoadFailure?` returning `.tokenRejected` / `.tokenRequired` for a refused request depending on `tokenSent`, and `nil` for anything else. `isRejectedToken` moves from `WhisperKitModelSource` onto this type, so the dependency points one way (source → failure).
- The production Hub steps (variant download, and both pipe constructions where the tokenizer fetch runs) go through one shared helper that runs the step, classifies a thrown error with `tokenSent: !token.isEmpty`, and rethrows the `WhisperKitLoadFailure` when one applies, otherwise the original error.
- `WhisperKitEngine` gains `private(set) var lastLoadFailure: WhisperKitLoadFailure?`: cleared when `performLoad` starts and when `applyModelVariant` changes the selection, set in `performLoad`'s download catch from `error as? WhisperKitLoadFailure`. `ensureModel` throws `lastLoadFailure ?? TranscriptionError.modelNotLoaded`, so a pipeline job's error text (the thrown error's `localizedDescription`) carries the message.
- Exact messages: `.tokenRejected` → "Hugging Face rejected the saved token. Check that it is valid and has access to this model, or remove it to download anonymously." `.tokenRequired` → "Hugging Face refused access without a token. The model may be private or gated (save a token under Hugging Face token), or its name may be wrong."
- The Settings engine status area, `.unloaded` case: below "Load Model", when the WhisperKit engine is active and `lastLoadFailure` is set, a caption line with its message (identifier `A11yID.whisperKitLoadFailureMessage`).

## Edge Cases & Constraints

- **Already on disk.** A model or tokenizer already on disk loads without any Hub request, token or not (local-first, issue #736, `WhisperKitLocalSnapshot`). Removing the token therefore does not stop an already downloaded private model from loading; it governs only the next download. [inferred]
- **Local copy fails, download refused.** When the local snapshot fails to load (e.g. its tokenizer fetch is refused) the engine falls back to the download as today, which hits the Hub with the same token and reports the refusal. [inferred]
- **Picked model folder.** It must carry its tokenizer (`WhisperKitLocalSnapshot.checkModelFolder`), so the override finds it locally and makes no request; the token is irrelevant there. If that tokenizer cannot be loaded, the load fails with `folderNotLoadable` instead of fetching one. [inferred]
- **Broken or incomplete local tokenizer.** A `tokenizer.json` that does not parse, or a cache missing `tokenizer_config.json`, fails the trial load; a Hub origin then fetches a fresh copy with the app's token, a picked folder fails. WhisperKit's own fetch with the machine token is never reached. [inferred]
- **Token change mid-load or with a model loaded.** A load reads the token at each Hub request; a model already loaded stays loaded when the token is saved or removed. The failure line reflects the last load attempt and clears when the next one starts or the model selection changes. [inferred]
- **Whitespace.** A pasted token with a trailing newline is trimmed on save, so it is not refused for a stray character. [inferred]
- **Keychain in tests.** No view body and no engine default reads the token's data: the field is write-only and the engine's default provider is anonymous. Rendering `TranscriptionSettingsView` in a ViewInspector test (which uses the production Keychain account, `AppSettings(defaults:)`) therefore never triggers the Keychain authorization prompt that blocks `swift test` (reason in the doc comment on `AppSettings`'s injectable API-key account). Tests that save or read the token inject a `HuggingFaceTokenStore` (in memory, failing, or `.keychain` on a unique account deleted in `tearDown`). [inferred]
- **No secret in logs or automation.** The token never appears in `os_log` output, `/state`, `/v1` responses, the RPC settings snapshot or a thrown error's text. [inferred]
- **App Store variant.** Keychain and network entitlements are already present (`Entitlements/AppStore.entitlements`); no `#if APPSTORE` branch. [inferred]
- **Behaviour change for the PR body (D5).** A token supplied through `HF_TOKEN`, `HUGGING_FACE_HUB_TOKEN`, `HF_TOKEN_PATH`, `$HF_HOME/token`, `~/.cache/huggingface/token` or `~/.huggingface/token` is no longer used for WhisperKit downloads; such users save it in the new field instead. The PR body must say this. [paraphrase]
- **Merge into the installed app (land stage).** `feat/custom-whisperkit-model` (head of upstream PR #759, listed in `branches.txt` on `tools`) carries its own copy of the fallback (commit 25fff68f, a different SHA than f2b84eef in wapp/main). Removing the fallback edits the same lines of `WhisperKitModelSource.swift`, so `mt-update`'s merge of that branch will conflict after this PR lands. Before merging, simulate the mt-update merge sequence and put the resolution to the owner (see the fork's memory note on mt-update conflicts). [inferred]
- **Do not edit `CLAUDE.md` / `AGENTS.md`** (fork rule). The CLAUDE.md sentence that WhisperKit fetches the tokenizer from the Hub becomes slightly stale; list it as a follow-up in the done summary. [inferred]

## Acceptance Criteria

- **R1:** With WhisperKit selected, Settings → Transcription (the issue's "Transcribe") shows next to the "Model" picker an optional "Hugging Face token" secure field with Save and Remove and a caption that says whether a token is saved; with Parakeet selected the row is not shown. The field never displays a saved token. Errors: a failed Keychain write keeps the typed token in the field and shows "The token could not be saved to the Keychain."; a failed removal shows "The token could not be removed from the Keychain."; the saved/not-saved caption always reflects what the Keychain holds after the attempt. [paraphrase]
- **R2:** A saved token is stored only in the Keychain (generic password, the app's service, account `huggingFaceToken`), trimmed of surrounding whitespace and newlines; it never appears in UserDefaults, logs, `/state`, `/v1` responses or error texts. Save is unavailable for an empty or whitespace-only entry, and Remove deletes the Keychain item. Errors: a failed Keychain write or delete is logged with its status and without the token, and is shown as in R1. [paraphrase]
- **R3:** With no token saved, every Hugging Face request the WhisperKit path makes (variant download and tokenizer fetch) carries no token, whatever `HF_TOKEN`, `HUGGING_FACE_HUB_TOKEN`, `HF_TOKEN_PATH`, `$HF_HOME/token`, `~/.cache/huggingface/token` or `~/.huggingface/token` hold; a public model therefore downloads and loads with a stale token in `~/.cache/huggingface/token`. Errors: a request refused without a token is reported as in R5. [paraphrase]
- **R4:** With a token saved, every such request carries exactly that token, and nothing retries the request without it when Hugging Face refuses it (the stale-token fallback is gone). Errors: a refused token is reported as in R5. [paraphrase]
- **R5:** When a model load fails because Hugging Face refused the request (HTTP 401 or 403), Settings shows under "Load Model" "Hugging Face rejected the saved token. …" if a token was sent, or "Hugging Face refused access without a token. …" if none was, and a transcription job failing for that reason carries the same message as its error. Errors: any other load failure keeps today's behaviour (no line, job error "WhisperKit model not loaded"); the line clears when the next load starts or the model selection changes. [paraphrase]
- **R6:** A model and tokenizer already on disk keep loading without any Hugging Face request, with or without a token (issue #736 unchanged), and a picked model folder never contacts the Hub. Errors: none beyond today's local-load fallback to the download. [inferred]
