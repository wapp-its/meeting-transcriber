## Goal & Context

Today the custom vocabulary (one term per line; names, units, abbreviations) comes only from a file on the user's own Mac, chosen in Settings → Transcription. Both engines use it: Parakeet boosts the terms during decoding, WhisperKit uses them as an optional prompt hint. In an organisation one office should maintain the list centrally, and every installation should pick up the same, current list without anyone copying files around. [paraphrase]

This spec lets the vocabulary come from a web address instead of a local file, for example the raw address of a text file in a GitHub or GitLab repository. The app downloads it at launch and periodically, transfers it again only when it changed, keeps the last good copy for offline use, can send an access token for private repositories, and shows in Settings where the list comes from, when it was last updated and whether the last attempt failed. [paraphrase]

Verified against today's code (wapp/main 65888b53): the local file is stored as a path plus a security-scoped bookmark (`AppSettings.customVocabularyPath` / `customVocabularyBookmark`), validated with fixed limits (`WhisperVocabularyPrompt.maximumFileBytes` 256 KB, `maximumTermCount` 256, `maximumTermBytes` 512), and pushed to both engines by `EngineController.syncEngineSettings()`. Both engines already re-read a file whose content changed at the same path before the next decode, because the file revision (inode, modification time, size) is part of their cache key (`ParakeetVocabularyConfiguration`, `WhisperVocabularyPrompt.CacheKey`). The App Store variant already holds the outbound-network entitlement (`com.apple.security.network.client`), and `KeychainHelper` already stores the OpenAI and Claude API keys. [inferred]

## Architecture & Data Models

- **Source choice, one at a time.** A new setting `vocabularySource` (`.file` default, `.url`) persisted in UserDefaults. With `.url`, the engines get the downloaded copy and the local file selection is kept but not used; nothing is merged and there is no silent fallback to the local file (D-A1). [inferred]
- **One effective vocabulary for the engines.** `AppSettings` gains `effectiveVocabularyPath` / `effectiveVocabularyBookmark`: the local path and bookmark for `.file`, for `.url` the path of the cached copy keyed by the currently configured address (empty when the address is invalid) and no bookmark. `EngineController.syncEngineSettings()` and its observer switch to these and also observe `vocabularySource` and `remoteVocabularyURL`. The engines themselves do not change: for one address the path is stable, and replacing its content atomically gives a new file revision, which both engines already pick up before their next decode. Because the path is derived from the address, a copy fetched for another address can never be read, whatever happens to deletions. [inferred]
- **Remote settings.** `remoteVocabularyURL` (String, UserDefaults; trimmed when used), and an access token read and written through `KeychainHelper` under an injectable account (pattern: `openAIAPIKey`, whose Keychain account is injected through `AppSettings.init`). An in-memory, observable `remoteVocabularyTokenRevision` counter is bumped by the token setter so a token change can be observed (the Keychain itself is not observable). Plain UserDefaults keys keep the source and URL presettable by a configuration profile later (#11); the token is per person. [inferred]
- **Cache.** One copy per address in `AppPaths.remoteVocabularyCacheDirectory` (`<dataDir>/vocabulary/`), named `remote-vocabulary-<bundle identifier>-<first 16 hex digits of the SHA-256 of the trimmed address>.txt`, plus a JSON sidecar with the same stem (`.json`) holding the source URL, the SHA-256 of the text it describes, ETag, Last-Modified, `updatedAt` (content last changed) and `checkedAt` (server last reached). The term count is derived from the cached text when it is loaded, never stored. Named per bundle identifier because the dev and release builds share `dataDir` (same reason as `AppPaths.livenessMarker`). Only the current address's copy is kept: copies of this bundle for other addresses are deleted when the address changes and at start; a deletion that fails leaves an unread file behind and is logged. The directory is injected into `AppSettings` (like `defaultOutputDir`) so tests never touch the real folder. Storing a new copy is a three-step commit: write the new text to a temporary file in the same directory, write the new sidecar atomically, then rename the temporary file over the text file. A failure before the rename leaves the previous text in place and is reported as "could not save" (the previous copy is then truly the one in use); a failure of the rename leaves the previous text under a sidecar that no longer matches it. **The sidecar's validators and dates are trusted only when its address and text hash match the text on disk**: on any mismatch (a failed or interrupted commit, a hand edit) the text, if present and valid, stays in use as this address's copy, its update time falls back to the file's modification date, the stale sidecar is deleted, and the next check sends no validators, so a full download repairs the pair and a 304 can never pin mismatched text. A missing or invalid text file deletes the pair. [inferred]
- **Fetcher.** A `RemoteVocabularyFetching` protocol (pattern: `UpdateProviding`) with a URLSession-backed implementation: one GET, `If-None-Match` / `If-Modified-Since` from the sidecar only when a usable copy exists, `Authorization: Bearer <token>` when a token is set, a 30 s idle timeout plus a 60 s total deadline for the whole check (a request timeout only bounds inactivity, so a server trickling bytes would otherwise hold the check open indefinitely; on the deadline the transfer is cancelled and the check fails as timed out), no URL cache (`urlCache = nil`, `.reloadIgnoringLocalCacheData`, so a 304 reaches our code instead of being answered from Foundation's cache). It returns modified (bytes + validators), not modified, or a failure reason. [inferred]
- **Controller.** `RemoteVocabularyController` (`@MainActor @Observable`, owned by `AppState` as `remoteVocabulary`, started from the menu-bar `.task` next to `updateChecker.startPeriodicChecks`). It runs one check at launch, one 2 s after the source, URL or token last changed, one on "Update now", and one every 60 minutes, only while the source is `.url` and the address is valid. It validates a downloaded body with the same rules as the local file, adopts it into the cache only when it is valid and differs from the cached text, and publishes a `RemoteVocabularyStatus` for Settings. Every change of source, URL or token starts a new generation; a result from an older generation is discarded. [inferred]
- **Settings UI.** In Settings → Transcription, a "Vocabulary source" picker (Local file / URL). Local file shows today's file row and its validation line. URL shows an address field, a secure token field, an "Update now" button and a status line. The new controls live in their own `View` struct, not in `TranscriptionSettingsView`'s section body, which sits near the 300 ms type-check limit (spec gh-17). [inferred]
- **What leaves the machine.** Only the GET to the configured address, with the optional token header. No meeting data, no terms, no device identifiers. [paraphrase]

## Edge Cases & Constraints

- Address empty, not `https://`, or without a host: nothing is fetched, Settings says what is wrong, and no vocabulary is used while the source is URL. [inferred]
- The address changes (typed, pasted, cleared): the engines switch at once to the new address's copy (none yet, so no vocabulary until the first successful check), the previous address's copy is deleted, and a download still in flight for the previous address is cancelled or its result discarded. Terms from one address are never used for another. [inferred]
- Switching the source to Local file and back to URL with the same address keeps the copy. [inferred]
- The server ignores the conditional headers and answers 200 with identical text: the cache file is not rewritten (no needless re-preparation in the engines), only `checkedAt` and the validators are updated. [inferred]
- The server sends neither ETag nor Last-Modified: every check downloads the whole file (at most 256 KB). [inferred]
- A 304 arrives although no validators were sent (no usable copy): treated as a failed check. [inferred]
- A body larger than 256 KB is not held in memory beyond 256 KB + 1 byte: the download is aborted and reported as too large. [inferred]
- A body that is not UTF-8, has no terms, more than 256 unique terms or a term over 512 bytes is not adopted; the previous copy stays and Settings names the reason (same limits and wording as the local file). [inferred]
- A response with `Content-Type: text/html` (a sign-in page after a redirect, an error page served with 200) is rejected as "not a text file". [inferred]
- With a token set, a redirect to another host is not followed (the token must never reach a host the user did not name); any redirect to a non-https address is not followed. Both are reported as failed checks. [inferred]
- A token pasted with surrounding whitespace or a trailing newline is trimmed before it is sent. [inferred]
- A server that keeps a response open by trickling bytes is cut off at the 60 s total deadline and reported as timed out; "Update now" becomes available again. [inferred]
- Network down, DNS failure, idle timeout: reported as offline; HTTP 401/403 as access denied (check the token); 404 as not found; other statuses with their code. In every failure case the last good copy stays in use, also across a restart. [paraphrase]
- No copy yet and the check fails: no vocabulary is used, and Settings says so. [inferred]
- The text file is missing or no longer valid: the pair is deleted and the next check downloads afresh. The sidecar is missing, corrupt, names another address or describes other text: the text stays in use, the sidecar is deleted and the next check sends no validators (spec § Architecture "Cache"). [inferred]
- Writing the cache fails (disk full, permissions) before the final rename: the previous copy stays in use unchanged and Settings reports that the download could not be saved. The rename itself fails: the previous text stays in use and the mismatch rule repairs it on the next check. The status never claims one copy while the engines read another. [inferred]
- A copy replaced while a job is transcribing affects only the next engine call; a dual-source job can get the old list on one track and the new one on the other. Accepted: rare and harmless. [inferred]
- The Mac sleeps through a scheduled check: the overdue check runs after wake; if the network is not up yet, the status shows offline until the next check or "Update now". [inferred]
- App Store variant: the cache lives inside the sandbox container (`dataDir` resolves there), the outbound-network entitlement is already present, the Keychain works as for the OpenAI key. No `#if APPSTORE` is needed. [inferred]
- Dev and release builds on one Mac keep separate copies (per-bundle file name) and separate settings (UserDefaults are per bundle identifier). [inferred]
- Privacy: the log gets one line per check with the outcome and HTTP status; the host is logged with `privacy: .private`; never the path or query of the address, the token, or any term. The token is stored only in the Keychain: never in UserDefaults, the sidecar, logs or `/state`. [inferred]
- Record-only mode dims the Transcription section as today; checks still run, harmlessly. [inferred]
- This fork does not edit `CLAUDE.md` or `AGENTS.md` (fork rule); rationale goes into the doc comments of the new types. [inferred]

## Acceptance Criteria

- **R1:** Settings → Transcription has a "Vocabulary source" picker with "Local file" (default, also for existing installations) and "URL". With "Local file", everything behaves exactly as today. With "URL", both engines use only the downloaded copy; the local file selection is kept for switching back and is not used. Errors: with "URL" and no usable copy, the engines run without vocabulary rather than falling back to the local file. [paraphrase]
- **R2:** With source "URL" and a valid `https://` address, the app checks the address at launch, about 2 s after the source, address or token was last changed, when the user presses "Update now", and every 60 minutes while running. Each check after the first sends the ETag / Last-Modified validators of the last successful response for that address; a 304 keeps the copy and only records the check time. Errors: an address that is empty, not `https://` or without a host is never fetched, and Settings says what is wrong. [paraphrase]
- **R3:** A downloaded file is adopted only when it passes the same limits as the local file (UTF-8, at most 256 KB, 1 to 256 unique terms, each at most 512 bytes) and is not served as `text/html`; it then replaces the cached copy atomically, and the next transcription with either engine uses the new terms without a restart. A body identical to the cached copy is not rewritten. Errors: a file that fails these checks is not adopted, the previous copy stays in use, and Settings shows the reason. [paraphrase]
- **R4:** When a check fails (no network, timeout, HTTP error, refused redirect, invalid content, the copy cannot be saved), the last good copy for the same address stays in use, also after a restart, and Settings shows the failure next to the date of the copy in use, for example "No connection to the server · using the copy from 6 Oct 2026, 14:02 (128 terms)". Errors: with no copy yet, Settings says no vocabulary is in use. [paraphrase]
- **R5:** An optional access token can be entered in a secure field; it is stored only in the Keychain (clearing the field deletes the item), sent only as `Authorization: Bearer <token>` over https, and never written to UserDefaults, the cache sidecar, logs or `/state`. With a token set, a redirect to another host is not followed. The help text names the address forms that work: a GitHub `raw.githubusercontent.com` address with a GitHub token, and the GitLab API raw-file address (`https://<host>/api/v4/projects/<id or URL-encoded path>/repository/files/<URL-encoded file path>/raw?ref=<branch>`) with a GitLab token. Errors: HTTP 401/403 shows "Access denied (HTTP <code>) – check the access token"; a refused redirect shows that the address points to another server. [paraphrase]
- **R6:** The copy the engines use always belongs to the address currently configured: copies are kept per address, the engines read only the current address's copy, copies for other addresses are deleted when the address changes, and the result of a check started for a previous address, source or token is discarded. Errors: a copy that cannot be deleted is logged and stays unread. [inferred]
- **R7:** With source "URL", Settings shows the address, the term count of the copy in use, when its content last changed ("updated"), when the server was last reached ("checked"), and an offline or failure note when the last check failed; "Update now" is disabled while a check runs. Errors: no error surface beyond R2–R5. [paraphrase]
- **R8:** The only network traffic this feature causes is the GET to the configured address; each check writes one log line with its outcome and HTTP status, with the host marked private and without the address path or query, the token or any term. Errors: no error surface beyond the log write itself. [paraphrase]

## Boundaries

- Terminology rules (`terminologyRulesText`) and protocol templates (#2) from a URL are a follow-up; the issue names them as later. [paraphrase]
- Merging the central list with a personal local file is a follow-up (D-A1); only one source is active at a time. [inferred]
- Locking the source and address through a configuration profile is #11's job; this spec only keeps both as plain UserDefaults keys so a profile can preset them. Tokens from a profile are out. [paraphrase]
- No per-profile vocabulary (#6), no notification or menu-bar indicator for a failing check, no `/state` or automation-API fields for the remote source: follow-ups if needed. [inferred]
- No retry schedule beyond the 60-minute cadence and "Update now" (for example a quick retry after a failure, or on network return or wake): follow-up. [inferred]
- No `PRIVATE-TOKEN` header and no GitLab `/-/raw/` web address for private projects; the API raw-file address covers private GitLab files. Follow-up if an organisation server rejects Bearer tokens. [inferred]
- The vocabulary limits (256 KB, 256 terms, 512 bytes per term) stay as they are for both sources. [inferred]
- No change to the engines' vocabulary handling (`ParakeetEngine`, `WhisperKitEngine`, `WhisperVocabularyPrompt`). [inferred]

### docs-scout
- **GitLab REST API** — a personal access token is accepted as `PRIVATE-TOKEN` or as `Authorization: Bearer <token>`; the raw-file endpoint is `GET /projects/:id/repository/files/:file_path/raw?ref=<branch>` with the project id or URL-encoded path and a URL-encoded file path; no ETag is documented for it, so full downloads must work. Source: https://docs.gitlab.com/api/rest/authentication/ and https://docs.gitlab.com/api/repository_files/
- **GitHub raw content** — `raw.githubusercontent.com` serves private files with `Authorization: Bearer <token>` (or `token <token>`); a fine-grained token needs Contents read access; the API alternative is `api.github.com/repos/<owner>/<repo>/contents/<path>?ref=<branch>` with `Accept: application/vnd.github.raw`. Source: https://github.com/orgs/community/discussions/53637
- **URLSession redirects** — a task delegate's `willPerformHTTPRedirection` that completes with nil cancels the redirect and delivers the 3xx response as the task's result; the async `data(for:delegate:)` / `bytes(for:delegate:)` calls accept a task-specific delegate. Source: https://developer.apple.com/documentation/foundation/urlsessiontaskdelegate

### practice-scout
- **Gotcha:** with a URL cache in place, URLSession may revalidate on its own and hand back a cached 200 for a 304, so the conditional request is invisible; give the fetcher its own session with `urlCache = nil` and `.reloadIgnoringLocalCacheData`, and send `If-None-Match` / `If-Modified-Since` yourself. Source: https://developer.apple.com/documentation/foundation/nsurlrequest/cachepolicy
- **Gotcha:** an access token in the URL query (`?private_token=`) would land in UserDefaults and could reach logs; keep tokens in the secure field and log only the host, marked private. Source: https://docs.gitlab.com/api/rest/authentication/
- **Gotcha:** a private GitLab `/-/raw/` web address without a session redirects to the sign-in page and answers 200 with HTML, which would pass a naive one-term-per-line parse; reject `text/html`. Source: https://docs.gitlab.com/api/repository_files/
