## Goal & Context

Every transcription job today is a line in the menu-bar menu. Failed jobs stay there until dismissed, so the menu grows; finished jobs vanish from it 60 seconds after they complete, so an older protocol can only be found by browsing the output folder. The person wants one window that lists every transcription, finds one by title or participant, and handles failed ones, while the menu stays short. [paraphrase]

What persists today, verified against the code on `wapp/main` (65888b53): [inferred]
- `PipelineQueue.jobs` (`PipelineQueue.swift:36`) holds waiting, running, naming-pending, failed and, for `completedJobLifetime` (60 s, `PipelineQueue.swift:658-663`), done jobs. It is written to the pipeline snapshot (`PipelineSnapshot.swift`, `pipeline_queue.json`). The restore drops done jobs and jobs whose audio is missing (`PipelineQueue+Recovery.swift:74-165, 260-283`) and keeps failed and naming-pending ones.
- The snapshot is only read when a wired queue is first built (`PipelineController.makeQueue`, `PipelineController.swift:247-294`), i.e. on watch start, a file import or a manual recording (`WatchingController.swift:236, 459`). At launch the controller holds a bare queue (`PipelineController.swift:112`) and `autoWatch` defaults to off (`AppSettings.swift:656`), so after a restart the menu shows no failed job until one of those happens.
- `TerminalJobStore` (`TerminalJobStore.swift`, `terminal_jobs.json`, owner-only, FIFO cap 200) keeps one `JobStatusDTO` per finished (done or failed) job across reaping and restarts, written at the terminal transition (`PipelineQueue.swift:654-671`). It lacks app, dates, duration and participants. Its element type is also the `/v1/jobs/<id>` wire shape (`JobStatusDTO.swift:3-41`).
- `ProcessedRecordingsLedger` holds audio paths only. The output folders hold `<yyyyMMdd_HHmm>_<slug>.md/.txt` files (`ProtocolGenerator.swift:243-260`): no app, no status, no duration, a lossy title, and only for jobs that produced a file, in whatever folder was current at the time.
- No job field holds the recording's length: `jobAudioSeconds` is in-memory only and is the last segment's end, not the audio length (`PipelineQueue+Stages.swift:494-497`).

So the finished-job store is the only existing store that can answer "every finished job, after a restart"; it needs four more fields, and the job needs a measured duration. The output folders cannot answer app, status or duration, and scanning them would be a slow, lossy second source. [inferred]

## Architecture & Data Models

- **History record.** A new `TerminalJobRecord` (new file `Sources/TerminalJobRecord.swift`) becomes `TerminalJobStore`'s element. It encodes flat: every `JobStatusDTO` key plus optional `appName`, `meetingStartTime`, `enqueuedAt`, `audioDuration` (seconds) and `participants`, following the flattening pattern of `JobStatusResponse` (`DebugRPCServer+V1.swift:9-31`, which is `#if !APPSTORE`; the new type is not). Missing keys decode as nil (participants as `[]`), so `terminal_jobs.json` files written before this change load unchanged, and an older build reading a newer file ignores the extra keys. `TerminalJobStore.lookup(jobID:)` keeps returning `JobStatusDTO`, so the `/v1` wire shape does not change and participants never reach the API through this change. [inferred]
- **Store.** `TerminalJobStore` becomes `@Observable` (records observed by the window and the menu; `path`/`cap` ignored), its default cap rises from 200 to 1000, and `PipelineQueue.recordTerminalJob` (`PipelineQueue.swift:669-671`) writes a full `TerminalJobRecord(job:)`. Atomic owner-only writes stay as they are. [inferred]
- **Duration.** `PipelineJob` gains `var audioDuration: TimeInterval?` (optional, so older snapshots decode). Stage 1 sets it once the 16 kHz audio exists: single source from the resampled mix before VAD trimming, dual source as the longer of the two resampled tracks, frames / `AudioConstants.targetSampleRate`, through a queue method shaped like `recordEchoVerdict` (`PipelineQueue.swift:751-754`). Zero frames leave it nil. `prepareForRetry` leaves it alone (same audio). [inferred]
- **One list, two views.** A pure `TranscriptionList` (new file `Sources/TranscriptionList.swift`) turns the live jobs plus the history records into `[TranscriptionEntry]` (id, title, app, date, enqueue time, duration, participants, `JobState`, error, warnings, protocol and transcript URL, whether the job is live). A job present in both sources appears once, from the live job. Order: newest first by enqueue time; entries without one (history written before this change) after all dated ones, newest stored first. Each finished entry also carries its finish order: the position of its record in the history, which the store appends to (or moves to the end) at every terminal transition, so it is the order jobs finished in; a finished live job with no record (a failed job whose record the history cap evicted) ranks below every recorded one. It also filters by a query and selects the menu's subset: every unfinished entry plus the 3 latest by finish order, shown in the order the jobs were added. `JobMenuSummary` gains overloads on `(JobState, hasWarnings)` so the window, the menu and history entries share one status wording. [inferred]
- **Controller actions.** `PipelineController` (new file `Sources/PipelineController+Transcriptions.swift`) exposes the merged entries, `removeFailedJob(id:)` (start the pipeline if it is not yet, remove the live job through `PipelineQueue.removeJob`, which marks its audio processed, then drop its history record) and a window-opening hook that starts the pipeline the way a file import does (`ensureQueue`, `PipelineController.swift:239-242`), so failed jobs restored from the snapshot are live and retryable while the window is open. Retry stays `PipelineQueue.retryJob`/`canRetryJob` (`PipelineQueue+Recovery.swift:363-395`). [inferred]
- **Window.** A new `Window("Transcriptions", id: "transcriptions")` scene in `MeetingTranscriberApp.swift`, declared as its own property like the other scenes (`MeetingTranscriberApp.swift:111-129`), showing a new `TranscriptionsView` (new file) that receives its data and actions as stored properties, the way `SettingsView` does: entries, a query binding, a can-retry check and open, reveal, retry and remove closures. Open and reveal go through one small file opener that runs inside the current output folder's security scope, as `openProtocolsFolder` does (`MeetingTranscriberApp.swift:401-407`), and reports a missing file instead of failing silently. [inferred]
- **Menu.** `MenuBarView.processingQueue` (`MenuBarView.swift:177-188`) renders `TranscriptionList`'s menu subset instead of every queue job, keeps one submenu per job (`MenuBarView.swift:248-286`), and gains an "All Transcriptions..." item. Its Open goes through the same scoped file opener as the window, because a history line can be opened right after launch, before any queue holds the output folder's scope. [paraphrase]

## Edge Cases & Constraints

- A done job is live for 60 s and in the history from its terminal transition on; a failed job is live until removed and in the history from its first failure. Both appear once (R2). [inferred]
- Retry removes the history record (`PipelineQueue+Recovery.swift:371`); the retried job is listed from the queue at its original position, since its enqueue time does not change. A retried job that is then cancelled leaves the list, as a cancelled job does today. [inferred]
- A job dismissed while waiting for speaker names leaves no history record (today's `removeJob`), so it leaves the list; this spec does not change that. [inferred]
- A failed job whose audio was deleted is dropped by the snapshot restore but stays in the history: listed as failed with its reason, Remove offered, Retry not. [inferred]
- Removing a failed job deletes no file: the audio, any transcript draft and the naming sidecars' cleanup stay exactly as `removeJob` handles them today (`PipelineQueue.swift:551-573`). [inferred]
- Entries written before this change have no app, date, duration or participants: shown as "—", matched by title only, sorted last. [inferred]
- The output folder may have moved since a job finished. Open and Show in Finder check the file at click time and say it is missing; in the App Store build a file outside the current output folder may also be unreachable because no security scope covers it, which then reads the same way. [inferred]
- More than 1000 finished jobs: the oldest records drop out of the history (and the window); their files stay on disk. [inferred]
- Participant names of finished jobs now stay on disk in the owner-only history file (the pipeline snapshot drops them once a done job is reaped today); titles and output paths already did. This is what makes participant search survive a restart; the file stays local and owner-only. [inferred]
- The menu's keyboard shortcut works while the menu is open, like every other menu item; it is not a system-wide hotkey. [inferred]
- Type-check budget: `MenuBarView` and the scene `body` are split into hoisted properties because the analyze build fails any body over 300 ms (`MenuBarView.swift:41-55`, `MeetingTranscriberApp.swift:111-118`); new view code follows that. [inferred]
- No `CLAUDE.md`/`AGENTS.md` edits (fork rule): the change is a candidate for the original. [inferred]

## Acceptance Criteria

- **R1:** The menu has an item "All Transcriptions..." with key equivalent ⌘T that opens a window titled "Transcriptions", or brings it to the front when it is already open; opening it starts the pipeline the way importing a file does when it has not started yet. Errors: if no transcription engine is wired, the window still opens and lists what the history holds. [paraphrase]
- **R2:** The window lists every job the app knows, once each: the pipeline's jobs (waiting, running, waiting for speaker names, done, failed) and every finished job in the history, newest first, each with title, app, date and time (meeting start, or when the job was added for an import), duration, and status: Waiting, the running stage, "Speaker names needed", "Done" or "Done, with warnings", "Failed". Errors: a value an entry does not have (history written before this change, or a duration not yet measured) shows "—", and entries without a date sort after all dated ones. [paraphrase]
- **R3:** Restarting the app leaves the list unchanged: finished jobs come back from the history, failed and naming-pending jobs from the pipeline snapshot once the pipeline starts, which opening the window does. Errors: an unreadable history file yields an empty history, is logged and never blocks launch (as today); a failed job whose audio is gone stays listed as failed, without Retry. [paraphrase]
- **R4:** A search field filters the list to entries whose title or any participant contains the typed text, ignoring case and diacritics; an empty field shows every entry. Errors: no match shows "No transcriptions match"; entries without participants match by title only. [paraphrase]
- **R5:** An entry with a protocol or transcript offers "Open" (the protocol, or the transcript when there is no protocol) and "Show in Finder" (reveals that file). Errors: when the file no longer exists, nothing opens and the window says the file was moved or deleted; an entry with neither file offers neither action. [paraphrase]
- **R6:** A failed entry shows its error text, offers "Retry" whenever the pipeline would accept a retry now (the menu's existing rule) and always "Remove"; Remove takes the entry out of the window, the menu and the history without deleting any file, and it stays gone after a restart. Errors: Retry is not shown when the audio is gone or another job holds it; Remove is never offered for an entry that is not failed. [paraphrase]
- **R7:** The menu lists every unfinished job (waiting, running, waiting for speaker names) and only the 3 most recently finished jobs (done or failed, from the same list as the window, "most recently" meaning by when they finished, so a retried older job that just finished is among them), shown in the order jobs were added, so its length no longer grows with the number of finished jobs. Unfinished lines keep today's actions; a finished line offers "Open" when a file exists, "Retry" under R6's rule and "Remove" when failed, and no "Dismiss". Errors: with fewer than 3 finished jobs it shows those; a failed job known only from the history offers Remove but not Retry until the pipeline has loaded it; Open on a file that no longer exists opens nothing, as today. [paraphrase]
- **R8:** The window's scene id is on none of the debug RPC server's window allowlists (`/screenshot`, `/ui/tree`, `/ui/press`, `/ui/type`), and no accessibility identifier added for the window or the menu contains a title, participant or path. Errors: no error surface. [paraphrase]
- **R9:** `GET /v1/jobs/<id>` returns the same fields as before (none added), including for jobs recorded before this change; the one behaviour change is that a failed job the user removed answers `404`, like a cancelled one, and the API documentation says so along with the new history size. Errors: a history file written by this version stays readable by the previous version (unknown keys ignored), and a file written before it loads with every record. [inferred]
