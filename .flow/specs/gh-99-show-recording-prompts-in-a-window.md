## Goal & Context

A person who works with a Focus mode on, or who simply misses a banner, today loses meetings without noticing: the recording prompt expires and counts as declined, and the end countdown stops a recording the person wanted to keep. With the new setting on, both questions also appear in a small window right below the menu bar icon. The window stays on screen until the question is settled, so the person sees it during the call and can answer it with one click, without leaving the meeting window. With the setting off, nothing changes. [paraphrase]

Focus holds the notifications back because the fork's own build does not carry the restricted Time Sensitive notification entitlement (the issue's log shows `timeSensitive=notSupported`; `scripts/lib/signing.sh` adds the key only when a provisioning profile allows it). The window does not depend on notifications at all. [inferred]

What the code does today (checked 2026-11-12 on `wapp/main` 4f3818b4). Specs gh-3, gh-49, gh-54 and gh-58 are done and merged; nothing this spec needs is still open. [inferred]

- The open recording prompt is `WatchLoop.pendingConsentQuestion` (`ConsentQuestion`: id, app, title, body). The menu answers it by id through `WatchLoop.answerParkedConsent` → `AppNotifying.answerConsentPrompt(id:granted:)` → `ConsentPromptCoordinator.resolve(id:…)`, the call a notification tap makes. That path carries only yes or no: "Never for this app" exists in the notification only. [inferred]
- The prompt is parked even when the person switched notifications off: `NotificationManager` refuses delivery only without an app bundle or before set-up. Its text names the app, never the meeting title: "Record <App> meeting?" / "A meeting is active in <App>. Everyone must agree to being recorded." [inferred]
- The end countdown has no question value. `WatchLoop.askToEnd` stores only `meetingEndQuestionID`; the deadline lives in a local `MeetingEndPhase` inside `waitForMeetingEnd`, and the text ("Meeting seems to have ended" / "No sign of the <App> call. The recording ends in 2 minutes.") is built inline. A notification tap answers through the `MeetingEndQuestions` registry by id (each question at most once); the loop applies the answer and withdraws the notification on its next poll (3 s by default). This is point 2 of issue #80. [inferred]
- The icon already shows a question mark for an open prompt (gh-49) and pulses during a countdown (gh-58). The live caption panel (`LiveCaptionsWindowController`) and the speaker naming window (`NamingWindowPolicy`) show how the app builds a floating, non-activating panel on all Spaces. [inferred]

## Architecture & Data Models

- **The countdown becomes a question value.** A small value type `MeetingEndQuestion` (id, app label, title, body, deadline) is built once in `askToEnd`, before the question is posted; its title and body are exactly what is posted, and its deadline is the one the loop's countdown uses. The loop stores it as `meetingEndQuestion`; `meetingEndQuestionID` becomes a read-only computed view of `meetingEndQuestion?.id`, so its readers (the icon pulse, the answer guard, the withdraw) keep working and the two cannot disagree. It is cleared on every way out of the question, as the id is today. This is the observable countdown state that #80 point 2 asks for; the shared question mechanic of #80 is not built here. [inferred]
- **One answer path per question, by id.** The window answers through the calls a notification tap uses, never through a second registry. [paraphrase]
  - Recording prompt: the answer-by-id call carries a full `ConsentAnswer` (Record = granted, Ignore = declined, Never = never), so "Never for this app" from the window resolves the parked prompt in `ConsentPromptCoordinator` exactly as the notification's Never does, and the loop's existing completion puts the app on the deny list. The menu keeps its current Record / Ignore behaviour on the same call. [inferred]
  - Countdown: `AppNotifying` gains an answer-by-id call for the meeting-end question (default: answers nothing and returns false). `NotificationManager` takes the handler from `MeetingEndQuestions`, the registry a tap uses, so each question is answered at most once whoever answers first. A `WatchLoop` accessor answers only when the given question is still the open one, like `answerParkedConsent`. [inferred]
- **What the window shows is one pure decision.** Inputs: the setting, the open recording prompt, the open countdown question, and the ids the person closed with ✕. Output: the ordered list of questions to show (countdown first), empty when the window must be closed. The window controller only renders this list; the bulk of the tests run against it. [inferred]
- **The window.** A new AppKit controller owns one `NSPanel` hosting a SwiftUI view, built with the live caption panel's recipe: non-activating, status-bar level, `canJoinAllSpaces` + `fullScreenAuxiliary`, not hidden on deactivate, never key or main. It is shown with `orderFrontRegardless` and never activates the app. It carries a window identifier so the debug `/state.windows` lists it. Its sharing type is set to "none" as a best effort against screen capture (A1). [inferred]
- **Placement is a pure function.** Inputs: the frame of the menu bar icon's window when it can be read, the screens' frames and visible frames, and the window's size. Output: the window's origin, its top edge at the bottom of the menu bar, centred under the icon and kept inside the screen; without a usable icon frame, at the top right of the screen that holds the menu bar. The icon frame is read from the window AppKit creates for the app's menu bar item, found among the app's own windows. As issue #99 asks, the build first proves this read in the running app (icon visible, icon in the notch overflow, icon hidden by a menu bar manager) before the window is built on it; the fallback keeps the feature working when the read fails. [paraphrase]
- **Time left.** The countdown row computes the time left from the question's deadline once per second while the window shows; it never feeds anything back into the loop, whose own deadline stays the only one that ends the recording. [inferred]
- **The setting.** One stored Boolean on `AppSettings`, default off, with a switch and its help text in Settings → General. [paraphrase]
- **Both build variants.** Nothing here sits behind `#if !APPSTORE`: the panel, the question values and the answer calls work in the App Store build too. Only the `/state.windows` listing is debug-only, as today. [inferred]

## API Contracts

None for outside clients: no new automation endpoint, and the `/state`, `/v1/watch` and `/v1/record` fields stay unchanged. The window is internal UI; the debug `/state.windows` list shows it like the app's other windows, which the live check uses. [inferred]

## Edge Cases & Constraints

- **Answered elsewhere just before the click.** The window can lag a moment behind the question (the countdown closes on the loop's next poll). A click on a question that is no longer open finds nothing under its id and changes nothing; it never answers a different question. [inferred]
- **Between setting and parking.** The recording prompt is set before the coordinator registers it; a click in that moment returns false, changes nothing, and the window stays (gh-49 has the same window for the menu). [inferred]
- **Answer after the deadline.** A "Keep recording" given after the countdown reached 0:00 counts for nothing, exactly as a late notification tap (gh-54 rules); the window shows 0:00 until the loop ends the recording at its next poll. [inferred]
- **Another meeting records while a prompt is open.** The window still offers the prompt; a Record answer is dropped as a notification Record is today ("an approval is not a reservation"). [inferred]
- **Both questions open at once** (a countdown for the recording meeting while another app's prompt waits): both show in the one window, the countdown first, each with its own answers and ✕ (A3). Apps waiting behind the open prompt are not shown, as in the notification. [inferred]
- **Notifications switched off, alert style None, or Focus on:** the window shows anyway; that is its purpose. Without an app bundle or before notification set-up (never the case in the installed app) the recording prompt resolves at once as a decline, and the countdown's answer buttons answer nothing; the countdown then ends the recording as gh-54 R5 says. [inferred]
- **Icon position unknown.** The icon hidden in the notch overflow, removed by a menu bar manager, or on a screen whose menu bar is hidden: the window uses the fallback position. A meeting app in full screen hides the menu bar; the window still appears at the same place, over the full-screen app. With several screens, it appears on the screen of the icon's window, else on the screen with the menu bar. [paraphrase]
- **The menu open at the same time:** the menu draws above the window; nothing else changes. [inferred]
- **Keyboard.** The window never becomes the key window, so a key pressed in the meeting app can never answer it. [inferred]
- **Screen sharing.** No public macOS call tells an app that the screen is being shared. The "none" sharing type keeps a window out of some captures, but developer reports say ScreenCaptureKit captures such windows anyway since macOS 15.4, so it is a best effort only, and the help text says so (A1). The window shows only the notification's text, which names the app and never the meeting title. [inferred]
- **Privacy.** No new log line carries a title or app window name; tests use made-up prompts, no real meeting content. [inferred]
- **Build gates.** A SwiftUI body that type-checks for over 300 ms fails the build, so the window's view is split into small properties and reads single-member `AppState` accessors. SwiftLint runs with `--strict`, and `AppState.swift` (600 lines), `MeetingTranscriberApp.swift` (599) and `WatchLoop.swift` (598) sit at the 600-line cap, so new code goes into new files or extensions. [inferred]
- **Docs and fork rules.** The consent prompt paragraph of `docs/architecture/detection.md` and the file table and menu bar sections of `docs/architecture-macos.md` are updated in the same change; `CLAUDE.md` is not edited. [inferred]

## Acceptance Criteria

- **R1:** Settings → General has a switch "Show prompts below the menu bar icon", off by default and kept across launches. Its help text says that the window shows even when a Focus mode holds notifications back, and that others may see it while the screen is shared. Off: no window ever appears and the app behaves exactly as today. Turning it off closes a shown window at once; turning it on while a question is open shows that question. Errors: a missing or unreadable stored value reads as off. [paraphrase]
- **R2:** With the setting on, when a "Record <App> meeting?" prompt opens, a window appears directly below the menu bar icon, in addition to the notification, with the prompt's title and text exactly as posted and the buttons "Record", "Ignore" and "Never for this app". It appears whatever the notification permission, alert style or Focus mode. Errors: a prompt that cannot be posted (no app bundle, notifications not set up) resolves at once as a decline, as today, and its window closes with it. [paraphrase]
- **R3:** "Record", "Ignore" and "Never for this app" answer that prompt by its id through the consent coordinator a notification tap uses, with the notification's effect: Record starts the recording under the existing rules, Ignore starts the same cooldown, Never puts the app on the "Never record these apps" list. The notification leaves Notification Center and the window closes. Errors: a click on a prompt that is no longer open (expired, answered elsewhere, declined by Stop Watching or a manual start, or replaced by a new prompt, also one about the same app) changes nothing and never answers another prompt. [paraphrase]
- **R4:** With the setting on, when a "Meeting seems to have ended" question opens, the window shows its title and text as posted, the time left until the recording ends in minutes and seconds (updated every second, 0:00 at the deadline), and the buttons "Keep recording" and "Stop now". Errors: when the question could not be posted (no app bundle, notifications not set up), the buttons answer nothing and the countdown ends the recording as gh-54 R5 says. [paraphrase]
- **R5:** "Keep recording" and "Stop now" answer that question by its id through the registry a notification tap uses, so each question is answered at most once, with the notification's effect (gh-54 R2 and R4); the notification leaves Notification Center no later than the loop's next poll, and the window closes. Errors: an answer to a question that is no longer open (signal back, already answered in the notification, recording ended) changes nothing; an answer after the deadline counts for nothing, as a late notification tap. [paraphrase]
- **R6:** The window closes when its question ends by any path: answered in the window, the notification, the menu or `POST /action/confirmBrowserConsent`; expired; withdrawn because the signal came back; declined by Stop Watching or a manual start; or its recording ended. It closes no later than one poll interval after the question ended. Errors: none beyond R3 and R5. [paraphrase]
- **R7:** "✕" closes the window for that question only and is not an answer: the question stays open in the notification and the menu, the icon keeps its question mark or pulse, the prompt expires and the countdown ends the recording on time as without the window. A later question (a new id) opens the window again. When a countdown and a prompt are open at once, the window shows both, the countdown first, each with its own buttons and ✕. Errors: none beyond R3 and R5. [inferred]
- **R8:** The window's top edge sits at the bottom of the menu bar, centred under the menu bar icon and kept inside the screen; when the icon's position cannot be read or lies outside every screen, the window sits at the top right of the screen with the menu bar, below the menu bar. It shows on every Space, also over an app in full screen. Showing it and clicking its buttons do not activate the app and do not change the frontmost app; it never becomes the key window, so no key press answers it. Errors: no error surface; a position that cannot be read falls back as stated. [paraphrase]
- **R9:** The window shows only the notification's text (the app name, never the meeting title) and is marked as not to be shared, as a best effort against screen capture. Errors: where macOS or a sharing tool ignores the mark, the window is visible in the share, as R1's help text warns. [inferred]

## Boundaries

- Other notices (recording started or stopped, errors, the 4-hour warning and notices of gh-58, local model notices) do not appear in the window: not in this spec. [paraphrase]
- The long-silence question of #45 does not appear in the window: follow-up. [inferred]
- "Record with Options…" stays in the menu only; the window offers the notification's three answers. [inferred]
- No time left for the recording prompt (its five-minute timeout); no sound, animation or keyboard shortcut; the window cannot be moved or resized and remembers no position: not in this spec. [inferred]
- No detection of screen sharing, and no hiding of the window while sharing. [inferred]
- The notifications themselves, their timeouts, cooldowns and texts, the menu section of gh-49, and the icon marks of gh-49 and gh-58 stay as they are. No new automation endpoint. [inferred]
- The shared question mechanic and the `WatchLoop` split of #80 are not built here; this spec adds only the countdown question value. [inferred]
- The Settings warning that an unseen prompt means nothing is recorded (`BrowserConsentReadiness`) keeps its wording when the window is on: follow-up. [inferred]
- The Time Sensitive entitlement for the fork's own build is not addressed. [inferred]
- Submitting this to the original project is a separate step, not part of this spec. [inferred]
