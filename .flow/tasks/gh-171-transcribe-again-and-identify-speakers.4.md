### Approach
- Name: `<name>.until-<yyyyMMdd_HHmmss>.<ext>` with `-2`, `-3`, … after the stamp. Reuse the stamp formatter Regenerate uses (`ProtocolRegeneration.swift:180`, `DateFormatter.filenameStamp`); the taken check asks the disk and folds case, as `ArtifactRenamePlan.availableStem` (47-59) and `MeetingReportFolder` do; past a fixed upper bound the re-run ends as R6.
- Order: write the list of renames into the record's marker; rename the current transcript and notes to their earlier names; rename the re-run's files to the current names (a meeting renamed to its AI title keeps that name) with a move that never replaces a file, so a name taken meanwhile (Generate Meeting Notes from Transcript writes `<stem>.md` beside a transcript without notes, `PipelineQueue.enqueueNotes(fromTranscripts:)`) fails the step and the swap is undone; a meeting without current notes (they failed, or no provider made any) gets no earlier notes, and the new notes take the name the meeting's notes have by its current transcript's stem; a meeting without a current transcript (its raw transcript not kept: `removeRawTranscriptArtifactsIfSafe`, `PipelineQueue.swift:1082-1125`, deleted it and its segments file, set `transcriptPath` to nil and marked both gone) gets no earlier transcript, and the new transcript takes the path the record lists for its gone transcript (`<notes stem>.txt`, `ProtocolGenerator.swift:244,262`); then one record update lists the new files as present with their current identity, appends both earlier versions as owned `previousProtocol` (`appendKept`), clears the marker, notes the stamp as committed and sets the outcome to finished. Then upsert the finished-job entry (it moves last, so Last Recording shows the meeting); `TerminalJobStore.record` returns whether its save landed (`TerminalJobStore.swift:51-90`, discardable for today's callers). Between the commit and that write, apply the raw-transcript setting as a new meeting's `.done` does (`removeRawTranscriptArtifactsIfSafe`, which task 3's early branch skips for a re-run job): it reads the value admission stamped from Settings (`stampTranscriptOutputOptions`, `PipelineQueue.swift:789-803`), and with "Save raw transcript separately" off and new notes saved it removes the new transcript and its segments file (by the current stem) and marks them gone, so the entry names no transcript; an earlier transcript stays as an earlier version. Once the entry write landed, the job turns into an ordinary finished job, with its transcript, notes and stem (`namingSlug`) set to the current names, which a later Retry Notion Export, Retry Meeting Notes and the held-job cleanup read, and leaves the re-run file; then the Notion export runs as for a new meeting. The re-run's notes were saved under its own stem by `saveGeneratedNotes` (`PipelineQueue+Stages.swift:1228-1268`), which also queued the pending export with its configuration; it starts only now (`startPendingNotionExport`). A failed export does not undo anything. A taken-over entry held for failed notes ends held only when the re-run made no notes (A12): then its notes failure stays, and Retry Meeting Notes reads the new transcript.
- Notion (A26): the export goes to the database the record names for the page. Resolve the configuration with that database in place of Settings' (`NotionExportConfiguration.resolve`, `PipelineQueue+Notion.swift:8-40`; for a re-run, where `saveGeneratedNotes` calls `resolveNotionExport`), so `notionPageToReuse` (186-191) finds the page and the client builds properties from that database's schema (`NotionClient.exportMeeting`, `NotionClient.swift:235-270`); a record without the database uses the configured one (A6). The finished job keeps a field saying its exports go to its page's database, so a later Retry Notion Export of a failed re-run export goes there too.
- Undo: a failed rename undoes the steps done, the pattern of `undoRenames` (`PipelineQueue+Stages.swift:1342`), then task 3's end path. Every rename, of the current files and of the re-run's, passes task 3's file check first.
- Launch, the Architecture table's two remaining rows beside task 3's: a marker with a list of renames is completed when every re-run file it names is there, else undone from the list; a stamp noted as committed while the job is still in the re-run file is handled when the queue restores that file: apply the raw-transcript setting again (a file already gone counts as removed), write the finished-job entry again, turn the job into an ordinary finished job and, with the export on, start its export once from the saved notes through the path `retryNotionExport` takes (`PipelineQueue+Notion.swift:345-400`). The launch's handling of interrupted exports (`recoverInterruptedNotionExports`, and `PipelineQueue+Recovery.swift:57,169`, which only record finished-job history) marks exports failed for a manual retry and starts none, so it does not cover this.
- The swap waits while a regeneration runs (as Move Meeting to Trash does; the queue gets that state injected).
- Notes off (A12): only the transcript is swapped and the current notes stay. Additional reports are not touched (A7).
- Docs: `docs/architecture/pipeline.md` gets the re-run, its marker and the swap; `docs/automation-api.md` says a done job can be live again and what `GET /v1/jobs/<id>` answers during, after and instead of a re-run.

Decisions (reversible, inside the spec):
- Finding 1 fixed by starting the renames only after the done state is confirmed written, not by recovering the swap from the record's marker whatever the saved job state. The spec's commit point clears the marker (Swap order), and its launch row for a committed stamp needs what only the saved job holds: whether the re-run made notes and owes an export.
