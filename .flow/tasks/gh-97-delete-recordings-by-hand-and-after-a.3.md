# gh-97-delete-recordings-by-hand-and-after-a.3 Delete a meeting's files: the Trash mover, Keep and the window's actions

## Description
The part that removes files: a mover that sends a list of a meeting's files to the Trash (manual) or deletes them for good (automatic, used by task .6), one file at a time with a result per file, plus the window's backend actions Move Audio to Trash, Move Meeting to Trash, Retry Deletion and Keep. No view changes here (task .5); the actions are callable and tested on their own, so the manual slice is proven before any button exists.

### Approach
- **Presence**: task .1's `MeetingFilePresence` and `FileIdentity`; never a plain `fileExists`, which cannot tell absence from a denied permission.
- **Pending deletion first** (spec "Pending deletion"): before touching any file, save `pending = PendingDeletion(kind: .audioToTrash | .meetingToTrash | .automatic, paths:, process:)` through the store and start only when that write returned true; `process` names this process (pid and launch time, as `LivenessMarker` identifies an instance) so another running build never treats it as abandoned. Clear `pending` when the action finishes, in the same write that records the outcome.
- **Mover**: `struct MeetingFileRemover` with injected `trash: (URL) throws -> Void` and `removeForGood: (URL) throws -> Void` (production: `FileManager.trashItem(at:resultingItemURL:)` and `removeItem(at:)`; the injection pattern of `ProtocolTemplates.swift:172-176`), and `func remove(_ files: [MeetingFile], mode: Mode, in store: MeetingFileStore, jobID: UUID) -> [FileOutcome]`. Per file: skip one already gone; an unreachable file fails with the reason that its drive or folder is not available; then check it is the same file (spec "Same file, right before removal": `lstat` says regular file, not a symbolic link or folder; its parent resolves to the recorded parent; device and inode match the recorded `identity`), and fail with "the file was replaced" if not; otherwise mark `.deleting` in the record, run the operation, mark `.gone`, or on a throw restore `.present` and fail with a reason (a Trash refusal reads "this volume has no Trash" or the error's text). **A refused Trash never falls back to `removeForGood`** (D6). `removeForGood` in production is `unlink(2)` on that one path, never `FileManager.removeItem`, which would empty a folder put in the file's place.
- **Shared paths**: a path that another record also lists is not removed and stays in this record, reported as blocked ("1 file is also listed by another meeting"); a retry removes it once no other record lists it (R1's error case). A recorded meeting whose audio was later imported as its own meeting is the realistic case: test both deletion orders.
- **Security scope**: run each action inside the scope of the configured output folder when `AppSettings.outputDirectoryResolution` is `.custom` (`AppSettings+OutputDirectory.swift:42`), never on `.fallback`, as `ProtocolRegeneration.swift:489-495` opens it on the resolved root through `SecurityScopeAccess` (`SecurityScopeAccess.swift:22`).
- **Launch reconcile**: at launch, a record whose `pending` names a process that is no longer running is reconciled: each covered file is re-probed (`.deleting` becomes `.present` or `.gone`); a manual kind then becomes `incomplete` with the same kind to retry (or completes, when nothing is left: for Move Meeting that removes the row and record as the action would have), and an automatic kind is cleared without `incomplete`, so the next check simply runs again. A crash between two files is covered the same way, since `pending` lists every file. A `pending` owned by a live process is left alone.
- **Actions** on `PipelineController` (`PipelineController+Transcriptions.swift`, beside `removeFailedJob`):
  - `moveAudioToTrash(jobID:)`: the audio roles that are owned and present; sets `audioDeletion = manual(at: now)` when all moved, else `incomplete` with the reason and the paths left (R5).
  - `moveMeetingToTrash(jobID:)`: every owned file; on full success removes the job from the queue if it is still listed, its `TerminalJobStore` entry and its record, so `GET /v1/jobs/<id>` answers 404 (A5); otherwise `incomplete`, and the row stays (R6, D7). A meeting with no local file left (A12) moves nothing and is removed the same way. `removeJob` silently keeps a done job with a Notion export in progress, so re-check before the first move and leave such a meeting untouched (R6, A9). The Notion page is never touched: no Notion call in this path (A10).
  - `retryDeletion(jobID:)`: repeats the kind stored in `incomplete` on the files still there; when none are left it completes as the original action would (R5, R6).
  - `setKeep(jobID:, _:)` (R8).
  - Each action refuses (returns false, changes nothing) when its pending write cannot be saved, while another deletion of the meeting is pending, for a meeting without a record (A2), a failed meeting (A3), and a live job that waits, runs, awaits speaker names or has a Notion export running (R4, A9); `moveAudioToTrash` and `setKeep` refuse an import (A4). These guards repeat the menu's rule on purpose, so a stale menu cannot act on a meeting that changed state.
  - The clock is injected (`now: () -> Date`, as `RemoteVocabularyController.swift:62-63`).
- **Tests, written first**: `MeetingFileRemoverTests` in a temp folder with an injected `trash` (moves into a fake Trash folder, or throws): audio moved while transcript and protocol stay; a refusing Trash leaves the file, sets the reason, and never calls `removeForGood`; a missing parent folder is unreachable, not gone; a file the user removed counts as gone without a failure; a file replaced by another file, by a folder (with a file inside that must survive) or by a symbolic link, and a parent folder replaced by a symbolic link, are not removed and fail; a shared path stays and is removed by a retry once the other record is gone, in both deletion orders; a failed pending write starts nothing; a `pending` from a dead process left after the first of three files reconciles to `incomplete` with the same kind (manual) or clears (automatic), and a `pending` of a live process is left alone. `PipelineControllerTranscriptionsTests` also runs a recorded meeting through the queue, confirms its speaker names (and, in a second case, runs a late re-diarization), then moves the whole meeting to the Trash and expects it to complete with nothing reported as replaced. `PipelineControllerTranscriptionsTests`: Move Meeting removes the record, the finished-job entry (`lookup(jobID:)` is nil) and the queue job; a meeting with no local file left goes the same way; an import's source file is not moved; Retry Deletion moves only the remaining file and then completes; each refusal case changes nothing; Keep survives a new store on the same file.

### Key context

### Decisions

DECIDED: `PendingDeletion.process` defaults to the current process, because `MeetingFileStoreTests`, outside Touches, builds one without it (rule 6).
DECIDED: a pending deletion names its process by ID and kernel start time, and a refused read counts as running. `LivenessMarker` goes by bundle ID, which is what tells the two builds apart, so another build's deletion would read as abandoned. `NSRunningApplication.launchDate` is nil for a process LaunchServices did not start (rule 1: spec "One writer").
DECIDED: only outcome `.finished` is actionable. `.inProgress` also covers another build's run and an unread snapshot, and `.leftUnfinished` keeps its audio (rule 1: A3, R4, spec edge cases).
DECIDED: every action builds the queue first, as `removeFailedJob` does, so a job only the snapshot knows is seen. The launch reconcile does not, as building it would resume other saved jobs (rule 1: `docs/architecture/pipeline.md`, `restorePendingNotionExports`).
DECIDED: the launch reconcile runs from `PipelineController.activate`, because the launch hooks in `MeetingTranscriberApp` are outside Touches (rule 6).
DECIDED: a meeting with nothing left to move and only an unread snapshot is taken out of that file directly. `removeJob` on the bare queue would save its empty list over the snapshot, and leaving the meeting incomplete would contradict the acceptance. A failed snapshot write keeps the pending mark, so the next launch tries again (rule 1: A12).
DECIDED: the shared-path check and the one-deletion-at-a-time check run under the record file's lock (rule 1: spec "One writer").
DECIDED: a path a not-owned entry of the same record also lists is never moved, and each path is covered once (rule 1: R1).
DECIDED: Retry derives its files from the record, so a file listed since the failure is not left behind and a retry with nothing left completes (rule 6).
DECIDED: Move Audio refuses when no audio entry is left, so the date of an earlier deletion stays (rule 1: R4). It also refuses while the meeting's own Move Meeting is incomplete, because finishing there would replace the record of what is left of the meeting (rule 6). Task .5's menu needs to match this.
DECIDED: an interrupted automatic deletion that had removed everything records `audioDeletion = automatic(now)`. Clearing the mark alone would leave the row reading "Audio not found", and the next check has no file left to act on. With files left, it only clears the mark, as the spec says (rule 6).
ASSUMED: the unreachable reason reads "on a drive or in a folder that is not available" · alternatives: B — the mockup's "on a drive that is not connected", which a permission error or a deleted folder would misreport; C — separate texts for each · flip at: `MeetingFileRemover.failureReason` · test: `testTheReasonCountsItsFilesAndKeepsTheRefusalsText`.
